Fine-tuning vs RAG vs prompting

Every capability you add to an AI product has exactly three homes: the words you send, the text you retrieve at query time, or the weights themselves. The most expensive mistakes in this space are capabilities placed in the wrong home.

Why you need it
  • Prompt ceiling: some behaviors refuse to stabilize from words alone, brand voice, format edge cases, niche jargon, refusal patterns.
  • Prompt bloat tax: teaching style with a 3k-token system prompt means paying that tax on every single call, see tokens and caching.
  • gotcha The classic mistake: fine-tuning to teach facts. Weights are a terrible knowledge store, frozen, expensive to refresh, no citations. Facts belong in RAG.
  • The opposite mistake: scheduling a training run for something a structured output call already solves, see tool calling.
  • Modern reset: long context windows plus prompt caching absorbed many old fine-tuning use cases, so the bar for tuning is higher than it used to be. What survives: tuning small models for narrow high-volume tasks as a cost play, plus style and format discipline that prompting cannot hold.
Solutions

Climb the ladder cheapest rung first: prompt it, retrieve it, then train the residual into the weights. Each rung costs roughly 10× the effort of the one before.

flowchart TD
  A["new capability"] --> B["prompt +<br/>structured output"]
  B --> C{"holds on<br/>edge cases?"}
  C -- yes --> D["ship it"]
  C -- no --> E["RAG for<br/>fresh facts"]
  E --> F{"style still<br/>slips?"}
  F -- yes --> G["LoRA tune<br/>the residual"]

How it works

  • Capability lives in the words you send: system instructions, few-shot examples, output contracts.
  • Changes ship in seconds, no training, and you debug it by reading it.
  • Output shape is not a prompt problem at all: extraction into a schema is solved with structured output plus a few examples.

Trade-offs

  • pro: cheapest and fastest rung to try, iterate in minutes.
  • con: token tax per call, a 3k-token style prompt is paid on every request.
  • con: weakest at consistency across edge cases, and quality drops on huge prompts.
  • con: facts that grow or change will overflow it, that is a retrieval problem.

How it works

  • Capability lives in the retrieval layer: relevant text is fetched at query time and grounded into the prompt, see RAG overview.
  • Fresh per document: a doc fix ships in minutes, no retrain, and answers can cite the page.
  • The only home that supports real citations back to source documents.

Trade-offs

  • pro: the right home for fresh, private, changing facts.
  • con: costs an ingestion pipeline to run and debug, plus updates per document.
  • con: awkward under hard latency floors or zero-ops constraints.

How it works

  • is the family name: a small fourth training stage (after the three that built the base, see how LLMs work) run by you, on your examples.
  • is the default recipe: freeze the base, train adapters. shrinks the bill further.
  • Data beats everything: hundreds to a few thousand excellent pairs outperform tens of thousands of mediocre ones. Dedupe, balance classes, match the chat template exactly.
  • Train: LoRA on a 7B to 70B base. Hours, not months. Hundreds of dollars, not millions.
  • Deploy: behind the same chat API. Swap the model name, keep the rest of the stack.

Trade-offs

  • pro: style, format discipline and jargon that prompting cannot hold, held as a guarantee on every call.
  • pro: at volume, a tuned small model with a short prompt beats a big model dragging a giant prompt on latency and cost. Classification and extraction at high volume are the classic wins.
  • gotcha con: catastrophic forgetting. Tuning on a narrow task erodes general ability. Keep a general eval set and check it after every run, see evals.
  • con: retrain per base upgrade. Version fine-tunes as artifacts with a retraining trigger.
  • con: worst home for facts, arithmetic or citations, anything without an eval set.
When to use · when not

Use when

  • The base model almost knows the task and words alone close the gap, prompting rung.
  • Facts are fresh, private or changing, and citations are required, RAG rung.
  • Style or format must hold on every edge case at high volume, tune rung.
  • A narrow high-volume task where a tuned small model wins on cost and latency.

Skip when

  • The transform is exact and writable in normal code.
  • You want facts in weights, they stale on contact with the world.
  • There is no eval set to prove the tune beats the base.
  • The latency floor is too tight for a retrieval step.

Full pretraining is not on the ladder. It buys new languages or domains at scale for millions of dollars, provider territory, see how LLMs work.

Example

A LoRA recipe in a few lines: freeze the base, attach rank-16 adapters beside the attention projections, train on a few thousand pairs, then eval against the base. Below it, one need per rung of the ladder.

from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")

cfg = LoraConfig(r=16, lora_alpha=32,  # rank 16 covers style + format
                 target_modules=["q_proj", "v_proj"],
                 task_type="CAUSAL_LM")
model = get_peft_model(base, cfg)  # well under 1% of params trainable
print(model.print_trainable_parameters())
# next: SFTTrainer on a few thousand pairs, then eval against the base
  • Support tone, tune: a bank tunes a small model on 2k polished replies, cuts its prompt from 3k to 300 tokens and its bill accordingly, see tokens and caching.
  • Product docs, RAG: a support bot answers from the current manual. A doc fix ships in minutes, no retrain, and answers cite the page, see RAG overview.
  • Output JSON shape, prompt: extraction into one schema is solved with structured output plus a few examples, no training needed.
  • Cost play, tune: a clause classifier fine-tuned onto a small model replaces a frontier model with a giant prompt.
Watch out
  • Fine-tuning for facts · weights are a stale snapshot the day you ship them · prices, policies and news belong in retrieval
  • Stale adapters · a new base model means a retrain · version fine-tunes with a retraining trigger
  • Eval gap · tuning without a golden set is flying blind · if the tune does not clearly win, the data was the problem
  • Alignment drift · safety training weakens when you tune · red-team your own model before shipping, see prompt injection
  • Skipping rungs · paying 10× to train what a prompt already solved · re-check the ladder every quarter, the prompt rung keeps getting stronger
Remember
  • Ask where the capability lives: words, retrieval, or weights.
  • Climb the ladder in order: prompt, RAG, fine-tune the residual.
  • Facts go to retrieval, behavior goes to weights, output shape goes to structured output.
  • Try long context and prompt caching before tuning for cost.
  • Hundreds of good pairs beat tens of thousands of bad ones.
  • Eval against the base before swapping, and keep a general eval set for forgetting.
  • You can read a prompt and inspect retrieved chunks, weights only show you metrics. The worst bugs live in the home you cannot see.
