Fine-tuning vs RAG vs prompting

A capability can live in the instructions you send, evidence retrieved at query time, or model weights, and sometimes in deterministic code or external systems. The most expensive mistakes here are capabilities placed in the wrong home.

In this chapter Decide which behavior belongs in a prompt, retrieval index or model weights by freshness, consistency, latency and evidence needs.

Why this layer matters

  • Prompt ceiling: some behaviors never stabilize from words alone: brand voice, format edge cases, niche jargon, refusal patterns.
  • Prompt bloat tax: teaching style with a 3k-token system prompt means paying that tax on every call, see tokens and caching.
  • gotcha The classic mistake: fine-tuning as the only store for changing facts. Weights can absorb facts but are harder to refresh, inspect and cite than retrieval. For fresh, attributable facts, use RAG.
  • The opposite mistake: scheduling a training run for something a structured output call already solves, see tool calling.
  • Modern reset: long context plus prompt caching absorbed many old fine-tuning use cases, raising the bar for tuning. What survives: small models tuned for narrow high-volume tasks as a cost play, and style or format discipline prompting cannot hold.

Decision model

Climb the ladder cheapest rung first: prompt it, retrieve it, then train the residual into the weights. Each later rung usually adds data, evaluation and operations work.

How it works

  • Capability lives in the words you send: system instructions, few-shot examples, output contracts.
  • Changes ship in seconds with no training, and you debug by reading.
  • Output shape is not a prompt problem: schema extraction is solved with structured output plus a few examples.

Trade-offs

  • pro: cheapest, fastest rung; iterate in minutes.
  • con: token tax per call: a 3k-token style prompt is paid on every request.
  • con: weakest at consistency across edge cases, and quality drops on huge prompts.
  • con: growing or changing facts overflow it; that is a retrieval problem.

How it works

  • Capability lives in the retrieval layer: relevant text is fetched at query time and grounded into the prompt, see RAG overview.
  • Fresh per document: a doc fix ships in minutes, no retrain, and answers can cite the page.
  • Citations: the only home that can point back to source documents.

Trade-offs

  • pro: the right home for fresh, private, changing facts.
  • con: an ingestion pipeline to run, debug and update per document.
  • con: awkward under hard latency floors or zero-ops constraints.

How it works

  • is the family name: a small fourth training stage, after the three that built the base (see how LLMs work), run by you on your examples.
  • is the default recipe: freeze the base, train adapters. shrinks the bill further.
  • Data beats everything: a small, curated, diverse set can beat a larger noisy one; the right volume depends on task coverage. Dedupe, balance classes, match the chat template exactly.
  • Train: LoRA adapts an open model; duration and cost depend on model size, dataset, hardware and sequence length, so estimates are workload-specific.
  • Deploy: behind the same chat API; swap the model name, keep the stack.

Trade-offs

  • pro: style, format and domain vocabulary become more reliable across calls, though no single output is guaranteed.
  • pro: at volume, a tuned small model with a short prompt beats a big model with a giant prompt on latency and cost; high-volume classification and extraction are the classic wins.
  • gotcha con: catastrophic forgetting: narrow tuning can erode general ability. Re-run a general eval set after every run, see evals.
  • con: retrain per base upgrade; version fine-tunes as artifacts with a retraining trigger.
  • con: worst home for facts, arithmetic, citations, or anything without an eval set.

Decision boundary

Use when

  • Prompt: the base model almost knows the task and words close the gap.
  • RAG: facts are fresh, private or changing, and citations are required.
  • Tune: style or format must hold on every edge case at high volume.
  • A narrow high-volume task where a tuned small model wins on cost and latency.

Skip when

  • The transform is exact and writable in normal code.
  • You want facts in weights; they go stale on contact with the world.
  • There is no eval set to prove the tune beats the base.
  • The latency floor is too tight for a retrieval step.

Full pretraining is not on the ladder: it needs data, compute and operations at a scale few teams have. See how LLMs work.

Worked example

A LoRA recipe: freeze the base, attach rank-16 adapters beside the attention projections, train on a few thousand pairs, eval against the base. Below it, one need per rung.

from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")

cfg = LoraConfig(r=16, lora_alpha=32,  # rank 16 covers style + format
                 target_modules=["q_proj", "v_proj"],
                 task_type="CAUSAL_LM")
model = get_peft_model(base, cfg)  # well under 1% of params trainable
print(model.print_trainable_parameters())
# next: SFTTrainer on a few thousand pairs, then eval against the base
  • Support tone, tune: a bank tunes a small model on 2k polished replies, cuts its prompt from 3k to 300 tokens and its bill accordingly, see tokens and caching.
  • Product docs, RAG: a support bot answers from the current manual; a doc fix ships in minutes and answers cite the page, see RAG overview.
  • Output JSON shape, prompt: extraction into one schema is solved with structured output plus a few examples, no training needed.
  • Cost play, tune: a clause classifier fine-tuned onto a small model replaces a frontier model with a giant prompt.

Failure modes

  • Fine-tuning for facts · weights are a stale snapshot the day you ship them · prices, policies and news belong in retrieval
  • Stale adapters · a new base model means a retrain · version fine-tunes with a retraining trigger
  • Eval gap · tuning without a golden set is flying blind · if the tune does not clearly win, the data was the problem
  • Alignment drift · safety training weakens when you tune · red-team your own model before shipping, see prompt injection
  • Skipping rungs · paying 10× to train what a prompt already solved · re-check the ladder quarterly, the prompt rung keeps getting stronger

Keep in mind

  • Ask where the capability lives: words, retrieval, or weights.
  • Climb the ladder in order: prompt, RAG, fine-tune the residual.
  • Facts go to retrieval, behavior goes to weights, output shape goes to structured output.
  • Try long context and prompt caching before tuning for cost.
  • Hundreds of good pairs beat tens of thousands of bad ones.
  • Eval against the base before swapping, and keep a general eval set for forgetting.
  • Prompts and retrieved chunks are readable; weights only show metrics. The worst bugs live in the home you cannot see.
