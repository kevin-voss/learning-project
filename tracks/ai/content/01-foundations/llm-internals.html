How LLMs actually work

A decoder-only language model is trained to predict the next token; system behavior also depends on architecture, training data, prompting, tools, serving code and policy.

In this chapter Trace how tokens become a response: distinguish prompt prefill from autoregressive decode, then connect training, sampling and per-request KV state.

Why this layer matters

  • Debugging blind: hallucinations, ignored system prompts and forgotten turns stay mysteries, not bugs, without a mental model.
  • Costs stay opaque: context limits, token prices and cache discounts follow from what a token costs to process, see tokens, cost, caching.
  • Knobs feel arbitrary: temperature, top-p and max_tokens have precise effects, yet teams tune them by vibes.
  • Security reasoning fails: prompt injection is obvious once you see that instruction hierarchy only influences behavior; trusted application code must enforce access.

Mechanism

Five connected mechanisms explain most everyday LLM behavior: next-token prediction, tokens and attention, sampling, training, and per-request KV state.

How it works

  • The loop: the network assigns a probability to every token in its model-specific vocabulary (sizes vary widely), one is picked and appended, and the loop repeats until a stop token.
  • Prediction, not lookup: no fact database sits inside. A question gets the most plausible continuation, not a fetched answer.
  • Knowledge lives in : training text is compressed into learned numbers, which is why one reply can hold tax-law poetry and an invented court case.
  • Planning can be learned or orchestrated: the base model only predicts next tokens; products add explicit planning, inference-time search, tools or workflow state around it.

Request context and external state

  • Per-request input: the model sees only the context assembled for this call. Stored conversation state is re-supplied by the app, never held in the weights.
  • Chat "memory" is your app re-sending history every turn, which is why context engineering and memory strategies exist as disciplines.
  • Overflow is a policy: the API or app may reject, truncate or compact. Make it observable; do not assume the oldest tokens silently drop.

Trade-offs

  • con: fluent is not true. Plausible continuation fills gaps between training patterns with confident invention. Ground with RAG and verify with evals.

How it works

  • Text is cut into by a model-specific vocabulary of subword pieces. Common words stay whole; rare words and new emojis split into several pieces.
  • Token meters: context windows, embedding input limits and input/output pricing count tokens. Chunking policies may use tokens, characters or structure.
  • Causal self-attention: each token becomes a vector that attends to itself and earlier positions, never future ones; that is how “bank” resolves its meaning. The mask lets prefill compute all prompt positions in parallel; decode adds one token at a time.
  • Layers: a stack of transformer layers refines contextual representations. What individual layers encode is model-specific; there is no fixed syntax-to-meaning map.

Trade-offs

  • why con: dense self-attention prefill does pairwise work that grows roughly with sequence length squared; total serving cost also depends on decode length, batching, architecture, hardware and caching.
  • con: long-context position sensitivity varies by model and task; test representative inputs, do not assume the edges always win.

  • cuts the candidate pool to the smallest set whose probabilities sum to p, then samples inside it. That removes catastrophic tail picks without flattening good variety.

How it works

  • Pretraining (broad capability): next-token prediction over trillions of tokens of internet-scale text, for months on GPU clusters, done once by the provider. The weights reflect training patterns but are not a clean fact store.
  • SFT, instruction tuning (format): fine-tune on curated instruction-response pairs, turning a text-continuer into an assistant that answers. Prompt-following is shaped here.
  • RLHF and DPO: RLHF fits a reward model to preference comparisons and optimizes the policy against it; DPO optimizes preference pairs directly, with no separate reward model. Stages are not strict compartments: knowledge and behavior can shift in any of them.
  • Inference (serving): not a training stage. Served weights stay fixed; the application supplies request context and may keep external state. Fine-tuning, when chosen, updates weights.

Trade-offs

  • pro: the stages tell you what you can change: prompting changes supplied context, retrieval adds source material at inference, fine-tuning updates weights and can shift behavior or learned knowledge.
  • con: alignment lives in the last mile, which is why your own tuning can erode refusals, see guardrails.

How it works

  • Generating a token needs attention over all previous tokens. The stores those computed states so past work happens once.
  • Latency: prefill finishes before the first generated token, so it sets time-to-first-token. Each decode step still attends over the growing cached history and is often memory-bandwidth bound.
  • Consequence: some providers reuse shared prefix computation across requests under their own eligibility, retention and pricing rules. That is distinct from per-request KV state and from application response caches. See prompt caching.

Trade-offs

  • pro: a provider may discount eligible cached input tokens; retention and rates vary, so check current rules.
  • con: a huge uncached prefix plus an unbounded max_tokens turns one runaway loop into a large bill.

Decision boundary

Use when

  • Fuzzy language in or out: parse, summarize, draft, classify, chat, tasks whose rules cannot be written down.
  • Knowledge is unstructured: answers live in scattered docs, tickets and PDFs, paired with RAG.
  • Long tail of variants: a flexible fallback for inputs nobody enumerated.
  • Ambiguity is the job: drafts, options and brainstorming where variety helps.

Skip when

  • The transform is exact and writable: totals, tax math, schema validation, sorting. An LLM adds cost, latency and drift for zero gain.
  • Answers must be audit-grade correct every time. Confidence is not correctness; keep a human path.
  • Volume is huge and the pattern is fixed: rules are cheaper and stable.
  • Downstream needs one canonical answer, so variety is a bug. Route easy cases to rules, only the hard tail to the model.

Worked example

Illustrative Python for an OpenAI-compatible API: count tokens for a sample model, then compare two temperatures. Tokenizers and supported parameters vary by model and provider; check the docs for yours. You can follow it without making a call.

import tiktoken, openai
enc = tiktoken.encoding_for_model("gpt-4o")

text = "How do refunds work for annual plans?"
print(len(enc.encode(text)))  # illustrative token count; tokenizer is model-specific

for temp in (0, 1.2):
    r = openai.chat.completions.create(
        model="gpt-4o",
        temperature=temp,
        messages=[{"role": "user", "content": "Name three uses for a fork"}])
    print(temp, r.choices[0].message.content)
# Illustrative only: observed variation depends on model and serving configuration.

Failure modes

  • Hallucination is confident interpolation · it cannot flag its own gaps · ground with RAG, require citations, verify with evals
  • Some long-context tasks show position sensitivity · test with your workload, no universal attention pattern · see context budgeting
  • System and developer messages get instruction priority in many interfaces, but prompts do not enforce authorization · retrieved and user content stay untrusted, which is why injection works
  • Model updates silently change behavior · pin versions and add evals
  • Temperature 0 is not a determinism contract · batching, quantization and near-ties flip outputs between runs

Keep in mind

  • It predicts the next token, it does not look facts up.
  • The supplied context is the model-visible working set; overflow is rejected, truncated or compacted by the API or app.
  • Temperature reshapes the distribution, top-p cuts the tail, neither is bit-exact.
  • Pretraining and post-training both shape capability and behavior; the boundaries are not clean.
  • Prefill sets time-to-first-token; the KV cache avoids recomputing past projections, but decode still reads growing history. Shared prefix caches are provider-specific.
  • Fluent is not true. Ground, cite, eval.

Try, verify, explain

  1. Trace the forward pass: prompt positions are prefilled in parallel, the first output token is sampled, then each decode step attends to cached earlier keys and values.
  2. Measure prefill versus decode: stream one fixed prompt with max_tokens 50 and then 500, log time-to-first-token and total time for each, and check which number scales with output length.
  3. Explain why a chat model "remembers" turn 1 at turn 20 although its weights never change, and what your app must decide when that history no longer fits the context window.
