How LLMs actually work

An LLM does exactly one thing: predict the next token. Every answer, bug, price tag and security hole in this sheet follows from that one sentence.

Why you need it
  • Debugging blind: why did it hallucinate, why did it ignore the system prompt, why does it forget. Without a mental model these are mysteries, not bugs.
  • Costs stay opaque: context limits, token prices and cache discounts only make sense once you know what a token costs to process, see tokens, cost, caching.
  • Knobs feel arbitrary: temperature, top-p and max_tokens have precise effects, yet teams tune them by vibes for years.
  • Security reasoning fails: prompt injection is obvious once you see that the model treats all text as data, wherever it came from.
Solutions

Five systems explain every LLM behavior you will meet: the prediction loop, tokens and attention, sampling knobs, training stages, and the KV cache.

How it works

  • Text goes in, the network scores every vocabulary token (about 100k of them) with a probability, one gets picked, appended, and the loop repeats until a stop token.
  • Prediction, not lookup: no database of facts sits inside. Ask a question and it generates the most plausible continuation, it does not fetch a stored answer.
  • Knowledge lives in : training text is compressed into learned numbers. That is why the same model can write poetry about tax law and invent a fake court case in one reply.
  • Planning emerged: there is no planner module. Multi-step behavior is a learned pattern of the single next-token objective.

The window is its entire world

  • Everything the model knows about this conversation is exactly the text you sent. No hidden notepad, no session state, nothing between calls.
  • Chat "memory" is your app re-sending history every turn, which is why context engineering and memory strategies exist as disciplines.
  • Overflow the window and the oldest tokens fall out silently. The model will not warn you, it will just calmly answer with half the document.

Trade-offs

  • con: fluent is not true. Its job is plausible continuation, not truth, so it fills gaps between training patterns with confident-sounding invention. Ground with RAG and verify with evals.

How it works

  • Text is cut into by a fixed vocabulary of about 100k pieces. Common words stay whole, rare words split, new emojis split into several pieces.
  • Every limit on this site is a token count: window size, price per million, chunk size, embedding input cap.
  • Each token becomes a vector. Self-attention lets every token read every other token, so "bank" collects its meaning from the words around it.
  • Layers (12 to 100+) refine this. Early layers hold syntax, deep layers hold meaning and task behavior.

Trade-offs

  • why con: attention cost grows with the square of input length. Long prompts get slow and pricey.
  • con: quality droops in the middle, the "lost in the middle" effect. Edges of the window get the most attention.

How it works

  • reshapes the whole distribution. Near 0 the top token almost always wins. Above 1 long-shot tokens get real probability mass.
  • cuts the candidate pool first: keep the smallest set of tokens whose probabilities sum to p, then sample inside it. It removes catastrophic tail picks without flattening good variety.
  • Presets: temp 0 to 0.3 for extraction, code, structured output, evals. 0.7 to 1.0 for prose and ideation. Change one knob at a time or you will never know which one did what.
  • max_tokens is the output budget. Hit it and answers cut mid-sentence, so reserve it in your context budget.

Trade-offs

  • gotcha con: temperature 0 is almost deterministic, not bit-exact. Floating-point order, batching and hardware differences can flip a near-tie, and one flip changes every token after it. Never build a system that requires identical repeats.

How it works

  • Pretraining (knowledge): predict the next token across trillions of tokens of internet-scale text, for months on GPU clusters. Done once by the provider, staggeringly expensive. Facts, style and languages live here, frozen into weights.
  • SFT, instruction tuning (format): fine-tune on curated instruction-response pairs. Turns the raw text-continuer into an assistant that answers instead of continuing. Prompt-following behavior is shaped here.
  • RLHF / DPO (alignment): humans rank outputs, a reward model learns the preference, the model is nudged toward preferred answers. DPO is the simpler pairwise variant. Refusals and persona come from these stages, not from pretraining.
  • Inference (serving): weights stay frozen, only the context changes per request. Generation is the sampling loop above. Your own fine-tuning is a small stage 4 you can run on top.

Trade-offs

  • pro: the stages tell you what you can change: prompting steers SFT-shaped behavior, tuning adds a stage, nothing you do touches pretraining knowledge.
  • con: alignment lives in the last mile, which is why your own tuning can erode refusals, see guardrails.

How it works

  • Generating a token needs attention over all previous tokens. The stores those computed states so past work happens once.
  • Consequence: the prompt is prefilled first, so the first token is the slow one, then generation steps are cheap.
  • Consequence: identical prefixes can be cached server-side and re-sold at a discount. That is the entire basis of prompt caching.

Trade-offs

  • pro: cached prefixes make a repeated system prompt nearly free.
  • con: a huge uncached prefix plus an unbounded max_tokens turns one runaway loop into a large bill.
When to use · when not

Use when

  • Fuzzy language in or out: parse, summarize, draft, classify, chat, tasks whose rules cannot be written down.
  • Knowledge is unstructured: answers live in scattered docs, tickets and PDFs, paired with RAG.
  • Long tail of variants: a flexible fallback for inputs nobody enumerated.
  • Ambiguity is the job: drafts, options and brainstorming where variety helps.

Skip when

  • The transform is exact and writable: totals, tax math, schema validation, sorting. An LLM there adds cost, latency and drift for zero gain.
  • Answers must be audit-grade correct every single time. Confidence is not correctness, keep a human path.
  • Volume is huge and the pattern is fixed, rules are cheaper and stable.
  • One canonical answer is required downstream, variety is a bug. Route easy cases to rules, send only the hard tail to the model.

Example

Counts the tokens of one question with tiktoken, so you see the real unit of price, then runs the same prompt at temperature 0 and 1.2. Expect the same boring list at 0 and riskier picks at 1.2.

import tiktoken, openai
enc = tiktoken.encoding_for_model("gpt-4o")

text = "How do refunds work for annual plans?"
print(len(enc.encode(text)))  # 9 tokens · the real unit of price

for temp in (0, 1.2):
    r = openai.chat.completions.create(
        model="gpt-4o",
        temperature=temp,
        messages=[{"role": "user", "content": "Name three uses for a fork"}])
    print(temp, r.choices[0].message.content)
# temp 0: the same boring list nearly every run · temp 1.2: creative, riskier picks
Watch out
  • Hallucination is confident interpolation · it cannot flag its own gaps · ground with RAG, require citations, verify with evals
  • Attention favors the edges · instructions at the top dilute as the window fills · repeat critical instructions near the end, see context budgeting
  • System prompts are just text, no privileged channel · any text in context counts as instructions, that is why injection works
  • Model updates silently change behavior · pin versions and add evals
  • Temperature 0 is not a determinism contract · batching, quantization and near-ties flip outputs between runs
Remember
  • It predicts the next token, it does not look facts up.
  • The context window is its entire world, and you manage what is in it.
  • Temperature reshapes the distribution, top-p cuts the tail, neither is bit-exact.
  • Knowledge comes from pretraining, assistant behavior from SFT and RLHF.
  • The KV cache makes first tokens slow and cached prefixes cheap.
  • Fluent is not true. Ground, cite, eval.
