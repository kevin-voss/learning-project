Context engineering and budgeting

The model has no memory. What it knows of the conversation is exactly what you put in the window on this call. Context engineering is assembling that window on purpose, every turn, within a budget.

Why you need it
  • There is no memory. The API takes a messages array (system, user, assistant, tool roles), no session object exists on the server. Your app owns the transcript, stores it, rebuilds the array for every call.
  • Miss one message and, for the model, it never happened. No hidden state, no "it probably remembers".
  • The window silently fills. At turn 40 the history alone can blow past the budget, and tool results plus retrieved docs arrive mid-run, after you already sized the prompt.
  • Quality drops before the limit. means more tokens can equal worse answers, see how LLMs actually work.
  • Naive trimming cuts the wrong things: "it" loses its antecedent, "as we discussed" points nowhere, the first turn's goal silently vanishes.
  • Users expect continuity anyway. "Last week you said" must work. Cross-session facts are a separate system, see memory. This topic is the window you build each turn.
Solutions

Treat the window as a budget: every slice gets a cap enforced in code, then spend it deliberately, summarize the old, keep the recent verbatim, place instructions early and data late.

System prompt · 5 to 10%

  • Rules, voice, format contracts
  • Stable across calls

Tool schemas · 2 to 5%

  • Every tool's JSON Schema rides every call, see tool calling
  • Grows silently as you add tools

Retrieved docs · 30 to 40%

  • Only what this turn needs, chosen by retrieval
  • Never a "just in case" dump

History · 20 to 25%

  • Running summary plus the last K turns verbatim
  • The slice compaction manages

Output reserve · 20 to 25%

  • Room for the answer, thinking and tool-call arguments
  • Guarded by max_tokens

The rule

  • Every slice gets a cap, caps enforced in code
  • Caps sum below the window, money lives in tokens, cost and caching

How it works

  • Two history layers: a running summary compresses the oldest turns, the last K turns stay word-for-word because users quote you on them.
  • Preserve anchors: decisions made, names, numbers, open questions. A summary that loses the decision is worse than truncation.
  • Structure beats narrative: a "decisions / open questions / facts" block outlives a flowing paragraph.
  • gotcha Drift: summarizing the summary compounds errors over long chats. Periodically re-derive the summary from the original turns kept in your store.
  • Facts that must outlive the session go to a long-term store, not the window, see memory.

Trade-offs

  • pro: the standard pattern for long sessions, keeps both recency and the old decisions.
  • con: compaction is itself an LLM call, and drift needs a re-derivation schedule.

How it works

  • 1 · Sliding window: keep the last N turns. Simple, loses everything older.
  • 2 · Anchored trim: keep the first turn (the goal) plus the last K. Cheap and surprisingly effective.
  • 3 · Summarize the middle: the hybrid above, the standard rung.
  • 4 · Retrieve-on-demand: embed past turns, fetch the relevant ones per query. History becomes retrieval over itself, see embeddings.
  • Overflow runs the ladder: trim first, then summarize, never silent truncation from the middle of a thought.

Trade-offs

  • pro: mechanical, cheap, predictable, easy to reason about.
  • con: rungs 1 and 2 lose middle detail without notice, rung 4 adds embedding cost.

How it works

  • Attention is uneven: content at the start and end of the window is attended more reliably than the middle. Long windows bury their own facts.
  • Instructions: stable and early. A static prefix at the top also feeds prompt caching, see tokens, cost and caching.
  • Data: late and labeled. Put evidence near the end, clearly marked as data.
  • What deserves the window: recency (last turns verbatim) and relevance (fetch by similarity against the current query). Volume is not safety, selection is.

Trade-offs

  • pro: free, improves quality and cache hits at the same time.
  • con: demands a stable prompt structure, dynamic per-user ordering fights it.

How it works

  • Trigger when history crosses ~70% of the window budget. After the cliff quality has already dropped, waiting for the overflow error is too late.
  • Why headroom: tool results and retrieved docs arrive mid-run, after you sized the prompt. An agent that fills the window before its tools answer truncates the very data it was about to need.
  • The compaction step is an LLM call that merges the oldest turns into the running summary while the last K stay verbatim, code below.

Trade-offs

  • pro: quality stays flat across long threads instead of degrading quietly.
  • con: an extra LLM call per compaction, a small latency spike at the trigger.
When to use · when not

Use when

  • Long working sessions, research agents, copilots, the summary hybrid is the default.
  • Any chat, anchored trim is a quick win, the goal stays and recency stays.
  • Very long histories, retrieve-on-demand fetches only the relevant past turns.
  • Cross-session products, preferences and project facts go to a long-term store, see memory.

Skip when

  • Short-lived FAQ chats, a sliding window is enough machinery.
  • Dense detail in the middle matters, anchored trim deletes it unseen.
  • Very long chats without a re-derivation schedule, drift wins.
  • Short chats, retrieve-on-demand adds embedding cost for nothing.
  • Regulated contexts or anonymous traffic, a long-term store is off the table.
Example

The compaction step that keeps long threads sane. It runs before every LLM call, triggers at 70% of the history budget, merges the oldest turns into the running summary and keeps the last 6 turns verbatim.

BUDGET = 100_000                # history token budget

def maybe_compact(state):            # runs before every LLM call
    msgs = state["messages"]
    if count_tokens(msgs) < BUDGET * 0.7:
        return state                  # plenty of room, nothing to do

    old, recent = msgs[:-6], msgs[-6:]  # last 6 turns stay verbatim
    state["summary"] = llm(
        "Merge into the running summary. Keep every decision,"
        " name, number and open question. Old summary:"
        + state.get("summary", "") + " Turns: " + render(old))
    state["messages"] = recent
    return state
# prompt = system + summary block + recent turns + docs
  • Coding agents assemble exactly this way: instructions early (AGENTS.md-style files), tool output late, old tool results compacted first because they age fastest.
  • Research agents compact at 70% and re-derive the running summary from source turns on a schedule, drift is the difference between "it remembers" and "it confabulates".
  • Copilots keep the last K turns verbatim no matter what, users quote what you said two turns ago and expect it honored.
Watch out
  • Silent truncation · a hard cut mid-thought breaks references the user still holds · overflow must run the ladder
  • Summarizer drift · summary-of-summary compounds errors · re-derive from source turns periodically
  • Stuffing the whole wiki "just in case" · pays input cost to hurt accuracy, context rot charges interest
  • Slice squeeze · tool schemas plus history crowd out docs and the output reserve, the model answers from stale memory
  • Losing the anchor · the first turn states the goal, every trimming strategy must keep it explicitly
  • Counter mismatch · your token counter differs from the provider's tokenizer, count with theirs or leave margin
Remember
  • The window is the world: what is not in it this call does not exist for the model.
  • Budget the window in slices, enforce the caps in code.
  • Compact at ~70%, keep headroom for mid-run tool results and docs.
  • Instructions early and stable, data late and labeled.
  • Keep the last K verbatim, summarize the middle, preserve anchors.
  • Re-derive running summaries from source turns on a schedule.
  • Cross-session facts belong in memory, retrieval slices in RAG, money in tokens and caching.
