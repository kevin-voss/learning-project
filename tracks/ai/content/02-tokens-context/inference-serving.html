Inference & serving

Serving an LLM is a scheduling problem over two very different workloads: a compute-bound prefill and a memory-bandwidth-bound decode that shares GPU memory with a growing KV cache.

In this chapter Explain why prefill and decode bottleneck differently, size a KV cache from a model config, and pick batching, quantization, speculative decoding and parallelism levers against TTFT, inter-token latency and goodput targets.

Why serving mechanics matter

  • Latency is two numbers: users feel time-to-first-token and streaming speed separately; one average hides which phase is slow and which knob fixes it.
  • Memory caps concurrency: on a single GPU, the KV cache, not FLOPs, usually decides how many requests run at once and how long their contexts can be.
  • Self-hosting is capacity planning: GPU count, precision and batch policy set cost per token; a wrong guess means idle GPUs or latency cliffs under load.
  • API users still pull these levers: streaming, batch endpoints, prompt caching and routing map directly onto the mechanisms below; billing details live in tokens, cost, caching.

Serving mechanics

Modern servers schedule at the granularity of one forward pass: every step they assemble a batch of decode tokens plus prefill work, run it, stream tokens out and recycle KV memory from finished requests.

How it works

  • Prefill: all prompt tokens go through each weight matrix as one large matrix-matrix multiply, roughly 2 × params FLOPs per token. Each weight byte loaded is reused across hundreds or thousands of tokens, so high makes it compute-bound.
  • Decode: each step produces one token per sequence, so every weight byte is read to serve only the current batch. At BF16 intensity is about the batch size in FLOPs per byte; an H100 SXM's ridge is near 295 (≈989 dense BF16 TFLOPS ÷ 3.35 TB/s), so small batches sit far below it.
  • KV reads never amortize: weights are shared across the batch, but each sequence reads its own KV cache every step, so long contexts keep decode bandwidth-bound even at large batch.
  • Metrics: TTFT = queueing + prefill. TPOT = (end-to-end − TTFT) ÷ (output tokens − 1), a per-request mean; ITL is each individual token gap. Throughput is total tokens or requests per second; counts only requests that met their SLOs.
  • Percentiles: report p50 and p95 (or p99) per metric under realistic concurrency; end-to-end ≈ TTFT + TPOT × (N − 1).

Trade-offs

  • con: larger batches raise throughput but lengthen every step, so ITL rises; batch size is a throughput-latency dial.
  • con: a long prefill in the same step stalls every running decode; that interference motivates chunked prefill and prefill/decode disaggregation (DistServe).

How it works

  • Formula: KV bytes = 2 (K and V) × layers × kv_heads × head_dim × bytes per element × tokens, summed over every live sequence.
  • matters: Llama 3.1 8B has 32 query heads but 8 KV heads, a 4× smaller cache than full multi-head attention. Always read num_key_value_heads, not num_attention_heads.
  • Linear in tokens: weights are a fixed cost; context length × concurrency is the variable one.
  • Where it lives: the server reserves a fraction of GPU memory (vLLM's gpu_memory_utilization); whatever weights and activations leave becomes the KV pool.

Trade-offs

  • con: setting the maximum model length to the full advertised window does not cost memory up front with paged allocation, but a few long sessions can evict or preempt many short ones.
  • pro: FP8 KV cache halves the per-token cost and roughly doubles concurrent context, at a small, model-dependent quality risk.

How it works

  • Static batching: the batch ends when its longest output finishes; short requests idle as padding, new arrivals wait.
  • Continuous batching: iteration-level scheduling (Orca; TensorRT-LLM calls it in-flight batching) admits and retires requests at every step, the loop in the diagram.
  • : KV lives in fixed-size blocks mapped by a block table, so memory is allocated as tokens arrive, fragmentation is near zero, and blocks can be shared (parallel sampling, beams, common prefixes). The vLLM paper reports 2 to 4× throughput over prior systems at similar latency.
  • Chunked prefill: long prompts are split into chunks that share a step with ongoing decodes under a token budget, so a 30K-token prompt no longer freezes everyone's stream (Sarathi-Serve). vLLM V1 enables it by default where possible; max_num_batched_tokens trades ITL against TTFT.
  • Prefix caching: KV blocks for an identical token prefix (system prompt, tool schemas, few-shot examples) are hashed and reused, skipping that part of prefill. vLLM exposes it as automatic prefix caching; SGLang's RadixAttention keeps a radix tree of prefixes.

Trade-offs

  • con: when the KV pool runs out, the scheduler preempts sequences and must swap or recompute them; p95 latency jumps abruptly rather than degrading smoothly.
  • con: prefix reuse needs byte-identical token prefixes; a timestamp at the top kills every hit, see placement discipline.

How it works

  • Weight-only (W8A16, W4A16): weights are stored at 8 or 4 bits with per-group scales and dequantized inside the matmul. It cuts bytes read per decode step, so it speeds bandwidth-bound decode and frees memory for KV; prefill math stays 16-bit.
  • Weights + activations (W8A8 INT8, FP8): the matmul itself runs on low-precision tensor cores, which also speeds compute-bound prefill. Activation outliers make this harder than weight-only; FP8 needs hardware support (Hopper, Ada and newer on NVIDIA).
  • KV cache (FP8, sometimes INT8/INT4): independent of weight precision; it buys concurrency and context length.
  • GPTQ: one-shot, layer by layer, uses approximate second-order information from a small calibration set and updates not-yet-quantized weights to absorb each rounding error.
  • AWQ: uses activation statistics to find the small fraction of salient weight channels and rescales them before quantizing so they lose less precision; no backpropagation.

Trade-offs

  • con: INT4 usually loses little on broad benchmarks yet can regress math, code, long-context and low-resource languages. Evaluate on your own eval set, not the model card.
  • con: calibration data unlike production traffic protects the wrong channels.

How it works

  • Draft: a small model with the same tokenizer proposes k tokens autoregressively. Self-speculative variants skip the separate model: extra prediction heads (Medusa, EAGLE), skipped layers, or n-gram lookup in the prompt.
  • Verify: the target scores all k positions in one forward pass. Because decode is bandwidth-bound, checking k + 1 positions costs about as much as generating one.
  • Exactness: draft token x is accepted with probability min(1, p(x) ÷ q(x)); on rejection the target resamples from the normalized residual max(0, p − q). This rejection-sampling step makes the output distribution identical to sampling the target alone; greedy mode simply accepts while tokens match the target argmax.
  • Payoff: with per-token α, expected tokens per target pass is (1 − αk+1) ÷ (1 − α); α = 0.8 and k = 4 gives about 3.4, before subtracting draft cost.

Trade-offs

  • con: at large batch the target is closer to compute-bound, so verifying rejected tokens wastes real FLOPs; gains shrink or turn negative under heavy load.
  • con: acceptance drops when traffic drifts from the draft's training data, and the draft adds its own weights and KV cache.

How it works

  • Tensor parallel: each layer's matrices are sharded across GPUs with all-reduces inside every layer. It cuts per-GPU memory (weights and KV heads) and per-token latency but needs NVLink-class links, so it stays within a node.
  • Pipeline parallel: contiguous layer groups live on different GPUs or nodes; micro-batches hide pipeline bubbles. It scales capacity across nodes but does not shorten a single request.
  • Expert parallel: in MoE models, experts are spread across GPUs and tokens travel via all-to-all dispatch and combine; load imbalance across experts becomes the bottleneck.
  • Data parallel: independent replicas behind a load balancer; the default throughput lever.
  • API levers: streaming cuts perceived latency to TTFT without changing total time; batch APIs trade hours of turnaround for price; prompt caching skips repeated prefill; a gateway routes easy requests to small models and handles fallback, rate limits and per-tenant metering. Decision boundary

Use when (self-host and tune)

  • Steady, high volume keeps GPUs busy; utilization is what makes self-hosted cost per token competitive.
  • Data residency, air-gapped or on-prem requirements rule out a hosted API.
  • An open-weight or fine-tuned model is good enough, and you need control over TTFT and ITL SLOs.
  • Workloads share long prefixes (agents, RAG templates) that prefix caching exploits.

Skip when

  • Traffic is spiky or low; idle reserved GPUs cost more than per-token pricing.
  • You need a frontier closed model; tune the API-side levers instead.
  • No one owns GPU operations, upgrades and on-call; see LLM ops.
  • Latency is dominated by retrieval or tool calls, not generation; profile first, see system architecture.

Worked example

Example capacity plan: serve Llama 3.1 8B (32 layers, 8 KV heads, head_dim 128, 8.03B parameters, per its published config) on one 80 GB H100 SXM for a support assistant with conversations up to 8K tokens. All figures are estimates from the formula, not benchmarks.

GIB = 2 ** 30
# Llama 3.1 8B config.json: 32 layers, 8 KV heads (GQA), head_dim 128
LAYERS, KV_HEADS, HEAD_DIM, PARAMS = 32, 8, 128, 8.03e9

def kv_bytes_per_token(kv_bytes):
    return 2 * LAYERS * KV_HEADS * HEAD_DIM * kv_bytes  # 2 = K and V

def max_sequences(weight_bytes, kv_bytes, seq_tokens=8192,
                  gpu_gib=80, util=0.9, overhead_gib=4):
    # overhead_gib: activations, CUDA graphs, allocator slack (assumed)
    weights_gib = PARAMS * weight_bytes / GIB
    pool_gib = gpu_gib * util - weights_gib - overhead_gib
    per_seq_gib = kv_bytes_per_token(kv_bytes) * seq_tokens / GIB
    return weights_gib, pool_gib, int(pool_gib // per_seq_gib)

print(kv_bytes_per_token(2) / 1024, "KiB per token")  # 128.0
for label, w, kv in [("bf16 weights, bf16 KV", 2, 2),
                     ("fp8 weights,  fp8 KV ", 1, 1),
                     ("int4 weights, fp8 KV ", 0.5, 1)]:
    wg, pool, n = max_sequences(w, kv)
    print(f"{label}: weights {wg:4.1f} GiB, KV pool {pool:4.1f} GiB, "
          f"{n} full 8K conversations")
# bf16 weights, bf16 KV: weights 15.0 GiB, KV pool 53.0 GiB, 53 full 8K conversations
# fp8 weights,  fp8 KV : weights  7.5 GiB, KV pool 60.5 GiB, 121 full 8K conversations
# int4 weights, fp8 KV : weights  3.7 GiB, KV pool 64.3 GiB, 128 full 8K conversations

A worst case: paged allocation spends memory only on tokens that exist, so shorter conversations admit more. FP8 to INT4 weights adds few slots; halving KV precision doubled them. Whether that batch meets a p95 ITL target is a measurement, not a formula.

Failure modes

  • Benchmarking one request at a time · it measures the batch-1 floor, not production · load-test at target concurrency and report p50 and p95 TTFT and ITL
  • Synthetic fixed-length prompts · real input and output length distributions change prefill share, KV pressure and preemption · replay sampled production traffic
  • KV pool exhaustion · preemption and recompute make p95 jump in a cliff · cap max model length per tenant, alert on preemptions and queue depth
  • Quantized model passes generic benchmarks and regresses your domain · gate every precision change on task evals
  • Speculative decoding enabled globally · it helps at low load and can hurt at high load or under drift · track acceptance rate and toggle per traffic tier
  • Prefix cache hit rate near zero · volatile tokens (timestamps, request IDs, reordered tools) sit before the stable prefix · move them to the end

Keep in mind

  • Prefill is compute-bound and sets TTFT; decode is bandwidth-bound and sets ITL.
  • KV bytes = 2 × layers × kv_heads × head_dim × bytes × tokens; read kv_heads from the config.
  • Continuous batching plus paged KV is the baseline; chunked prefill and prefix caching protect latency.
  • Quantize weights for bandwidth, activations for compute, KV for concurrency, then eval.
  • Speculative decoding is exact, and it pays most when the GPU is underused.
  • Optimize goodput at p95 against an SLO, not mean throughput.
