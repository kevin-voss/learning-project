Reasoning models & test-time compute

Reasoning models are trained to spend output tokens thinking before they answer, which turns inference compute into a dial: more tokens or more samples buy accuracy on hard problems at a price in latency and cost.

In this chapter Explain how RL on verifiable rewards produces long reasoning, compare serial and parallel test-time scaling, configure effort, budgets and interleaved thinking through vendor APIs, and decide when the extra compute pays for itself.

Why this layer matters

  • A new cost axis: the same prompt can cost a few hundred or tens of thousands of output tokens depending on one effort setting, and the hidden part still bills at the output rate, see tokens, cost, caching.
  • Accuracy you can buy: on math, code and multi-step planning, extra inference compute can beat a bigger model; on simple extraction it only adds latency.
  • Different integration contract: reasoning state must be round-tripped across tool calls, output caps now include invisible tokens, and some sampling knobs are fixed or unsupported.
  • Prompting habits invert: step-by-step scaffolding that helped chat models often adds nothing; clear goals and success criteria do the work.

Mechanism

Test-time compute is spent in two directions: serially, as one longer reasoning chain, and in parallel, as many candidates filtered by a vote or a verifier. Reasoning models internalize the serial axis; your application can add the parallel one.

How it works

  • : the model samples a chain plus answer, a checker scores only the outcome (tests pass, number matches), and the policy is updated toward high-reward samples. Details in training and alignment.
  • Emergent length: DeepSeek-R1-Zero, trained with RL from a base model without an SFT stage, grew its responses over training and began re-checking and backtracking on its own; nobody wrote those behaviors as rules.
  • Cold start and polish: production recipes add curated long-chain SFT data before RL and preference tuning after it, fixing readability and language mixing that pure RL leaves behind.
  • Same architecture: a reasoning model is still a decoder predicting tokens; the difference is a learned policy for spending before the answer.

Trade-offs

  • pro: strongest where answers are checkable, because that is where the reward signal was dense: math, code, logic, structured planning.
  • con: outcome-only reward does not grade the chain itself, so the chain is optimized for usefulness, not for being an honest transcript.

How it works

  • Longer chains: raise effort or budget; one sequential pass, latency grows with every reasoning token because decode is serial.
  • : sample N chains, extract each final answer, return the mode. No extra model, but only works when answers are comparable (numbers, labels, test outcomes).
  • Best-of-N with a verifier: score candidates with an outcome reward model, a , or a real checker such as a test suite; return the top one. A program-based verifier beats a learned one when you have it.
  • Tree search: expand partial solutions step by step and prune with a PRM (beam search, lookahead). Spends compute where the verifier is uncertain instead of on full rollouts.
>4×compute efficiency over best-of-N when test-time compute is allocated per prompt by difficulty (Snell et al., 2024)
14×larger model outperformed at matched FLOPs, only on prompts where the small model already had non-trivial success (same study)

Trade-offs

  • con: returns diminish and vary by difficulty: easy prompts saturate fast, the hardest ones barely move, and there more pretraining compute wins.
  • con: parallel methods multiply cost by N and inherit verifier errors; a reward model can be gamed by confident wrong answers.

How it works

  • Depth control: vendors converged on discrete effort levels; supported values and defaults vary per model. OpenAI: reasoning.effort. Anthropic: adaptive thinking plus output_config.effort, which replaces the older budget_tokens on newer models. Gemini: thinking_level. Adaptive modes may skip thinking on easy inputs.
  • Visibility: raw chains are not returned. You get nothing or an opt-in summary written by a separate summarizer (OpenAI reasoning.summary, Anthropic display: "summarized", Gemini thought summaries).
  • Billing: all three bill the full reasoning, not the summary, at the output rate, and report it separately in usage (for example output_tokens_details.reasoning_tokens).
  • Caps: the output limit covers reasoning plus answer. Hit it mid-thought and the response is incomplete, possibly with no visible text, and still billed.

How it works

  • Within one turn: the model reasons between tool calls instead of only up front, so it can react to a failing test or an empty search before committing to the next action. See tool calling.
  • Opaque state: reasoning comes back as an . In stateless mode you resend it unchanged with the tool output; server-side conversation state does this for you.
  • Vendor shape: OpenAI asks for all reasoning, call and output items since the last user message; Anthropic needs thinking blocks with signatures; Gemini needs thought signatures resent.

Trade-offs

  • pro: fewer wasted tool calls and better recovery in long agent loops.
  • con: dropping or editing the blob breaks continuity or errors out; middleware that "cleans" message history is a common culprit.

How it works

  • Goal, constraints, format: what to produce, what it must not violate, and the exact output shape. Vendor guides for reasoning models emphasize this over prescribed intermediate steps.
  • Define done: for agentic work, state how the model should verify (run the tests, re-derive the total, cite the clause). It plans against that criterion.
  • Drop scaffolding: "think step by step" or hand-written chains duplicate what training already does and can constrain a better plan.
  • Answer anchor: ask for a fixed final line (for example ANSWER: …) when you vote, parse or grade. General patterns are in prompting.

Trade-offs

  • con: vague goals plus high effort yield long, expensive exploration of the wrong problem; effort is a tuning knob, not a substitute for a clear task.

How it works

  • Sweep effort: run your eval set at each level, log accuracy, p50/p95 latency and output tokens; pick the knee of the curve, not the top.
  • Metric: cost per correct answer, not cost per call. A cheaper level that needs retries can cost more.
  • Hard caps: set the output limit with room for reasoning (OpenAI suggests reserving at least 25,000 tokens while experimenting), alert on incomplete responses.
  • Routing: classify requests and send extraction and lookups to a non-reasoning model or minimal effort; reserve high effort for the hard tail.

Trade-offs

  • con: a router adds a misclassification path; log routed-low failures and feed them back into the eval set.

Faithfulness caveat: visible reasoning is not guaranteed to reflect the computation that produced the answer. Chen et al. (2025) planted hints in prompts; models that used a hint mentioned it in their chain often less than 20% of the time, and outcome-based RL improved this only up to a plateau. Treat chains and summaries as debugging aids, never as an audit trail.

Decision boundary

Use when

  • Correctness depends on multi-step derivation: math, proofs, algorithm design, tricky debugging.
  • Code with a checker: tests or compilers let you add best-of-N on top of the model's own reasoning.
  • Agentic tool loops where the model must judge each result and replan, with interleaved thinking enabled.
  • Planning under many constraints: scheduling, migrations, multi-document reconciliation.
  • A wrong answer costs far more than seconds of latency and extra output tokens.

Skip when

  • Latency is the product: autocomplete, voice turns, interactive UI under a second.
  • Simple extraction, classification or rewriting, where a chat model at a fraction of the tokens is as accurate.
  • Overthinking risk: trivial prompts trigger long chains that add cost and latency with no accuracy gain.
  • Very high volume with a fixed pattern; route to a small model or rules.
  • You need the reasoning itself as evidence; it is hidden, summarized and not guaranteed faithful.

Worked example

A finance-ops assistant gets two request types: pulling fields from an invoice (easy) and reconciling a ledger against bank lines (hard, one numeric answer). Easy requests go to low effort; hard ones get five medium-effort chains and a majority vote, escalating when no answer wins three votes. Hypothetical budget: if a hard chain uses about 4,000 output tokens, one vote costs about 20,000, so the vote is worth it only when the eval shows it lifts accuracy enough to beat a single high-effort call on cost per correct answer. Shown with the OpenAI Responses API; effort values vary by model.

import os
from collections import Counter
from openai import OpenAI

client = OpenAI()
MODEL = os.environ["REASONING_MODEL"]  # any model that accepts reasoning.effort

def ask(prompt, effort, cap=25_000):
    r = client.responses.create(
        model=MODEL, input=prompt,
        reasoning={"effort": effort},
        max_output_tokens=cap)  # caps reasoning + visible answer together
    if r.status == "incomplete":
        raise RuntimeError(f"cap hit: {r.incomplete_details.reason}")
    hidden = r.usage.output_tokens_details.reasoning_tokens
    print(f"{effort}: {hidden} reasoning / {r.usage.output_tokens} output tokens")
    return r.output_text.strip()

def final(text):
    return text.rsplit("ANSWER:", 1)[-1].strip()

def solve(task, hard):
    if not hard:  # route: extraction never needs a vote
        return ask(task, "low")
    prompt = task + "\nVerify the totals. End with one line: ANSWER: <amount>"
    votes = Counter(final(ask(prompt, "medium")) for _ in range(5))
    best, n = votes.most_common(1)[0]
    return best if n >= 3 else None  # None: escalate to high effort or a human

Failure modes

  • Output cap too tight · the model spends it all thinking, returns incomplete with no answer, and you still pay · reserve headroom and alert on it
  • Reasoning blob dropped between tool calls · continuity breaks or the API rejects the turn · pass reasoning items and signatures back byte-for-byte
  • Treating the summary as the reasoning · it is written by a separate summarizer from hidden tokens and may omit what drove the answer · do not use it for compliance evidence
  • Overthinking simple prompts · long chains on trivial inputs burn tokens and latency · route easy traffic to minimal effort or a chat model
  • Voting without a canonical answer format · "1,200", "$1200" and "1200.00" split the vote · normalize before counting
  • Cost dashboards that count visible text · reasoning tokens and re-sent prior reasoning dominate the bill · read usage fields, not string length

Keep in mind

  • Reasoning models are decoders trained with RL on checkable outcomes to think before answering.
  • Test-time compute scales serially (longer chains) and in parallel (votes, verifiers, search).
  • Gains depend on difficulty: big on mid-hard checkable tasks, small on trivial or out-of-reach ones.
  • Hidden reasoning bills as output, counts against the cap and must be round-tripped in tool loops.
  • Prompt with goals and success criteria; effort is a tuning knob, not a fix for a vague task.
  • Optimize cost per correct answer, and never treat the visible chain as a faithful trace.
