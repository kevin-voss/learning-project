Tokens, cost and caching

Every request is metered twice: tokens you send in and tokens the model writes out. Cost control is four stacked levers: send less, cache what repeats, batch what can wait, cap the output.

In this chapter Estimate token-driven spend with explicit assumptions and distinguish request KV state from reusable prefix and semantic caches.

Why this layer matters

  • Bills explode on two meters: tokens in (your prompt) and tokens out (the answer), both multiplied by volume. Output rates are usually higher; the ratio varies by model, provider and date.
  • Why the asymmetry: input is , one parallel pass over the whole prompt. Output is decode, one serial pass per token attending over everything so far via the . Provider rates reflect that serving economics, not a direct FLOP count.
  • One formula: cost = tokens_in × rate_in + tokens_out × rate_out, token charges only, before discounts, cache effects, other fees and infrastructure. Long agent loops multiply both meters per step.
  • Tokenization sets the bill: English text averages several characters per token. Tokenizers differ, and code, JSON and non-English text often need more tokens, so the same content costs differently by format.
  • Hidden spend everywhere: system prompts, tool schemas, retrieved docs, history. A stable system prompt still bills input tokens on every request; count the real tokens and apply any cache policy.
  • The window is billed, not free: a large context window still meters every token sent, see how LLMs actually work.
  • Repeat traffic pays full price unless cached: same system prompt, same FAQs, near-identical questions, re-billed every call.
  • Toy rates: the worked example uses $2.50 per million input and $10 per million output tokens. Real prices, cached-input discounts and batch rates vary by provider and date; use the active rate card.

Cost model

Four levers that stack: cache the prefix, replay the repeats, batch the patient, cap the output.

How it works

  • reuses provider-side KV state for identical prefixes, often at a discounted cached-input rate.
  • Prefix matching only: the cache hits only while the first N tokens are identical; reuse stops at the first divergence.
  • Order is everything: static content first (system prompt, tool schemas, few-shots), dynamic last (timestamps, per-user data, the query). One shared prefix, user deltas appended.
  • Provider-specific rules: minimum prefix length, cache granularity, lifetime, explicit controls and cached-token rates differ by API, model and date. Treat them as versioned configuration and check the rate card before estimating savings.
  • What invalidates: timestamps or request ids at the top, system prompt churn from A/B tests or per-user variants, tool schema re-ordering, version bumps.

Trade-offs

  • pro: eligible prefix reuse cuts repeated prefill work, and often cached-input charges and latency.
  • con: demands stable-prefix discipline; hit-rate loss from prefix churn is silent, so track hit rate next to cost per request.

How it works

  • Exact layer first: identical request, replay the stored answer. Cheapest check; only for deterministic, cacheable outputs.
  • Semantic layer second: the question; if a stored one is closer than a threshold (cosine ~0.95+), replay its answer in milliseconds, see embeddings.
  • Where it pays: support and doc traffic repeats heavily; realistic hit rates are 20 to 40%.
  • TTL everything: prices, policies and docs age; a cached answer that outlives its source is confident misinformation.
  • gotcha Near-duplicate is not identical: "refund for order 123" must not replay "refund for order 456". Keep personalization out of cached answers; bypass the cache for anything transactional.

Trade-offs

  • pro: a hit skips the model entirely, the only free lunch here.
  • con: a loose threshold replays answers to different questions; tune it and add a TTL.

How it works

  • Trade: batch APIs swap latency for lower rates; delivery windows and discounts are provider-specific.
  • Perfect fits: eval suites, embedding backfills, classification, archive summaries: anything nobody waits on.
  • Retry path: handle failed items, and occasionally whole failed jobs.

Trade-offs

  • pro: lower rates for workloads with flexible completion time.
  • con: completion time is bounded only by provider terms; unfit for interactive paths.

How it works

  • Reasoning tokens are output: thinking chains, tool-call arguments and JSON scaffolding bill at the output rate before the user sees a word.
  • Set max_tokens on every call. At the toy rates, 4k in and 500 out still spends a third of its cost on output: the 4x premium at work.
  • Budget output before input. The classic FinOps horror: an uncapped agent loop thinking out loud for 20k tokens per answer, see durable ops.
  • Sibling lever, model downgrade: route easy tasks to a small model. Cheap models get expensive when they fail twice; back routing with evals.

Trade-offs

  • pro: caps the worst tail, free to implement.
  • con: answers cut mid-sentence read as bugs; tune the cap per task.

Decision boundary

Use when

  • Any stable prefix exists (system prompt, tool schemas, few-shots), turn prompt caching on.
  • Traffic repeats (FAQs, doc search, support), add the response caches.
  • Nobody waits on the answer (evals, backfills, classification), send it to batch.
  • Always: cap output with max_tokens, it is the pricier meter.
  • Easy tasks at volume, route them to a small model with evals behind it.

Skip when

  • Prefixes are per-user and built dynamically, they break the prefix match.
  • Answers are personalized, transactional or time-sensitive, never replay them from a cache.
  • Anything interactive or dependent on immediate completion.
  • Quality-critical calls lack the evals to back a model downgrade.
  • Cache hit rate is unmeasured, you cannot tune what you do not track.

Worked example

Toy budget: 50,000 requests/day, each 4,000 input tokens (1,200 eligible cached-prefix + 2,800 uncached) and 500 output tokens, at $2.50 per million input and $10 per million output. Cached prefix input costs 10% of the normal rate (90% discount). Not provider quotes; substitute your rate card.

INPUT_RATE = 2.50   # toy dollars per million input tokens
OUTPUT_RATE = 10.00  # toy dollars per million output tokens
CACHED_PREFIX_RATE = INPUT_RATE * 0.10  # toy 90% discount on cached prefix only
REQUESTS_PER_DAY = 50_000
UNCACHED_INPUT, CACHED_PREFIX, OUTPUT = 2_800, 1_200, 500
PER_MILLION = 1_000_000

def model_cost_per_request(cached_prefix_tokens):
    input_cost = (UNCACHED_INPUT * INPUT_RATE + cached_prefix_tokens * CACHED_PREFIX_RATE)
    output_cost = OUTPUT * OUTPUT_RATE
    return (input_cost + output_cost) / PER_MILLION

baseline = (UNCACHED_INPUT + CACHED_PREFIX) * INPUT_RATE / PER_MILLION
baseline += OUTPUT * OUTPUT_RATE / PER_MILLION
prefix_cached = model_cost_per_request(CACHED_PREFIX)
print(baseline)       # $0.015 per request · $750/day
print(prefix_cached)   # $0.0123 per request · $615/day
print(prefix_cached * REQUESTS_PER_DAY * 0.70)  # $430.50/day after 30% response-cache hits
  • Baseline: input is 50k × (4,000 / 1M) × $2.50 = $500/day; output is 50k × (500 / 1M) × $10 = $250/day. Total: $750/day.
  • Cached-prefix case: each request has 2,800 × $2.50 + 1,200 × ($2.50 × 0.10) + 500 × $10 = $12,300 per million requests, or $0.0123/request and $615/day.
  • Response-cache case: if 30% of requests are valid response-cache hits that skip the model, 70% × $615 = $430.50/day in model charges, before cache, embedding and infrastructure costs. Check validity, tenant, ACL and model-version boundaries before replaying.

Failure modes

  • The timestamp at the top · the most common cache killer · "Current time: ..." before the system prompt re-randomizes the prefix on every call
  • System prompt churn · A/B tests, version banners, per-user variations quietly zero the hit rate
  • Loose semantic thresholds · cosine 0.90 on short questions replays answers to different questions
  • Tool sprawl · every added tool rides its schema on every request, see tool calling · fewer tools is a permanent discount
  • Prefix-splitting refactors · per-user prompts and dynamic ordering can double the bill with no error raised anywhere
  • Unbounded output · agent loops with no max_tokens burn the pricier meter, often 3-5x input

Keep in mind

  • Write the formula down: tokens_in × rate_in + tokens_out × rate_out, token charges only.
  • Order every prompt static-first, dynamic-last.
  • Track cache hit rate as a first-class metric next to cost per request.
  • A cache hit is the only free lunch: discounted input or a skipped model call.
  • Set max_tokens on every call, budget output before input.
  • Send evals and backfills to the batch API.
  • Budget the window itself, see context budgeting.
