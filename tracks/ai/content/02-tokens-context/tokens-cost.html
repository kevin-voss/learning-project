Tokens, cost and caching

Every request is metered twice: once for the tokens you send in, once for the tokens the model writes out. Cost control is four levers stacked, send less, cache what repeats, batch what can wait, cap the output.

Why you need it
  • Bills explode on two meters: tokens in (your prompt) and tokens out (the answer), and volume multiplies both. Output runs 3 to 5x pricier per token than input.
  • Why the asymmetry: input is , one parallel pass over the whole prompt. Output is decode, one serial pass per token attending over everything so far via the . Serial compute, priced accordingly.
  • One formula: cost = tokens_in × rate_in + tokens_out × rate_out. Nothing else enters it. Long agent loops multiply both meters per step.
  • Tokenization sets the bill: roughly 4 characters of English per token. Code, JSON and non-English text tokenize denser, so the same visible text costs differently by format.
  • Hidden spend everywhere: system prompts, tool schemas, retrieved docs, history. The 1k-token system prompt nobody touches is a permanent tax on every request.
  • The window is billed, not free. A 200k context window still pays for every token sent, see how LLMs actually work.
  • Repeat traffic pays full price unless you cache it: same system prompt, same FAQs, near-identical questions, re-billed on every call.
  • Ballparks, per 1M tokens: small fast tier $0.15 to $0.60 in, flagship tier $2 to $5 in, output 3 to 5x that, cached input 50 to 90% off, batch ~50% off both meters. Numbers drift quarterly, price from the provider's current page, never from memory.
Solutions

Four levers that stack: cache the prefix, replay the repeats, batch the patient, cap the output.

How it works

  • reuses the provider-side KV cache for identical prefixes: cached input bills at 50 to 90% off and prefill latency mostly disappears.
  • Prefix matching only: the cache hits when the first N tokens are identical. One changed character at position 10 invalidates everything after it.
  • Order is everything: static content first (system prompt, tool schemas, few-shots), dynamic last (timestamps, per-user data, the query). Build one shared prefix, append user deltas.
  • OpenAI: automatic for prompts over 1,024 tokens, roughly 50% off cached tokens, no code changes, still needs a stable prefix. Anthropic: explicit cache_control, writes ~1.25x once, reads ~0.1x, so a single reuse already wins. TTL 5 minutes, or 1 hour at 2x write cost.
  • What invalidates: timestamps or request ids at the top, system prompt churn from A/B tests or per-user variations, tool schema re-ordering and version bumps.

Trade-offs

  • pro: the cheapest lever, cuts latency as well as cost, works on existing traffic.
  • con: demands stable-prefix discipline, and hit-rate loss when the prefix churns is silent, track cache hit rate next to cost per request.

How it works

  • Exact layer first: identical request, replay the stored answer. Cheapest to check, only for deterministic, cacheable outputs.
  • Semantic layer second: the incoming question, and if a stored one sits closer than a threshold (cosine ~0.95+), replay its answer. Millisecond latency, see embeddings.
  • Where it pays: support and doc traffic repeats heavily, realistic hit rates are 20 to 40%.
  • TTL everything: prices, policies and docs age. A cached answer that outlives its source becomes confident misinformation.
  • gotcha Near-duplicate is not identical: "refund for order 123" must not replay "refund for order 456". Keep personalization out of cached answers and bypass the cache for anything transactional.

Trade-offs

  • pro: a hit skips the model entirely, the only free lunch in this business.
  • con: a loose threshold replays answers to different questions, tune it and add a TTL.

How it works

  • ~50% off for patience: batch endpoints queue the work and deliver within ~24h, half price on both meters.
  • Perfect fits: eval suites, embedding backfills, classification, summarizing archives. Anything where nobody waits on the answer.
  • Retry path: failed batch items need handling, whole batch jobs fail sometimes.

Trade-offs

  • pro: half price with zero cleverness, ideal for nightly work while nobody is awake to read it.
  • con: never interactive. A 24h window on a chat reply is an outage, not a discount.

How it works

  • Reasoning tokens are output: thinking chains, tool-call arguments and JSON scaffolding all bill at the output rate before the user sees a word.
  • Set max_tokens on every call. A request with 4k in and 500 out can still spend a third of its cost on output, that is the 4x premium at work.
  • Budget output before input. The horror story every FinOps person knows: an agent loop thinking out loud for 20k tokens per answer with no cap, see durable ops.
  • Sibling lever, model downgrade: route easy tasks to a small model. Cheap models are expensive when they fail twice, back the routing with evals.

Trade-offs

  • pro: caps the worst tail, free to implement.
  • con: answers cut mid-sentence read as bugs, tune the cap per task.
When to use · when not

Use when

  • Any stable prefix exists (system prompt, tool schemas, few-shots), turn prompt caching on.
  • Traffic repeats (FAQs, doc search, support), add the response caches.
  • Nobody waits on the answer (evals, backfills, classification), send it to batch.
  • Always: cap output with max_tokens, it is the pricier meter.
  • Easy tasks at volume, route them to a small model with evals behind it.

Skip when

  • Prefixes are per-user and built dynamically, they break the prefix match.
  • Answers are personalized, transactional or time-sensitive, never replay them from a cache.
  • Anything interactive, a 24h batch window is an outage.
  • Quality-critical calls lack the evals to back a model downgrade.
  • Cache hit rate is unmeasured, you cannot tune what you do not track.
Example

A support chatbot priced end to end. 50,000 requests/day, each 4,000 tokens in (system 800 + tool schemas 400 + history 1,500 + retrieved docs 1,200 + query 100) and 500 tokens out, at $2.50 per 1M in and $10.00 per 1M out. The estimator wires the cache lever in.

IN, OUT = 2.50, 10.00   # $ per 1M tokens, flagship class

def cost(tin, ans, cached=False):
    if cached:            # prompt cache hit, input at ~10%
        return tin * IN * 0.1 + ans * OUT
    return tin * IN + ans * OUT

req = 800 + 400 + 1500 + 1200 + 100  # sys + tools + history + docs + query
print(cost(req, 500))               # ~$0.015 per request
print(cost(req, 500, cached=True))   # ~$0.006 with a cache hit
  • Input: 50k × 4,000 = 200M tokens/day × $2.50 = $500/day.
  • Output: 50k × 500 = 25M tokens/day × $10.00 = $250/day.
  • Total: $750/day, about $22,500/month. Output was only 11% of the tokens but 33% of the cost.
  • Now the levers: prompt-cache the 1,200-token static prefix at ~90% off, replay 30% of FAQ traffic semantically, run the nightly suite on batch. Same traffic lands near $400/day, same product, half the bill.
Watch out
  • The timestamp at the top · the most common cache killer · "Current time: ..." before the system prompt re-randomizes the prefix on every call
  • System prompt churn · A/B tests, version banners, per-user variations quietly zero the hit rate
  • Loose semantic thresholds · cosine 0.90 on short questions replays answers to different questions
  • Tool sprawl · every added tool rides its schema on every request, see tool calling · fewer tools is a permanent discount
  • Prefix-splitting refactors · per-user prompts and dynamic ordering can double the bill with no error raised anywhere
  • Unbounded output · agent loops with no max_tokens burn the 3-to-5x meter
Remember
  • Write the formula down: tokens_in × rate_in + tokens_out × rate_out. Nothing else enters it.
  • Order every prompt static-first, dynamic-last.
  • Track cache hit rate as a first-class metric next to cost per request.
  • A cache hit is the only free lunch: discounted input or a skipped model call.
  • Set max_tokens on every call, budget output before input.
  • Send evals and backfills to the batch API.
  • Budget the window itself, see context budgeting.
