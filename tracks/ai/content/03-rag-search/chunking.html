Chunking

Chunking picks the addressable unit of retrieval. The chunk you embed is the chunk you get back, so where you cut decides what search can find and what context the model sees.

In this chapter Choose boundaries that preserve meaning and provenance, then measure retrieval quality rather than tuning overlap by intuition.

Why this layer matters

  • Hard input limit: embedding models cap at 512 to 8,192 tokens (see embeddings), and most truncate oversized input silently. Your conclusions on page 40 stop existing.
  • One vector is averaged meaning: embed an 80-page manual and pricing, safety, install and legal blend into one point that nothing matches well.
  • Granularity is what you get back: one giant chunk means paying for 79 irrelevant pages around the paragraph the model needed.
  • Too small bites the other way: fragments lose antecedents ("it" points nowhere) and one thought spans many pieces.
  • The dial: addressable precision vs surviving context. Chunking picks a point on it.

Chunking mechanics

Five ways to cut. Pick one per corpus, then apply the shared sizing, overlap and metadata rules.

How it works

  • Cut every N tokens, ignoring content. Deterministic, predictable sizes, trivially simple.
  • Cuts mid-sentence by design, so pair it with overlap.

Trade-offs

  • pro: the dumbest cut in the room, and exactly right for logs and homogeneous streams with no structure.
  • con: shreds prose, orphans ideas and antecedents.

How it works

  • Split at the biggest boundary that fits the size cap: paragraphs, then lines, then sentences, then words.
  • Structure-aware without needing structure. The sane default for docs, wikis and knowledge bases.
  • Respect headings where they exist; 400 to 800 tokens with 10 to 15% overlap (sizing below).

Trade-offs

  • pro: one configuration covers most corpora.
  • con: size and overlap are knobs that still need retrieval evals to tune honestly.

How it works

  • Cut where structure already breaks: headings, sections, list items. One subsection = one chunk.
  • Markdown from the parser makes heading-aware cuts easy; the section path rides along as metadata for provenance.

Trade-offs

  • pro: ideas survive whole, citations come from the section path.
  • con: sections vary wildly in size: cap the big ones, fall back to recursive inside them.
  • con: flat text with no markup gains nothing over recursive.

How it works

  • Embed consecutive sentences, cut where neighbor similarity dips. The dip IS the topic change.
  • Fits topic-hopping prose and support transcripts.

Trade-offs

  • pro: boundaries land on meaning, not character counts, so each chunk is one idea by construction.
  • con: an extra embedding pass at ingest.

How it works

  • Prepend a short LLM-written context line ("from the Q3 pricing section") to each chunk before embedding.
  • The line carries provenance when a chunk matches alone; large recall gains are reported.

Trade-offs

  • pro: worth it in legal, medical, compliance, anywhere a miss costs money or health.
  • con: one LLM call per chunk at ingest. Cache the lines, they are stable for unchanged text, or the re-index bill bites twice.

Beyond the five

  • Sentence-window: embed single sentences, return each hit with its neighbors. Match at sentence precision, answer with the paragraph.
  • Parent / small-to-big: embed small for sharp vectors, paste the parent block for context.
  • Late chunking: run a long-context embedder over the whole document once, then pool token ranges into chunks. Whole-doc context at zero per-chunk LLM cost.

Sizing · why a max exists at all

  • architecture BERT-style encoders have exactly 512 positional embeddings. Token 513 has no position, the model cannot attend to it.
  • training embedders are contrastively trained on passages of a few hundred tokens (MS MARCO question-answer pairs). A 6,000-token chunk is out of distribution even when the API accepts it.
  • mean pooling the output vector averages all token vectors (see embeddings), so each extra token dilutes the rest and precision falls long before the hard limit.
  • silent truncation most APIs drop the tail of oversized input without an error. Chunk to the recommended size, never the maximum.

The 400 to 800 default: it sits inside every mainstream embedder's recommended range and keeps roughly one idea per chunk. Leave it until retrieval evals say otherwise. Deviate on purpose: dense reference docs with one fact per line go smaller, section-locked corpora like legal go structure-first and let sections set their size.

Overlap · 10 to 15 percent

  • What it protects: the sentence severed at the boundary. With bleed it lives in two chunks and either can match.
  • Where it matters: fixed-size and recursive cuts, which can land mid-thought. Heading and section cuts need less.
  • Too much overlap: near-duplicate chunks crowd top-k and multiply storage. 10 to 15% is a common band; confirm it with evals.

Metadata travels with every chunk

  • Source: document id, title, URL. No source, no citation.
  • Section path: handbook > refunds > policy. Restores the context a cut removes and powers breadcrumb citations.
  • Date and version: retrieve the current policy, not the 2022 one that embeds identically.
  • ACL / tenant: filter access in retrieval, before the model sees a token. Tenancy that lives only in the prompt is a leak.
  • Page number: the cheapest debugging hook you will ship, and it links answers to source pages.
  • filtering beats bigger chunks a metadata pre-filter narrows candidates before similarity runs, so chunks stay small and sharp. Growing chunks to smuggle context in dilutes them (see search and filtering).

The chain to answer quality, and re-chunking cost

  • The chain: boundaries decide what is addressable, retrieval returns only addressable units, the model cites only what retrieval returned. Chunking caps every later stage.
  • A strategy change re-embeds everything: new size, overlap or method means re-chunk, re-embed and re-index the whole corpus.
  • Consequence: fix parsing and strategy before scale (see ingestion), and prove each change with retrieval evals so every migration buys real recall.

Decision boundary

Use when

  • Documents exceed the embedder's input cap.
  • Search must return precise passages, not metered walls of context.
  • Citations must link answers to a source page or section.
  • Tenant, date or section filters must narrow candidates before similarity runs.

Skip when

  • Whole documents fit the embedder's recommended window.
  • A one-shot paste into a long context answers the demo fine.
  • Retrieval quality is not measured yet (see evals): every knob becomes vibes-tuning.

Worked example

The default cut in practice, then the splitter: recursive character splitting at 800 characters with 15% overlap, biggest boundary first.

docs site · recursive

  • Recursive 400 to 800 tokens, overlap 10 to 15%, headings respected.
  • Most docs sites run exactly this and sleep fine.

legal and medical · contextual

  • An LLM context line per chunk, because misses cost money or health.
  • Lines cached across re-indexes.

support transcripts · semantic

  • Semantic cuts so one ticket's ranting never blurs into the next topic's vector.
  • Worth the extra embedding pass.
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,      # characters, roughly 200 tokens
    chunk_overlap=120,   # about 15 percent bleed across the cut
    separators=["\n\n", "\n", ". ", " "],  # biggest boundary first
)
chunks = splitter.split_text(markdown_doc)

Why 800/120: those are characters, about 4 per token, so 800 characters is roughly 200 tokens, inside every embedder's sweet spot. For markdown, split on headings first and fall back to recursive inside oversized sections.

Failure modes

  • Silent truncation: chunking to the embedder's maximum quietly deletes tails · chunk to the recommended size and verify with a token count.
  • Characters vs tokens: 800 characters is about 200 tokens · confusing the units quadruples or quarters your real chunk size.
  • Shredded structure: a table or code block split across chunks answers nothing · keep them atomic or serialize the rows.
  • Overlap overdone: 30% overlap fills top-k with near-duplicates and inflates storage for almost no recall.
  • Most-tuned, least-evaluated knob: teams nudge chunk size on vibes · measure with retrieval evals or leave it.
  • Re-chunk amnesia: every strategy change re-embeds the corpus · budget the migration and version the strategy with the index.
  • Contextual cost: one LLM call per chunk at ingest · cache the context lines.

Keep in mind

  • Start recursive, 400 to 800 tokens, overlap 10 to 15%, cut on headings where they exist.
  • Chunk to the recommended size, never the maximum, and count tokens, not characters.
  • Keep tables and code blocks atomic.
  • Attach source, section path, date, ACL and page to every chunk; filter on metadata before similarity.
  • Try contextual chunks when misses are expensive, and cache the context lines.
  • Treat strategy changes as migrations: re-chunk, re-embed, re-index, prove the recall gain with evals.
