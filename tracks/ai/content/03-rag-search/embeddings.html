Embeddings and vector stores

Keyword search fails the moment wording differs. An embedding turns each chunk of text into a vector of numbers, so "how similar are these two meanings" becomes arithmetic instead of string matching. The model sets the quality of that map, the store sets how fast you can query it.

Why you need it
  • Paraphrase: "How do I get my money back?" and "What is the refund policy?" share zero useful keywords.
  • String matching: fails on synonyms, jargon gaps and typos, and computers can only compare numbers.
  • Forced move: turn meaning into geometry, so "distance between two texts" becomes computable.
  • Meaning as a vector: an compresses a passage into a few hundred or a few thousand floats. No single dimension is readable on its own, the direction of the whole vector carries the meaning. Same representation-learning idea as ML fundamentals.
  • : compare directions, ignore lengths. Rough ruler: ~1.0 same meaning · ~0.8 cousins · ~0.5 vaguely related · ~0 unrelated. Calibrate on your own corpus before trusting any threshold.
  • Geometry: plot every chunk as a point, paraphrases cluster together, questions land near their answers. "Find similar" becomes "find nearest", a problem maps solved decades ago. The vector is the mean of token vectors, so wide chunks blend to topic mush, see chunking.
  • Trained by contrast: millions of (passage, similar passage, stranger) triples, pull the pair together, push the stranger away. That one objective is why paraphrases land close.

Solutions

The model sets the map's quality, the store sets how fast you can point at it. Three real homes for the vectors.

How it works

  • Chunks, users, tenants and permissions join in a single query. Backups and transactions come free because it is Postgres.
  • An index keeps queries fast into the low millions of rows per table.
  • Rule of thumb: if Postgres already runs your app, start here. Leave only on a measured wall (recall at your p99, index build time, memory pressure), see DB sync.
-- one table for state + vectors, one index for speed
ALTER TABLE chunks ADD COLUMN embedding vector(1536);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

ANN indexes · HNSW vs IVFFlat

  • Brute force is hopeless: 100M rows means 100M distance computations per query. trades a sliver of recall for log-scale speed.
  • HNSW: layered proximity graph, enter zoomed out and refine downward, about log(n) hops. No training pass, tolerates updates, but memory hungry because the graph lives in RAM.
  • IVFFlat: cluster vectors into lists at build time, probe only the nearest few lists per query. Cheaper memory, but needs a training pass and recall drops on skewed or drifting data.
  • Recall vs latency: tune ef_search (HNSW) or nprobe (IVF) up for recall, down for speed. Measure recall against a brute-force sample on your own data, defaults are usually safe, your corpus may not be usual.

Trade-offs

  • pro: zero new infrastructure, vectors join app data, transactions and backups free
  • con: tuning is on you, walls past the low millions of rows per table, pgvectorscale for tens of millions

How it works

  • Quantization, rich filterable indexes, scale-out and managed options come built in. The whole engine assumes vectors.
  • Wins at large scale, heavy filtered search, or when vectors ARE the product rather than a feature.

Trade-offs

  • pro: scale, filtered-search speed, quantization, managed options
  • con: one more system to run and keep in sync, ops burden, vendor lock and egress costs on the managed ones

How it works

  • The index is a library or a local file. Minutes to first query, nothing to operate.
  • Right tool for notebooks, spikes and demos where the corpus fits in memory.

Trade-offs

  • pro: fastest start, no infrastructure, free
  • con: a starter kit, not a database. No concurrency, permissions or backup story, rebuild on restart

choosing the model

  • General models first: a strong general embedding model beats a clever pipeline on a weak one, most corpora are covered.
  • Domain when jargon is dense: code (Voyage), multilingual (BGE-M3, Cohere embed v3), finance and biology (Voyage domain models). Wins show up as recall on your rare terms.
  • Leaderboards are a starting point: rankings age fast and test tasks that are not yours. Shortlist two or three, run them on your own golden queries, see evals.
  • Etiquette matters: E5-style models need "query:" and "passage:" prefixes, Cohere wants an input_type. Skip them and quality quietly tanks.

dimensions · storage · MRL

  • The ladder: 384 dims for mini models (fast, fuzzy) · 768 to 1024 the open-weight sweet spot (BGE, E5) · 1536 the sensible API default (3-small) · 3072 max quality and max cost (3-large).
  • Storage math: floats = rows × dims × 4 bytes (float32). One million chunks at 1536 dims is about 6 GB before index overhead, roughly double it for HNSW.
  • : embed once at full width, truncate to the first N dims for cheap storage or fast comparisons, re-normalize after truncating. No re-embedding when the tradeoff changes.
When to use · when not

Use when

  • Postgres already runs the app → pgvector + HNSW first
  • Scale, heavy filters, or vectors are the product → dedicated store
  • Notebook, spike or demo → in-process index
  • Jargon-dense corpus (code, finance, biology) → domain model
  • Bulk cost pressure → fewer dims or MRL truncation

Skip when

  • Skip dedicated while pgvector still passes recall at your p99
  • Skip pgvector past tens of millions of rows without a tuning budget
  • Skip in-process for anything production
  • Skip leaderboards as the decision, test candidates on your own queries
  • Skip full 3072 dims when a truncated 1024 passes evals

Example

Two phrases with zero shared keywords, one dot product. The API returns normalized vectors, so the bare @ IS cosine. Store normalized too, or your distance filters quietly prefer long documents.

from openai import OpenAI
import numpy as np

client = OpenAI()
resp = client.embeddings.create(
    model="text-embedding-3-small",
    input=["How do refunds work?", "Money-back guarantee"],
)
v = np.array([d.embedding for d in resp.data])  # (2, 1536)
sim = v[0] @ v[1]  # about 0.8+, same meaning, zero shared keywords

ticket dedup · clusters

  • Ten years of support tickets embedded and clustered by meaning.
  • Duplicates surface as near-zero-distance neighbors, close them in bulk.
  • Zero keywords in common, same angry customer.

semantic cache · nearest answer

  • Repeated questions answered by nearest neighbor instead of a fresh generation.
  • Cuts cost and latency on FAQ-shaped traffic.
  • Scoping and staleness rules live in caching.

code search · geometry

  • "Find a similar function" is a nearest-neighbor query over code embeddings.
  • Production code search fuses embeddings with lexical signals.
  • Symbol names still need the keyword lane, see search and reranking.
Watch out
  • Mixing embedding models: query embedded with model A, documents with model B. Different maps, similarity becomes noise, results quietly degrade instead of erroring. Store the model id on every row and assert query model equals index model.
  • Stale embeddings after a model swap: re-embed everything, blue/green. New column or index, backfill, verify recall, then flip reads.
  • Normalization drift: dot product equals cosine only on unit-length vectors. A few unnormalized rows and distance quietly prefers long documents. Normalize once at write time, pick one metric per index, never mix.
  • Dimension confusion: MRL truncation without re-normalizing, or a 1536 query against a 1024 index, is a silent bug in the making. Validate dims and norms at insert.
  • Threshold folklore: 0.75 is not a universal "relevant" line, the cosine distribution shifts per model and corpus. Calibrate on labeled pairs from your own data.
  • Ignoring ANN recall: a smaller index or an aggressive ef_search cut silently drops the exact chunk retrieval needed. Track recall@k against a brute-force sample, see evals.
Remember
  • One embedding model for queries AND documents, record its id on every row.
  • Store normalized vectors, know your distance metric, validate dims at insert.
  • Pick dimensions deliberately, try MRL truncation before paying full width.
  • Start with pgvector + HNSW when Postgres is already there, move on a measured wall.
  • Calibrate similarity thresholds on your own corpus, not folklore numbers.
  • Re-embed the whole corpus on any model change, blue/green, then flip.
  • Track ANN recall@k so speed wins never eat quality silently.
