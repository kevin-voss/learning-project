Embeddings and vector stores

Keyword search fails the moment wording differs. An embedding turns each chunk into a vector, so "how similar are these meanings" becomes arithmetic instead of string matching. The model sets the map's quality, the store sets how fast you can query it.

In this chapter Trace text through embedding, approximate nearest-neighbor retrieval and metadata filtering; understand recall, dimension and index tradeoffs.

Why this layer matters

  • Paraphrase: "How do I get my money back?" and "What is the refund policy?" share zero useful keywords.
  • String matching: fails on synonyms, jargon gaps and typos. Computers compare numbers.
  • Forced move: turn meaning into geometry, so distance between texts becomes computable.
  • Meaning as a vector: an compresses a passage into a few hundred to a few thousand floats. No single dimension is readable; the direction of the whole vector carries the meaning. Same representation-learning idea as ML fundamentals.
  • : compare directions, ignore lengths. Rough ruler: ~1.0 same meaning · ~0.8 cousins · ~0.5 vaguely related · ~0 unrelated; real ranges shift per model, so calibrate.
  • Geometry: paraphrases cluster, questions land near their answers. "Find similar" becomes "find nearest", a problem maps solved decades ago. In mean-pooled models the vector is the mean of token vectors, so wide chunks blend to topic mush, see chunking.
  • Trained by contrast: millions of (passage, similar passage, stranger) triples; pull the pair together, push the stranger away. That objective is why paraphrases land close.

Representation and index

Three real homes for the vectors, from production default to prototype.

How it works

  • Chunks, users, tenants and permissions join in one query. Backups and transactions come free because it is Postgres.
  • An index keeps queries fast into the low millions of rows per table.
  • Rule of thumb: if Postgres already runs your app, start here. Leave only on a measured wall: recall at your p99, index build time, memory pressure (see DB sync).
-- one table for state + vectors, one index for speed
ALTER TABLE chunks ADD COLUMN embedding vector(1536);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

ANN indexes · HNSW vs IVFFlat

  • Brute force is hopeless: 100M rows, 100M distance computations per query. trades a sliver of recall for log-scale speed.
  • HNSW: layered proximity graph, enter zoomed out and refine downward, about log(n) hops. No training pass, tolerates updates, but memory hungry: the graph lives in RAM.
  • IVFFlat: cluster vectors into lists at build time, probe only the nearest few lists per query. Less memory, but needs a training pass and recall drops on skewed or drifting data.
  • Recall vs latency: raise ef_search (HNSW) or nprobe (IVF) for recall, lower for speed. Defaults are usually safe; check recall against a brute-force sample of your own data.

Trade-offs

  • pro: zero new infrastructure, vectors join app data, transactions and backups free
  • con: tuning is on you; walls past the low millions of rows per table, pgvectorscale for tens of millions

How it works

  • Quantization, filterable indexes, scale-out and managed options built in. The whole engine assumes vectors.
  • Wins at large scale, heavy filtered search, or when vectors ARE the product.

Trade-offs

  • pro: scale, filtered-search speed, quantization, managed options
  • con: one more system to run and keep in sync, vendor lock and egress costs on managed ones

How it works

  • The index is a library or local file: minutes to first query, nothing to operate.
  • For notebooks, spikes and demos where the corpus fits in memory.

Trade-offs

  • pro: fastest start, no infrastructure, free
  • con: a starter kit, not a database. No concurrency, permissions or backup story, rebuild on restart

choosing the model

  • General models first: a strong general model beats a clever pipeline on a weak one.
  • Domain when jargon is dense: code (Voyage), multilingual (BGE-M3, Cohere embed v3), finance and biology (Voyage domain models). Wins show up as recall on your rare terms.
  • Leaderboards are a start: rankings age fast and test tasks that are not yours. Run two or three candidates on your own golden queries, see evals.
  • Etiquette matters: E5-style models need "query:" and "passage:" prefixes, Cohere wants an input_type. Skip them and quality quietly tanks.

dimensions · storage · MRL

  • The ladder: 384 dims for mini models (fast, fuzzy) · 768 to 1024 the open-weight sweet spot (BGE, E5) · 1536 the sensible API default (3-small) · 3072 max quality and max cost (3-large).
  • Storage math: rows × dims × 4 bytes (float32). One million chunks at 1536 dims is about 6 GB before index overhead; budget roughly double for HNSW.
  • : embed once at full width, truncate to the first N dims for cheaper storage and comparisons, re-normalize after truncating. No re-embedding when the tradeoff changes.

Decision boundary

Use when

  • Postgres already runs the app → pgvector + HNSW first
  • Scale, heavy filters, or vectors are the product → dedicated store
  • Notebook, spike or demo → in-process index
  • Jargon-dense corpus (code, finance, biology) → domain model
  • Bulk cost pressure → fewer dims or MRL truncation

Skip when

  • Dedicated store while pgvector passes recall at your p99
  • pgvector past tens of millions of rows without a tuning budget
  • In-process for anything production
  • Leaderboards as the decision, test on your own queries
  • Full 3072 dims when a truncated 1024 passes evals

Worked example

Two phrases, zero shared keywords, one dot product. On normalized vectors the bare @ IS cosine. Store normalized too, or dot-product scores quietly favour vectors with larger norms instead of closer meaning.

from openai import OpenAI
import numpy as np

client = OpenAI()
resp = client.embeddings.create(
    model="text-embedding-3-small",
    input=["How do refunds work?", "Money-back guarantee"],
)
v = np.array([d.embedding for d in resp.data])  # (2, 1536)
norms = np.linalg.norm(v, axis=1, keepdims=True)
v = v / np.maximum(norms, 1e-12)
sim = float(v[0] @ v[1])  # cosine for normalized vectors; inspect the returned score

ticket dedup · clusters

  • Ten years of support tickets embedded and clustered by meaning.
  • Duplicates surface as near-zero-distance neighbors even with zero keywords in common. Close them in bulk.

semantic cache · nearest answer

  • Repeated questions answered by nearest neighbor instead of a fresh generation, cutting cost and latency on FAQ-shaped traffic.
  • Scoping and staleness rules live in caching.

code search · geometry

  • "Find a similar function" is a nearest-neighbor query over code embeddings.
  • Symbol names still need a lexical lane fused in, see search and reranking.

Failure modes

  • Mixing embedding models: query from model A, documents from model B. Different maps, so similarity is noise, with no error. Store the model id per row and assert it at query time.
  • Stale embeddings after a model swap: re-embed blue/green: new column or index, backfill, verify recall, flip reads.
  • Normalization drift: dot product equals cosine only on unit vectors; unnormalized rows skew distance toward long documents. Normalize at write, one metric per index.
  • Dimension confusion: MRL truncation without re-normalizing, or a 1536 query against a 1024 index. Validate dims and norms at insert.
  • Threshold folklore: 0.75 is not a universal "relevant" line; cosine distributions shift per model and corpus. Calibrate on labeled pairs.
  • Ignoring ANN recall: a smaller index or aggressive ef_search silently drops the chunk you needed. Track recall@k against brute force, see evals.

Keep in mind

  • One embedding model for queries AND documents, its id on every row.
  • Store normalized vectors, one distance metric, dims validated at insert.
  • Try MRL truncation before paying full width.
  • Start with pgvector + HNSW when Postgres is already there; move on a measured wall.
  • Calibrate similarity thresholds on your own corpus.
  • Re-embed the whole corpus on any model change, blue/green.
  • Track ANN recall@k so speed wins never silently eat quality.
