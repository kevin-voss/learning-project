RAG the big picture

A base model only knows its training data. Retrieval puts a few paragraphs of fresh, private text in front of it per question and has it answer and cite from them. No retraining.

In this chapter Follow the offline ingestion path and online query path; identify where permissions, freshness and evidence can fail.

Why this layer matters

  • Frozen knowledge: the model has never seen your wiki, contracts or tickets, and stopped learning at its training cutoff.
  • Confident invention: ask anyway and it fills the gaps with fluent, plausible, unverifiable text.
  • Pasting everything fails: context is finite and metered (see context budget). 500 pages × 10k queries a day is a real invoice, and recall still droops mid-window.
  • Fine-tuning the facts in fails: weights teach style, not facts (see the fine-tune decision). Nothing trained today knows tomorrow's prices.
  • The real need: the right few citable paragraphs per question, without retraining anything.

Retrieval pipeline

Four ways to ground an answer in your facts. Retrieval wins most of them, the alternatives win niches.

How it works

  • = fetch, then answer. Look up passages from YOUR data, put them in the prompt, answer from them, cite them.
  • Two pipelines: an offline ingest batch job and an online query hot path. Keep them separate in your head and your code.
  • Fresh evidence, no retraining: updating the index is a file drop; the model may still be fine-tuned for other goals. Enforce tenant and document ACL filters during retrieval, before evidence reaches the model, and recheck authorization at any action boundary.
  • What retrieval provides: candidate evidence and provenance. Citation correctness, data locality and request cost depend on your implementation and must be validated (see token cost).

Ingestion and parsing · where RAG pipelines quietly die

  • A PDF is a printout, not a document: characters at coordinates. Two-column layouts, tables as positioned text, scans that are just photographs.
  • Native text vs OCR: born-digital PDFs, HTML and Office files carry an exact text layer, so extraction is faithful. Scans are pictures: OCR guesses the letters, and every wrong guess flows into the embeddings. More in ML and multimodal.
  • The parser ladder: spend more only as the document resists. Layout parsers (Docling, Unstructured, LlamaParse) for born-digital files, classic OCR (Tesseract, PaddleOCR) for clean scans, cloud document AI (Azure DI, Google DocAI, Textract) for forms and tables at scale, a vision LLM for horror layouts, ColPali-style page-image retrieval when text is hopeless.
  • why markdown headings become boundaries for chunking, code fences stay atomic, lists stay lists.
  • Tables are the boss fight: keep each table atomic (one table = one chunk) or serialize rows to markdown or JSON. A table split across three chunks answers nothing.
  • Incremental sync: re-parse only changed documents, delete-and-replace by document id, dedupe on the way in. One PDF uploaded five times becomes five near-identical chunk sets that crowd out diversity.
  • Source of truth: the index is disposable and rebuildable. Permissions, deletes and versions flow from the source system, never from index state.
  • gotcha failures are invisible: the pipeline never errors. A merged table column or glued header surfaces months later as wrong answers, not parse logs. Parsing is the number one silent RAG killer.
  • cost parsing is the biggest ingest line item: every page, once per run, so per-page prices compound across re-ingestions. Get the ladder right before scaling.

Naive RAG failure modes

  • Retrieval miss: the model cannot use a passage you never fetched. Most "the LLM is wrong" incidents are retrieval misses. Fixes live in hybrid search and rerank.
  • Vocabulary gap: users say "time off", the docs say "PTO accrual". Pure vector search can miss, keyword fusion rescues.
  • Top-k redundancy: five near-identical chunks fill the window with one idea and crowd out the rest.
  • Ignored context: the model answers from its weights despite the passages. Instruct "answer only from these passages", require citations, then verify each citation supports its claim; a well-formed citation is not a correct one.
  • No honest miss: without an abstention path, "not in my docs" becomes a hallucination.
  • Stale index: documents changed upstream, the index never heard. Wire sync to source events.

Trade-offs

  • pro: fresh, private, citable answers with no retraining; cost comes from parsing, retrieval and generation.
  • pro: permissions and freshness live in the retrieval layer, before the model sees a token.
  • con: a system, not a feature: parsing, chunking, search and evals, and one weak link caps everything downstream.
  • con: retrieval quality is the ceiling. No generation upgrade recovers an unfetched passage.

How it works

  • Skip retrieval: paste a few hundred static pages into a long-context window and ask.
  • Fine for a small, static, rarely queried doc set: a demo, an internal FAQ, one contract.

Trade-offs

  • pro: zero infrastructure, no pipeline to build, debug or keep fresh.
  • con: you pay for the whole corpus on every question (see token cost).
  • con: recall droops mid-window on long prompts (see context budget).
  • con: weak citations, the model read one wall of text, not addressable passages.
  • con: live, large or private corpora need retrieval anyway.

How it works

  • Train on examples so behavior sticks: style, tone, output format, domain vocabulary.
  • Fine-tuning can change behavior and knowledge, but is a poor freshness mechanism for facts that change often; retrieval exposes current source evidence at query time. Full decision in fine-tune vs RAG.

How it works

  • No retrieval, no fine-tune: ask and trust the training data. Fine for demos and throwaways over small static fact sets.

Trade-offs

  • pro: zero setup, the fastest first prototype.
  • con: no citations, silent staleness, private data out of reach.

Each pipeline stage has its own deep dive: parsing above, then chunking, embeddings and search and rerank.

Decision boundary

Use when

  • The corpus is large, private or live, and citations are part of the product.
  • Facts change faster than any training cycle.
  • Cost per question should stay flat as the corpus grows.
  • Permissions must filter answers per user or tenant.

Skip when

  • The doc set is tiny and static: paste it whole.
  • You only want style, tone or format: prompt or fine-tune instead (see fine-tune vs RAG).
  • It is a demo or throwaway, grounding does not matter yet.
  • Nobody can own parsing, chunking, search and evals.

Worked example

Failure modes

  • Silent parse failure: confidently wrong answers about the one table the user cared about · inspect parsed output for your worst pages before scaling (see evals).
  • Per-page cost compounds: every re-ingestion parses every page again · vision-LLM parsing at scale is a budget decision.
  • Vision parsing invents details: validate critical fields against source systems, keep page images for audit.
  • Duplicate ingestion: five copies, five overlapping chunk sets · hash or content-match on the way in.
  • Retrieval is the ceiling: debug "wrong answer" as a retrieval bug first, a generation bug second.
  • Stale index: answers keep quoting deleted policy · tie deletions and updates to source-of-truth events.

Keep in mind

  • Two code paths, one index: offline ingest batch job, online query hot path.
  • Parse to markdown with tables and headings intact before chunking.
  • Escalate parser spend only as documents resist: native text, then layout, then OCR, then vision.
  • Dedupe and delete-and-replace on every sync. The index is disposable, the source system is not.
  • Filter permissions in retrieval, before the model sees a token.
  • Prompt for citations and honest misses. Evaluate retrieval separately from generation.
