RAG variants: vector, graph, agentic

Plain vector RAG is one hop: question in, similar chunks out. It answers "which passages resemble this query?" and nothing else. Every other variant covers a question shape that hop cannot reach.

In this chapter Choose vector, graph, multi-query or agentic retrieval based on query structure, corpus relationships and latency budget.

Why this layer matters

  • Connections: "How are Acme, Beta and Omega related?" The evidence spans a dozen documents and no single chunk resembles the question.
  • Multi-hop: "Who worked with whom on project X?" is a chain of lookups, each depending on the last.
  • Corpus-wide themes: "What trends run through all 200 reports?" Fetching the top 5 chunks is a category error.
  • Blind retry: when the first retrieval misses, the plain pipeline still generates. It cannot notice and search again.

Retrieval patterns

One corpus can feed several machineries. A cheap router (keyword rules, schema match or one classify call) picks per query. Start from the RAG big picture baseline.

How it works

  • One hop: embed the query, fetch top-k similar chunks, generate. Predictable latency and cost.
  • Quality is upstream: fancier variants do not save a weak baseline. Wins come from chunking, embeddings and hybrid search plus rerankers.
  • Limits: no relations, no aggregation, no corpus-level synthesis.

Trade-offs

  • pro: cheapest lane, latency you can promise, handles "find docs about X".
  • con: relationship, aggregate and corpus-wide questions get confident shallow answers.

Lighter alternatives

  • Long-context stuffing: when a small static corpus fits the window, paste everything. Every call pays for the whole window (see token cost) and needle recall drops as it grows (see context budget).
  • Parent-child retrieval: small child chunks match precisely, their parent chunks go to the model for full context.
  • Late interaction: the idea (ColBERT) ranks by token-level matches. Sharper than single vectors, heavier storage.
  • Siblings: aggregates belong to text-to-SQL, pixels to multimodal retrieval. Same routing idea.

How it works

  • Ingest builds the graph: an LLM extracts entities and relations from every document. Acme, Beta and Omega become nodes, "acquired" and "supplies" become edges.
  • Questions become traversals: questions like "who worked with whom on X" are a two-edge walk, exactly where similarity search fails.
  • Local vs global: local queries walk one entity's neighborhood and feed it to the model. Global queries need corpus-level text no single chunk holds.

Costs, the full bill

  • Upfront: LLM extraction over the whole corpus before the first query. Prototype on a slice, measure cost per document, then scale.
  • Updates: the graph does not re-extract itself. Wire re-extraction to a pipeline trigger or answers quietly rot.
  • Per query: traversals cost more than top-k, plus a standing budget for and human spot checks.

Trade-offs

  • pro: wins when relationships are the product: compliance lineage, knowledge graphs, org and supply-chain questions.
  • con: gotcha extraction quality caps everything downstream; garbage edges produce confident wrong traversals.

How it works

  • The model decides when and what to search. Retrieval becomes a loop: retrieve, grade the hits, then answer, refine the query, or pivot.
  • Grading is in the self-RAG style: relevant? supported? enough coverage?
  • Pivots: corrective RAG discards bad hits and falls back to the web, query rewrite repairs vague asks, decomposition splits one question into sub-searches.

Budgets stop the loop

  • Max steps, max tokens, wall-clock cap, or the loop spins forever, see durable ops.
  • Implementation shape: the retrieve-grade-rewrite cycle maps onto orchestration graphs; steering ideas live under agent patterns.

Trade-offs

  • pro: ambiguous multi-step research questions get real answers where no single pass finds the evidence.
  • con: every step is a model call plus retrieval, so latency and cost multiply per round.

Keep FAQ-shaped traffic off the agentic lane: a loop answering "how many sick days do I get" costs several vector answers for zero quality gain.

Decision boundary

Use when

  • A real query log shows connection, aggregate or corpus-wide questions the baseline flunks.
  • Research-style traffic needs search, read, pivot, search again.
  • Relationships are the product: lineage, compliance, knowledge graph.
  • You can budget LLM ingest and re-extraction.

Skip when

  • Traffic is FAQ-shaped and single passages answer it.
  • The budget cannot absorb LLM extraction over the corpus.
  • Nobody will maintain graphs or indexes as documents change.
  • Latency targets rule out multi-step loops.

Worked example

A cheap router picks the lane per question shape. Drug interactions ride the graph: "is X safe with Y" is a two-node lookup with labeled edges, not anecdotes from papers. Policy Q&A rides the vector lane, where the lever is chunking discipline. Patent and legal research ride the agentic loop, with a hard step budget and a fallback answer. First the router, then the loop it routes to.

def route(query: str) -> str:
    if asks_connections(query):     # entities, relations, multi-hop
        return "graph_rag"
    if needs_research(query):          # ambiguous, needs a plan
        return "agentic_rag"
    return "vector_rag"                 # the sensible default
def agentic_rag(query, max_steps=4):
    for step in range(max_steps):
        hits = retrieve(query)
        grade = grade_hits(query, hits)  # relevant? supported? enough?
        if grade.enough:
            return answer(query, hits)
        query = rewrite(query, grade.gaps)
    return answer_insufficient(query)

Failure modes

  • Extraction noise: the LLM invents or misses relations and the graph amplifies them · budget entity resolution and human spot checks
  • Runaway loops: each iteration is a model call plus retrieval · cap steps, tokens and time, log the caps you hit
  • Cold-start bills: graph RAG pays extraction before the first query · prototype on a slice
  • Stale machinery: graphs and indexes do not re-extract themselves · wire updates to a pipeline trigger
  • Router misfires: a research question routed to vector gets a confident shallow answer · log the route per query, misroutes are your best evals signal
  • Long-context false economy: cheap to build, expensive to keep · usage growth makes stuffing your largest line item

Keep in mind

  • Default to vector RAG, justify every departure with a real query log.
  • Route by question shape: lookup to vector, connections to graph, research to agentic.
  • Ship every agentic loop with a step, token and time budget.
  • Price graph RAG ingest as an LLM job and schedule re-extraction when the corpus changes.
  • For global questions, pre-build community summaries.
  • Log which lane answered each query and review misroutes monthly.
