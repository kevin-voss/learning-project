RAG variants: vector, graph, agentic

Plain vector RAG is one hop: question in, similar chunks out. It answers "which passages resemble this query?" and nothing else. Every other variant exists to cover a question shape that hop cannot reach.

Why you need it
  • Connections: "How are Acme, Beta and Omega related?" The evidence is spread across a dozen documents and no single chunk resembles the question.
  • Multi-hop: "Who worked with whom on project X?" is a chain of lookups where each step depends on the previous answer.
  • Corpus-wide themes: "What trends run through all 200 reports?" Fetching the top 5 chunks is a category error.
  • Blind retry: when the first retrieval misses, the plain pipeline still generates. It cannot notice the miss and search again.
Solutions

One corpus can feed several machineries at once. A cheap router, keyword rules, schema match or one classify call, picks per query, and a misroute gives a shallow answer, not a crash. Start from the RAG big picture baseline.

How it works

  • One hop: embed the query, fetch top-k similar chunks, generate. One retrieval round trip, predictable latency and cost.
  • Quality is upstream: fancier variants do not save a weak baseline. Wins come from chunking, embeddings and hybrid search plus rerankers.
  • Limits: no relations, no aggregation, no corpus-level synthesis. Not broken, just one shape.

Trade-offs

  • pro: cheapest lane to run, latency you can promise, handles "find docs about X".
  • con: relationship, aggregate and corpus-wide questions get confident shallow answers.

Lighter alternatives

  • Long-context stuffing: when the corpus fits the window, skip retrieval and paste everything. Fine for small static doc sets, but every call pays for the whole window (see token cost) and needle recall drops as the window grows (see context budget).
  • Parent-child retrieval: small child chunks make matches precise, their big parent chunks go to the model so generation gets full context.
  • Late interaction: the idea (ColBERT) ranks by token-level matches. Sharper than single vectors, heavier storage.
  • Siblings: aggregates belong to text-to-SQL, pixels to multimodal retrieval. Different machinery again, same routing idea.

How it works

  • Ingest builds the graph: an LLM extracts entities and relations from every document. Acme, Beta and Omega become nodes, "acquired" and "supplies" become edges.
  • Questions become traversals: questions like "who worked with whom on X" are a two-edge walk, exactly where similarity search fails.
  • Local vs global: local queries walk one entity's neighborhood and feed the walk to the model. Global queries need corpus-level text no single chunk holds.

Community summaries

  • Cluster the graph with , pre-write one summary per community at ingest.
  • Global questions read the summaries instead of fetching every chunk. Never fetch all chunks and hope. why communities

Costs, the full bill

  • Upfront: extraction is an LLM call over the whole corpus before the first query lands. Prototype on a slice, measure cost per document, then scale.
  • Updates: documents change but the graph does not re-extract itself. Wire re-extraction to a pipeline trigger or answers quietly rot.
  • Per query: traversals are more complex than top-k, plus a standing budget for and human spot checks.

Trade-offs

  • pro: wins when relationships are the product. Compliance lineage, knowledge graphs, org and supply-chain questions.
  • con: gotcha extraction quality caps everything downstream. Garbage edges produce confident wrong traversals.

How it works

  • The model decides when and what to search. Retrieval becomes a loop: retrieve, grade the hits, then answer, refine the query, or pivot.
  • Grading is in the self-RAG style: relevant? supported? enough coverage?
  • Pivots: corrective RAG discards bad hits and falls back to the web, query rewrite repairs vague asks, decomposition splits one question into sub-searches.

Budgets stop the loop

  • Max steps, max tokens, wall-clock cap. An unbudgeted loop spins forever, see durable ops.
  • Implementation shape: the retrieve-grade-rewrite cycle maps onto orchestration graphs, the steering ideas live under agent patterns.

Trade-offs

  • pro: ambiguous multi-step research questions get real answers, no single pass finds the smoking gun.
  • con: every step is a model call plus retrieval, so latency and cost multiply per round.

FAQ-shaped traffic must not take the agentic lane. A loop answering "how many sick days do I get" costs several times the vector answer for zero quality gain.

When to use · when not

Use when

  • A real query log shows connection, aggregate or corpus-wide questions the baseline flunks.
  • Research-style traffic needs search, read, pivot, search again.
  • Relationships are the product: lineage, compliance, knowledge graph.
  • You can price LLM ingest and re-extraction into the budget.

Skip when

  • Traffic is FAQ-shaped, single passages answer everything, keep the vector lane.
  • The budget cannot absorb LLM extraction over the corpus.
  • Nobody will maintain graphs or indexes as documents change.
  • Latency targets rule out multi-step loops.

Example

A cheap router picks the lane per question shape. Drug interaction checks ride the graph lane, "is X safe with Y" is a two-node lookup with edge labels instead of anecdotes from papers. Policy Q&A rides the vector lane, one hop over single passages where the lever is chunking discipline. Patent and legal research ride the agentic loop, shipped with a hard step budget and a fallback answer. The first sample routes, the second is the loop it routes to.

def route(query: str) -> str:
    if asks_connections(query):     # entities, relations, multi-hop
        return "graph_rag"
    if needs_research(query):          # ambiguous, needs a plan
        return "agentic_rag"
    return "vector_rag"                 # the sensible default
MAX_STEPS = 4  # the budget that stops the loop

for step in range(MAX_STEPS):
    hits = retrieve(query)
    grade = grade_hits(query, hits)    # relevant? supported? enough?
    if grade.enough:
        return answer(query, hits)
    query = rewrite(query, grade.gaps)   # refine and go again
return answer_insufficient(query)
Watch out
  • Extraction noise: the LLM invents or misses relations and the graph amplifies confident nonsense · budget entity resolution and human spot checks
  • Runaway loops: each iteration is a model call plus retrieval · cap steps, tokens and time, then log the caps you hit
  • Cold-start bills: graph RAG pays LLM extraction before the first query lands · prototype on a slice, then scale
  • Stale machinery: graphs and indexes do not re-extract themselves · wire updates to a pipeline trigger
  • Router misfires: a research question routed to vector gets a confident shallow answer · log the route per query, misroutes are your best evals signal
  • Long-context false economy: cheap to build, expensive to keep · usage growth turns stuffing into your largest line item
Remember
  • Default to vector RAG, justify every departure with a real query log.
  • Route by question shape: lookup to vector, connections to graph, research to agentic.
  • Ship every agentic loop with a step, token and time budget before it goes near users.
  • Price graph RAG ingest as an LLM job and schedule re-extraction when the corpus changes.
  • For global questions, pre-build community summaries. Never fetch all chunks and hope.
  • Log which machinery answered each query and revisit the misroutes monthly.
