Search and reranking

Every corpus gets asked two kinds of questions: "cozy winter jacket" and "XR-2500-B". The first needs meaning, the second exact characters, and no single lane serves both. Production retrieval runs both lanes, merges them by rank, then spends a slow expert on the finalists only.

In this chapter Separate candidate recall from ranking precision and use a trace to decide when lexical, dense, hybrid and cross-encoder stages help.

Why this layer matters

  • Meaning queries: "cozy winter jacket". Exact words fail, paraphrase wins. Dense vectors from embeddings own this half.
  • Identifier queries: "XR-2500-B", "ERR_CONN_RESET_7", "section 4.2". No embedding knows which SKU matters, and paraphrase power actively hurts.
  • Single-lane systems fail the half they were not built for, and users cannot tell you in advance which half they are in.

Search pipeline

Two cheap lanes, one merge, one slow expert: right lane, good merge, honest second opinion.

How it works

  • Smart word counting: . weights rare terms heavily, rewards repeats with saturation, length normalization stops big documents winning by size.
  • Saturation (k1 ~ 1.2): ten mentions of "refund" are not ten times more relevant. Also blunts keyword spam.
  • Length normalization (b ~ 0.75): long documents mention everything by accident; without b they out-score tight answers for sheer size.
  • Why it still wins on exact terms: IDs, error codes, function names and rare tokens are characters, not meaning. BM25 matches them verbatim, ranks deterministically and explains itself.
  • Cost profile: an inverted index, no model calls, sub-millisecond queries. Postgres full-text search uses tsvector + ts_rank_cd (cover-density ranking), not BM25.

Trade-offs

  • pro: sub-millisecond, no model calls, deterministic and explainable
  • con: paraphrase, synonyms and cross-language all miss; typos and morphology need fuzziness or stemming

How it works

  • Strength: "money-back guarantee" retrieves the refund policy, see embeddings.
  • Honest blind spots: exact identifiers, negation ("no refund" sits NEAR "refund"), rare entities, out-of-vocabulary codes.
  • Learned sparse (): a model expands each document with implied terms. Some of both lanes, bigger indexes, less explainability.

Trade-offs

  • pro: owns the meaning half of traffic, no keyword overlap required
  • con: quality capped by the embedding model

How it works

  • Run BM25 AND dense retrieval on every query, then merge the two ranked lists with .
  • why fuse ranks not scores BM25 scores are unbounded sums, cosine lives in [-1, 1]; averaging them is unit soup. Ranks are universal: score = sum of 1/(60 + rank), where k ~ 60 is a conventional value that damps top-rank dominance.
  • Why hybrid is the default: the query mix is unknowable in advance, and one lane alone loses the half of traffic it cannot serve. Two cheap indexes beat one clever one.

Trade-offs

  • pro: serves both halves of traffic, no lane guessing per query
  • con: two indexes to operate, k = 60 is a start not law

How it works

  • A reads query AND document together through one model, so it sees token-level interactions a bi-encoder (two separate vectors) never can. Far more accurate, paid per pair.
  • Stage 2, not stage 1: retrieve top-50 to top-100 cheaply, rerank down to top-5 or top-10. Scoring the whole corpus this way is hopelessly slow.
  • best cheap win often the biggest quality-per-effort jump in retrieval: same index, same first stage, one extra model call over 50 candidates.
  • Budget: roughly 100 to 300 ms. Batch the candidates, cache popular queries, see caching.

The pipeline · recall wide, rank narrow

  • Recall wide: hybrid retrieval pulls the top-100 candidates, quantity over precision.
  • Rerank narrow: the cross-encoder reorders them and keeps the top-5.
  • Stuff context: survivors go into the prompt best-first, with source citations. Sizing rules live in context budgeting.
  • Query surgery before search: fix typos and abbreviations, decompose multi-part questions, union hits from 3 query variants, or try to close the question-vs-document gap. Each transform is another LLM call that must earn its latency.

Trade-offs

  • pro: top-5 precision soars, one extra call on an existing index
  • con: 100 to 300 ms added, per-pair cost, useless over wide candidate sets

measuring retrieval

  • : did the right chunk make the candidates at all? Target for the hybrid stage.
  • : where does the first good hit land? Target for the rerank stage.
  • Golden questions: 30 to 100 real user questions with labeled relevant chunks, run on every retrieval change. Wire them into evals.

Decision boundary

Use when

  • Exact identifiers dominate → BM25 lane
  • Natural-language and find-similar → dense lane
  • Query mix unknowable → hybrid + RRF, the default
  • Top-5 precision matters → rerank the top-50
  • Vague, multi-part or mismatched queries → query transforms

Skip when

  • BM25-only for paraphrase or cross-language traffic
  • Dense-only on identifier-heavy corpora
  • Cross-encoder scoring of the full corpus
  • Query transforms on simple FAQ traffic, just latency

Worked example

RRF in a few lines of python, then the same fusion in one Postgres round trip: both lanes, ranks fused, top-5 out.

def rrf(ranked_lists, k=60, top_k=5):
    """Merge ranked lists without score-scale headaches."""
    scores = {}
    for ranked in ranked_lists:               # BM25 hits + dense hits
        for rank, doc_id in enumerate(ranked):   # rank 0 = best
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)[:top_k]
-- PostgreSQL full-text + pgvector candidates, tenant-filtered before fusion
WITH keyword_candidates AS (
  SELECT id, ts_rank_cd(tsv, websearch_to_tsquery('english', $1)) AS score
  FROM chunks
  WHERE tenant_id = $3 AND tsv @@ websearch_to_tsquery('english', $1)
  ORDER BY score DESC LIMIT 100
), keyword AS (
  SELECT id, row_number() OVER (ORDER BY score DESC) AS rank FROM keyword_candidates
), vector_candidates AS (
  SELECT id, embedding <=> $2::vector AS distance
  FROM chunks WHERE tenant_id = $3
  ORDER BY distance LIMIT 100
), vector AS (
  SELECT id, row_number() OVER (ORDER BY distance) AS rank FROM vector_candidates
)
SELECT id, sum(1.0 / (60 + rank)) AS score
FROM (SELECT id, rank FROM keyword UNION ALL SELECT id, rank FROM vector) hits
GROUP BY id ORDER BY score DESC LIMIT 5

e-commerce · both lanes

  • BM25 for SKUs and model numbers, dense for "cozy office chair".
  • Rerank the top-50 so the first product row is the right one.

enterprise wiki · unknowable mix

  • Users type both "the Q3 refund thing" and "XR-2500-B".
  • Hybrid underneath, golden questions guarding every change, tenant filter inside both lanes.

Failure modes

  • Filter-before vs filter-after: pre-filtering can starve the ANN index (fewer than k candidates, or a filter it cannot push down); post-filtering can shrink top-100 to three hits. Test your narrowest real filters; prefer indexes that filter during traversal.
  • Tenant isolation: one missing tenant_id predicate puts another tenant's chunks in the prompt. Filter in both lanes via the query builder, test with a cross-tenant canary.
  • Semantic cache lies: a nearest-neighbor hit answers a similar, not identical, question. Scope per tenant and corpus version, set a similarity floor, invalidate on re-index, see caching.
  • Reranking too wide: a cross-encoder over 500 candidates buys little accuracy and burns 2 to 3 seconds. Keep stage 2 at top-50.
  • Unmeasured tuning: tweaking k, ef_search or rerank thresholds without recall@k and MRR on golden questions ships regressions silently.
  • Score soup: a weighted sum of BM25 and cosine scores breaks the moment either model changes scale. Ranks are the stable currency.

Keep in mind

  • Default to hybrid: BM25 + dense on every query, fused with RRF at k ~ 60.
  • Rerank the top-50, feed the top-5 into the context budget.
  • Exact-match traffic belongs on the keyword lane.
  • Tenant and permission filters go inside every lane, tested with canary queries.
  • Guard every retrieval change with recall@k, MRR and golden questions in evals.
  • Cache popular queries only with a similarity floor and per-tenant scope.
