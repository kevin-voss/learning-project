A2A · Agent2Agent protocol

A2A is an open wire protocol for delegating work to an agent whose internals you cannot see: discover it from an Agent Card, send it Messages, and follow the Task it creates until the task completes, asks for input or fails.

In this chapter Read an Agent Card, trace a Task through its v1.0 lifecycle over JSON-RPC, gRPC or HTTP+JSON, secure the trust boundary between agents, and decide when remote delegation beats a tool call or a shared graph.

Why this layer matters

  • Opaque peers: the agent that can do the job often belongs to another team or vendor, with its own model, prompts, tools and memory that you cannot and should not import. A tool schema cannot describe a multi-turn, hours-long negotiation with it.
  • Bespoke glue, again: without a shared contract every agent pair needs its own API, auth and status polling: the N×M integration problem that MCP solved for tools, one level up.
  • Delegation is stateful: remote work needs states such as working, waiting for input and waiting for authorization, plus streaming and callbacks. Plain request/response loses all of that.
  • Complement, not replacement: MCP connects an agent to tools and context it controls; A2A connects it to a peer that keeps its internals private. Typical systems use A2A between agents and MCP inside each one.

Protocol mechanics

Version: this chapter follows the A2A specification v1.0 (v1.0.0 released March 2026, patch v1.0.1 May 2026), an Apache-2.0 project contributed by Google and hosted by the Linux Foundation. The wire version is negotiated as Major.Minor, so peers say 1.0. v1.0 broke compatibility with v0.3: method names, enum spellings and the Part shape all changed, so check which version an SDK or peer speaks before reading its payloads. Every interaction follows one loop: fetch the card, send a Message, follow the Task the server creates until it is interrupted or terminal.

  1. SUBMITTEDServer creates the Task and assigns id plus contextId; clients never pick task ids.
  2. WORKINGRemote agent runs its own loop and emits statusUpdate and artifactUpdate events.
  3. INPUT_REQUIRED · AUTH_REQUIREDInterrupted: the client replies with the same taskId, or resolves authorization out of band.
  4. COMPLETED · FAILED · CANCELED · REJECTEDTerminal and immutable: further messages to the task return UnsupportedOperationError.

On the wire every state carries the TASK_STATE_ prefix, for example TASK_STATE_INPUT_REQUIRED. v0.3 used lowercase input-required; some v1.0 prose still does.

How it works

  • Discovery: every A2A server must publish an , conventionally at https://{domain}/.well-known/agent-card.json; registries and pre-configured URLs are also allowed.
  • Endpoints: supportedInterfaces is an ordered list of {url, protocolBinding, protocolVersion, tenant?}. Clients take the first entry they support and, if tenant is set, copy it into every request. v0.3's top-level url, preferredTransport and protocolVersion are gone.
  • Contract: capabilities declares streaming, pushNotifications, extendedAgentCard and extensions; calling an undeclared capability yields an error. skills[] (id, name, description, tags, examples, input and output media types) describe what the agent is likely to succeed at; they are descriptive, not callable functions.
  • Auth declaration: securitySchemes names API key, HTTP auth, OAuth 2.0, OpenID Connect or mutual TLS schemes; securityRequirements says which apply, card-wide or per skill.
  • Signatures: optional signatures[] are JWS (RFC 7515) over the card canonicalized with JCS (RFC 8785), excluding the signature field; the key is found via kid/jku or a trusted key store.
  • Extended card: with extendedAgentCard: true, authenticated clients call GetExtendedAgentCard for extra skills or quotas hidden from the public card.

Trade-offs

  • pro: standard HTTP caching (Cache-Control, ETag) applies, so discovery costs one conditional GET.
  • con: an unsigned card is a claim, not an identity. Skills are free text a malicious card can tune to win routing decisions.

How it works

  • Message: one turn: messageId (creator-generated), role (ROLE_USER for client to server, ROLE_AGENT back), parts, optional taskId, contextId, referenceTaskIds, metadata.
  • Part: exactly one of text, raw (base64 bytes), url or data (any JSON value), plus optional mediaType and filename. v0.3's kind discriminator and separate TextPart, FilePart and DataPart types are removed.
  • : id, contextId, status (state, optional message, timestamp), artifacts, history. A SendMessage result holds either a task or a direct message; the agent decides whether work deserves a task.
  • Artifact: a deliverable with artifactId, name, parts. Status messages explain; artifacts are the output.
  • vs taskId: a context groups many tasks into one conversation; a taskId continues one task. Mismatched pairs must be rejected, and a client-supplied taskId must name an existing task.

Trade-offs

  • pro: media types per part let a client advertise acceptedOutputModes and get JSON, images or files without a side channel.
  • gotcha con: JSON uses camelCase fields and ProtoJSON enum strings ("TASK_STATE_COMPLETED"), not the proto's snake_case names or integers.

How it works

  • Operations: SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask, SubscribeToTask, CreateTaskPushNotificationConfig, GetTaskPushNotificationConfig, ListTaskPushNotificationConfigs, DeleteTaskPushNotificationConfig, GetExtendedAgentCard. The normative source is a2a.proto, package lf.a2a.v1.
  • JSON-RPC 2.0: POST to the interface URL with "method": "SendMessage". PascalCase replaced v0.3's message/send and tasks/get; streaming uses Server-Sent Events, one JSON-RPC response per event.
  • gRPC: service A2AService with the same method names; streams are server-streaming RPCs.
  • HTTP+JSON: resource routes such as POST /message:send, GET /tasks/{id}, POST /tasks/{id}:cancel, media type application/a2a+json.
  • Versioning: clients must send A2A-Version: 1.0 (header or query parameter); servers read an empty value as 0.3 and return VersionNotSupportedError otherwise. Errors map per binding, e.g. TaskNotFoundError is JSON-RPC -32001, gRPC NOT_FOUND, HTTP 404.
  • Blocking: by default SendMessage waits until the task is terminal or interrupted; configuration.returnImmediately: true returns the task as soon as it exists.

Trade-offs

  • pro: bindings are functionally equivalent, so the choice is operational: JSON-RPC for simplicity, gRPC for typed internal meshes, HTTP+JSON for gateways and caches.
  • con: forgetting the version header silently downgrades you to 0.3 semantics on a dual-version server.

How it works

  • StreamResponse: each event holds exactly one of task, message, statusUpdate (TaskStatusUpdateEvent) or artifactUpdate (TaskArtifactUpdateEvent, with append and lastChunk for chunked output).
  • Streaming: a task stream starts with the Task, delivers events in generation order and closes at a terminal state. SubscribeToTask reattaches after a dropped connection; several streams may watch one task.
  • Push: pass configuration.taskPushNotificationConfig in SendMessage, or call CreateTaskPushNotificationConfig later, with url, optional token and authentication {scheme, credentials}. The agent POSTs the same StreamResponse JSON with an Authorization header built from that config, whatever binding the task used.
  • Delivery: at least once, retries with backoff allowed, 10 to 30 s timeouts recommended. Receivers return 2xx, deduplicate and check the task id is one they created.

Trade-offs

  • pro: webhooks free the client from holding connections across hours-long tasks or restarts.
  • con: the client must expose a reachable HTTPS endpoint, and the agent now makes outbound requests to caller-chosen URLs, an SSRF surface.

How it works

  • Out of band: the client reads securitySchemes, obtains credentials through the scheme's normal flow (OAuth 2.0 client credentials, authorization code with PKCE, device code, OIDC, mTLS), and sends them as HTTP headers or gRPC metadata. Identity never travels inside A2A message bodies.
  • Server duties: authenticate every request; authorize per skill, action, data and tenant; scope ListTasks and GetTask to the caller before touching storage so other tenants' task ids do not leak.
  • In-task auth: when the agent needs a downstream credential or human approval mid-task, it moves to TASK_STATE_AUTH_REQUIRED with an explanatory status message. Credentials should arrive out of band, directly to the agent; the client may delegate up its own chain.
  • Transport: production requires HTTPS or TLS; clients should validate the server certificate.

Trade-offs

  • pro: reuses existing IdPs, gateways and audit tooling; nothing agent-specific to invent.
  • con: passing credentials in-band through a chain of agents exposes them to every hop; if an extension does it, bind them to the requesting agent and encrypt them.

How it works

  • Impersonation: anyone can publish a card claiming any name. Pin agents by domain allowlist, TLS identity and verified card signatures from keys you trust, not by name or skill text.
  • Cross-agent prompt injection: remote text, files and data parts enter your model's context. A compromised or malicious peer can embed instructions; treat every part as data and gate privileged follow-up actions with guardrails.
  • Data leakage: everything in a Message, including history you forward via a shared contextId, leaves your trust domain. Send the minimum the skill needs; never forward secrets or other users' data.
  • Webhook abuse: agents should reject private, loopback and link-local webhook targets; receivers verify the credential they issued, use one single-purpose token per config and rate-limit.

Trade-offs

  • con: opacity is the point of A2A and also its cost: you cannot inspect the remote agent's tools or prompts, so contracts, evals and logs on your side are the only evidence.

Decision boundary

Use when

  • The callee is an agent owned by another team, vendor or trust domain and must stay opaque.
  • Work is long-running or multi-turn: it may ask questions, need authorization or stream partial artifacts.
  • Several agent frameworks must interoperate without sharing a runtime or codebase.
  • You need discovery: callers pick agents at runtime from cards in a registry.

Skip when

  • The capability is a deterministic function with typed inputs: expose it as a tool or MCP server.
  • All agents live in one process and team: a shared orchestration graph gives typed state and checkpoints without network hops.
  • The peer is a human UI: agent-to-frontend events belong to AG-UI.
  • Latency budgets are tight: each delegation adds a network round trip plus a full remote agent loop.

Worked example

A planner agent delegates a flight booking to a remote travel agent over the v1.0 JSON-RPC binding, using plain httpx. The remote agent stops at TASK_STATE_INPUT_REQUIRED to ask a question; the client answers on the same task until it completes. The token comes from the OAuth flow the card declares; card signature verification is omitted here and belongs in production.

import uuid
import httpx

BASE = "https://travel-agent.example.com"
HEADERS = {"A2A-Version": "1.0", "Authorization": "Bearer ACCESS_TOKEN"}  # token obtained out of band

card = httpx.get(f"{BASE}/.well-known/agent-card.json", timeout=10).raise_for_status().json()
iface = next(i for i in card["supportedInterfaces"]  # ordered by server preference
             if i["protocolBinding"] == "JSONRPC" and i["protocolVersion"] == "1.0")

def send(text, task=None):
    msg = {"messageId": str(uuid.uuid4()), "role": "ROLE_USER", "parts": [{"text": text}]}
    if task:  # continue the same task; contextId must match it
        msg.update(taskId=task["id"], contextId=task["contextId"])
    params = {"message": msg, "configuration": {"acceptedOutputModes": ["text/plain"]}}
    if iface.get("tenant"):
        params["tenant"] = iface["tenant"]
    rpc = {"jsonrpc": "2.0", "id": str(uuid.uuid4()), "method": "SendMessage", "params": params}
    reply = httpx.post(iface["url"], json=rpc, headers=HEADERS, timeout=120).raise_for_status().json()
    if "error" in reply:
        raise RuntimeError(f"A2A {reply['error']['code']}: {reply['error']['message']}")
    return reply["result"]  # exactly one of "task" or "message"

def text_of(parts):
    return " ".join(p["text"] for p in parts if "text" in p)

result = send("Book economy LIS to BER on 12 Nov, under 250 EUR")
task = result.get("task")
while task and task["status"]["state"] == "TASK_STATE_INPUT_REQUIRED":
    question = text_of(task["status"].get("message", {}).get("parts", []))
    result = send(input(f"agent asks: {question}\n> "), task)
    task = result.get("task")

if task is None:  # agent replied with a direct Message, no task
    print(text_of(result["message"]["parts"]))
elif task["status"]["state"] == "TASK_STATE_COMPLETED":
    for art in task.get("artifacts", []):
        print(art.get("name", art["artifactId"]), text_of(art["parts"]))
else:  # AUTH_REQUIRED, FAILED, REJECTED, CANCELED: surface it, do not guess
    print(task["id"], task["status"]["state"])

The default SendMessage blocks until the task is terminal or interrupted, which is why one loop suffices. For work measured in minutes or hours, set returnImmediately: true and add a taskPushNotificationConfig or use SendStreamingMessage, as in the sequence diagram.

Failure modes

  • Version drift · a v0.3 peer expects message/send, kind fields and lowercase states · send A2A-Version and pick the interface whose protocolVersion you implement
  • Treating remote artifacts as instructions · a peer's text lands in your model's context · apply the same injection defenses as for retrieved documents
  • Trusting card names · a look-alike card wins routing on skill text · allowlist domains and verify signatures with keys you control
  • Orphaned tasks · a dropped stream or lost webhook leaves a task WORKING forever on your side · reconcile with GetTask, resubscribe, and CancelTask on timeout
  • Over-sharing context · reusing one contextId across users or forwarding full history leaks data · one context per user conversation, minimal messages
  • Webhook as attack surface · forged or replayed POSTs, SSRF via caller-chosen URLs · verify per-config tokens, dedupe by task and event, block private targets

Keep in mind

  • MCP is agent to tool; A2A is agent to opaque agent; most systems need both.
  • The Agent Card is discovery plus contract: interfaces, capabilities, skills, auth, optional JWS signature.
  • Server owns task ids; clients continue work by echoing taskId and contextId.
  • Interrupted states pause, terminal states are final: four terminal, two interrupted.
  • Poll, stream or webhook: the event shapes are the same StreamResponse.
  • Credentials travel out of band in HTTP auth; remote output is always untrusted data.
