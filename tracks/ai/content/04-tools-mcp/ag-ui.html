AG-UI · generative UI

The agent does not have to answer in prose. It returns UI intent as typed events, and the frontend renders tool calls as live components while the text keeps streaming around them.

Problemchat is a lossy channel
  • Data through a keyhole: the agent has the table, the chart data, the sources. Its only way to show you is prose. Narrating data that could simply be rendered is describing a painting over the phone.
  • Event soup: every backend framework emits its own streaming events, so frontends get rewritten per backend. The N×M matrix again, now between agent engines and UIs.
Solutiona standard event stream, plus tools that render
  • Split the problem: MCP standardizes agent to tools. AG-UI standardizes agent to interface.
  • One alphabet: the backend emits a defined set of events: lifecycle, text deltas, tool-call progress, state sync. Any AG-UI frontend renders any AG-UI backend, and adapters exist for the major agent frameworks.
  • Generative UI is the showstopper: a tool call becomes your React component, mounted mid-answer while text keeps flowing around it. The chat bubble stops being the only thing an agent can draw.

Howthe event alphabet, and how a call becomes a component

the event protocol · one stream, four families

  • Lifecycle: run started / finished / errored. Brackets for everything below. The UI knows when to spin and when to stop.
  • Text message deltas: the model's tokens as they stream from the LLM. The typing effect is literally these events concatenated.
  • Tool-call events: call starts, arguments stream in chunks (they are just tokens, tool calling), result arrives. Show "searching restaurants..." with the query building live, before any result exists.
  • State events: the agent's working state syncs to the frontend as patches. why this matters the UI reflects what the agent knows (form half-filled, filter selected), not just what it says. No re-fetch, no guessing.
// lifecycle brackets the run
{ "type": "RUN_STARTED", "threadId": "t-91" }
// text streams token by token
{ "type": "TEXT_MESSAGE_CONTENT", "messageId": "m-1", "delta": "Revenue is up " }
// a tool call mounts a component · args arrive in chunks
{ "type": "TOOL_CALL_START",  "toolCallId": "c-1", "name": "run_query" }
{ "type": "TOOL_CALL_ARGS",   "toolCallId": "c-1", "delta": "metric='revenue'" }
{ "type": "TOOL_CALL_ARGS",   "toolCallId": "c-1", "delta": " range='q3'" }
{ "type": "TOOL_CALL_RESULT", "toolCallId": "c-1", "content": "92 rows" }
// agent state syncs as patches
{ "type": "STATE_DELTA", "patch": [ { "op": "replace", "path": "filters/quarter", "value": "q3" } ] }
// and it ends
{ "type": "RUN_FINISHED" }

custom component rendering · the flow

  • 1 · Emit: the backend emits typed events and tool-call messages over the one stream. The tool names are the contract.
  • 2 · Map: the frontend keeps a registry from tool call name to component. run_query mounts a Chart, search_docs mounts a SourceList.
  • 3 · Stream: the component renders from arguments while they stream, so the chart builds live, then fills with data when the result arrives.

why tools, not markdown

  • typed a component is typed, styleable and interactive. The model cannot inject prose into your chart axis.
  • gotcha every tool now implies a design decision: loading, empty and error states. A tool that renders badly is worse than a tool that does not render.

Rule of thumb: if the answer is words, render words. If the answer is a thing (a table, a form, an approval), let the tool call be the thing.

Examplea tool call becomes a component
function ToolRenderer({ call }: { call: ToolCall }) {
  switch (call.name) {
    case "run_query":        // args stream in · chart builds live
      return <Chart data={JSON.parse(call.args)} />
    case "search_docs":
      return <SourceList items={call.result?.sources} />
    case "request_approval":
      return <ApprovalCard txn={call.args} />
    default:
      return <InlineTool name={call.name} status={call.status} />
  }
}
// text deltas render as prose · tool calls mount real components mid-stream
  • In-app data analysts stream "querying revenue..." while a live chart mounts mid-answer. The tool call IS the UI event.
  • Support copilots render ticket cards and refund forms inline instead of describing them.
  • Approval cards carry amount, reason and risk with one click to decide. Human in the loop, rendered as UI instead of a yes/no prompt.
  • CopilotKit is the reference stack: AG-UI grew out of its patterns, which is why the event names feel so UI-native.
Pitfallsthe cost side of custom UI
  • Component contract drift: a renamed tool or a changed arg breaks renderers silently. Pin names and schemas, test backend and frontend together.
  • Over-custom UI cost: every bespoke component is design, build and maintenance forever. Ship few, good ones, fall back to InlineTool for the rest.
  • Accessibility: streamed components must be keyboard navigable and announced by screen readers. Loading states need aria-live, charts need text alternatives.
  • Print and export: dynamic UI does not survive paper or PDF by default. Give every component a serialized fallback (the chart plus its data table).
  • The prose lane still leaks: markdown injection from tool output applies to every text delta, see prompt injection.
  • State conflicts: when agent and user edit the same state, last-write-wins bites eventually. Define merge rules before you need them.
Checklist6 things to remember
  • The agent returns UI intent, the frontend owns rendering. Never let the model emit raw HTML.
  • Map tool name to component in one registry, with a default fallback for unknown tools.
  • Design three states per component: loading (args streaming), empty or error, result.
  • Keep the event alphabet small: lifecycle, text message, tool call, state.
  • Sanitize the prose lane, treat tool output as untrusted input.
  • Plan keyboard access, screen readers and print export from day one.
