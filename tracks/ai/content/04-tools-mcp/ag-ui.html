AG-UI · agent-to-frontend events

AG-UI is an event protocol from agent to frontend: text, lifecycle, tool-call and state events. The application maps events to its own components; the protocol prescribes no markup or rendering framework.

In this chapter Read AG-UI as an event protocol between an agent backend and a user interface; separate protocol events from rendering choices.

Why this layer matters

  • Data through a keyhole: tables, charts and sources narrated as prose.
  • Event soup: every agent backend emits its own streaming events.
  • N×M again: each frontend rewritten per backend, per engine.
  • Tool calls are typed: prose is not the only channel worth rendering.

Event flow

Three rendering levels for agent output, cheapest first.

How it works

  • Concatenate text deltas for the typing effect, render markdown in bubbles.
  • Lifecycle events (RUN_STARTED, RUN_FINISHED) drive the spinner.

Trade-offs

  • pro: works with any backend, nothing to design.
  • con: live data gets narrated instead of shown.
  • con: markdown injection from tool output (injection).

How it works

  • An app-owned registry maps a recognized tool name to a local component: run_query selects a Chart renderer.
  • Validated arguments populate it as events arrive (tool calling); the app keeps control of rendering.
  • The result arrives and the component fills with data.

Trade-offs

  • pro: typed, styleable, interactive. The model cannot touch your chart axis.
  • con: every tool implies loading, empty and error design.

How it works

  • Text keeps streaming around mounted component cards.
  • STATE_DELTA patches sync agent state into the frontend, no re-fetch.

Trade-offs

  • pro: explanations and live artifacts in one answer.
  • con: shared state needs merge rules, budget like durable ops.

The event alphabet · four families

  • Lifecycle: run started, finished, errored. Brackets everything.
  • Text deltas: model tokens as they stream from the LLM.
  • Tool-call events: identify calls and may stream arguments before a result exists; an event never authorizes execution.
  • State sync: patches keep the UI aligned with agent state.

AG-UI connects compatible agent backends and frontend adapters; both ends still need matching event support. MCP covers host-client-server integration with tools and data; AG-UI covers agent-to-frontend events.

Decision boundary

Use when

  • Answers carry data users should see live: charts, tables, forms.
  • The agent co-drives the app, filling forms and flipping states.
  • Approvals deserve real cards, not yes/no prompts.
  • Multiple frontends must render one agent backend.

Skip when

  • Words are the product: FAQs, support prose.
  • One backend, one frontend, no sharing pressure.
  • Nobody can maintain component contracts and their states.
  • Print and PDF fidelity matters more than live interaction.

Worked example

Render only a completed, schema-validated local view model; show a loading state while streamed arguments are partial. Events carry arguments, not authorization. A fixed component allowlist owns rendering.

type View =
  | { kind: "chart"; points: Array<{ x: string; y: number }> }
  | { kind: "sources"; items: Source[] }
  | { kind: "approval"; requestId: string };

function ToolRenderer({ call }: { call: ToolCall }) {
  if (call.status === "streaming" || !call.validatedView) return <ToolLoading />;
  const view = call.validatedView as View; // local schema validation completed
  switch (view.kind) {
    case "chart": return <Chart data={view.points} />;
    case "sources": return <SourceList items={view.items} />;
    case "approval": return <ApprovalCard requestId={view.requestId} />;
  }
}
  • In-app analysts: "querying revenue..." streams while a live chart mounts.
  • The approval server authenticates the actor and authorizes the action; a frontend card only displays the request.

Failure modes

  • Contract drift: a renamed tool breaks renderers silently. Pin names, test both ends.
  • Cost: every bespoke component is design and maintenance forever. Ship few.
  • Accessibility: aria-live for loading states, text alternatives for charts.
  • Print: give every component a serialized fallback for paper and PDF.
  • Prose lane leaks: sanitize markdown from tool output (injection).

Keep in mind

  • The protocol carries events; the frontend owns rendering. Validate event data, never run model-supplied markup as trusted UI.
  • One registry maps tool name to component, with a default fallback.
  • Design three states per component: loading, empty or error, result.
  • Keep the alphabet small: lifecycle, text, tool calls, state.
  • Sanitize the prose lane, tool output is untrusted input.
