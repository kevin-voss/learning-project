MCP · Model Context Protocol

MCP is an open protocol that connects AI apps to tools and data. Write the server once, every client gains it, and the tool menu builds itself at runtime from what the server reports.

Problemthe N×M integration matrix
  • Math first: M apps × N tools = M×N bespoke integrations to write, test and maintain forever.
  • Plugin sprawl: each app grew its own plugin language, so tool builders wrote the same tool five ways.
  • A REST endpoint describes nothing to a model: schema, usage notes and auth story live in human docs the model cannot browse.
  • Famous precedent: editors × languages had the same matrix until turned it into M+N.
Solutionone protocol, self-describing servers
  • Open protocol: your app is a host that runs one MCP client per server. Servers expose tools, resources and prompts over one standard wire.
  • The wire: , implementable in any language, no vendor SDK favored.
  • Decisive feature: servers describe themselves at runtime. The client calls tools/list and menus plus schemas build themselves from the response.
  • Build once, plug into every client: Claude Desktop, Cursor, goose, your own agents. The matrix collapses to N+M.
  • Ecosystem: a public server registry is emerging under the Linux Foundation's Agentic AI Foundation. Npm, but for tools.

Howwire · flow · transports · primitives · vs plain HTTP · Inspector

the wire · one JSON-RPC envelope

  • Requests: method + params + id, and a result is expected back.
  • Notifications: no id, fire and forget. How servers announce "my tool list changed".
  • why JSON-RPC language-neutral, tiny, structured error codes, boring on purpose.

the flow · handshake, discover, call, execute

  • 1 · Handshake: connect, then initialize. Both sides exchange protocol version and capabilities ("I support tools, resources, sampling, elicitation").
  • 2 · Discover: the client calls tools/list and receives names, JSON schemas and descriptions written for a model to read.
  • 3 · Call: the model picks a tool through the tool calling contract, the client sends tools/call with arguments.
  • 4 · Execute: the server does the real work and returns a result (or a structured error) the model consumes.
  • why negotiation is the killer feature the interface is discovered at runtime, not wired at build time. Add a tool server-side, every connected client sees it on the next tools/list. Compare OpenAPI: a static document hand-wired into one app, drifting the moment the server changes.

transports · stdio and streamable HTTP

  • stdio: the host spawns a local subprocess, JSON-RPC flows over stdin/stdout. Zero network, fastest loop, ideal for filesystem, shell and dev DB.
  • gotcha stdout IS the wire. A stray print() corrupts the stream and the whole server hangs. Log to stderr, always. The Inspector makes this visible in seconds.
  • Streamable HTTP: POST JSON-RPC, optionally receive an SSE stream back for results and notifications. Sessions and resumable streams survive network blips. Replaced the older dual HTTP+SSE setup.
  • why two transports a local tool should never touch the network (attack surface, latency, auth). SaaS tools must be reachable over HTTP. One message format normalizes both.

the three primitives · the axis is who initiates

  • Tools (model-controlled): functions with schemas, can have side effects, need approval UX. The tool calling contract, standardized.
  • Resources (app/user-controlled): readable data. Files, rows, schemas. Think GET, no side effects, the UI lists them.
  • Prompts (user-controlled): parameterized templates servers ship, your /slash commands, reusable across clients.

beyond calls · sampling, roots, elicitation

  • Sampling: the server asks the client's LLM to complete a prompt. Server authors ship AI behavior without hardcoding a vendor key, with a consent gate in the host.
  • Roots: the client tells the server which directories it may care about. Scope, not trust.
  • Elicitation: mid-operation the server asks the user a structured question through the client ("which workspace?").

mcp vs "just call my REST API"

plain HTTP / REST

  • A transport: verbs, URLs, status codes. Says nothing about what an endpoint does.
  • Primary consumer is a developer reading docs and writing code.
  • Discovery: static OpenAPI wired per-app at build time, docs drift.
  • Auth: per-vendor keys, hand-rolled per app.
  • Request and response, client-initiated only. SSE bolted on with per-service conventions.

MCP

  • An application protocol: defined methods, capabilities, a lifecycle. Runs over HTTP or stdio.
  • Primary consumer is a model. Schemas and descriptions written to be read by an LLM.
  • Discovery: tools/list at runtime, always current, the UI builds itself.
  • Auth: standardized OAuth 2.1, implemented once per client.
  • Bidirectional sessions: notifications plus server-to-client requests (sampling, elicitation). Streaming built in, with session resume.

The punchline: MCP is not "instead of HTTP". It is an app layer on top of HTTP or stdio, the way LSP sits on stdio. If only your own code calls your endpoint, REST is right. When the consumer is a model, or many apps must share your tools, the standard wins outright.

mcp inspector · your first stop

  • What: the official local web UI that connects to any MCP server over any transport. Drive your server standalone before wiring it into Claude Desktop, Cursor or goose.
  • Browse tools, resources, prompts with forms auto-generated from their JSON schemas. Invoke with real inputs, schema typos surface in seconds, not as mystery client failures.
  • Raw JSON-RPC traffic log: every request, notification and error in order. The stray print() corrupting stdio is visible here immediately.
  • Test OAuth flows for remote servers, plus sampling and elicitation callbacks.
  • why it matters debugging through a client multiplies suspects (their bug? my schema? the wire?). The Inspector removes the client from the question.

Examplea server in 12 lines, and debugging it in 1
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("tools")   # one server · every MCP client can use it

@mcp.tool()
def get_weather(city: str) -> str:
    """Current weather for a city."""       # the docstring IS the description
    return fetch_weather(city)          # your real logic

@mcp.resource("docs://api")
def api_docs() -> str:
    return open("API.md").read()        # readable data, not callable

mcp.run()   # stdio locally · streamable HTTP for remote clients
# fire up the Inspector against any server · a web UI opens locally
npx @modelcontextprotocol/inspector python fastmcp_server.py

Pitfallsa remote server is remote code influence
  • Trust decision, not a config line: whoever runs the server shapes what your model sees and does. Connecting to a remote server hands over influence, scope it like any dependency.
  • Auth: remote MCP uses OAuth 2.1 (authorization code + PKCE, dynamic client registration, resource indicators). Keys authenticate a developer, OAuth grants a user's consent per app with scopes and revocable tokens.
  • Audit what servers expose: servers hold the keys, scope them hard. An over-exposed server (drop table next to read row) is one confused model away from damage.
  • Prompt injection via content: resources and tool results are untrusted input. A poisoned file or row can steer the model, see prompt injection.
  • stdio corruption: any stray stdout write breaks the wire, including prints from third-party libraries.
  • Protocol overhead: handshake, listing and JSON-RPC envelopes cost latency. Keep high-frequency inner loops as native calls, budget them like any ops dependency.
  • Version drift: client and server negotiate a protocol version, capability gaps still bite (old client, new tool semantics).
Checklist7 things to remember
  • M×N collapses to N+M: one server, every client. That is the whole pitch.
  • Pick the primitive by who initiates: tools model, resources app, prompts user.
  • Handshake first: initialize, exchange capabilities, then tools/list, then call.
  • stdio means stdout is the wire. Logging goes to stderr, always.
  • Debug in the Inspector before blaming the client.
  • Remote servers get OAuth, rate limits and audit logs. Treat them as web services.
  • Treat tool and resource output as untrusted input.
