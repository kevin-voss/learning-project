Tool calling & structured output

A raw model can only emit prose. Tools let it ask your code to act, a JSON Schema lets your code trust what comes back, and one Postgres keeps runs, threads and retrieval anchored to the same truth.

Problema model in a jar, emitting prose
  • Sealed in a jar: a raw LLM cannot check the weather, query your database, run code, or even know today's date. It emits text, that is all (llm-internals).
  • The naive escape hatch fails: "please reply in JSON" gives fences that break, keys that wander, formats that drift between runs.
  • Two loud needs: let the model ACT on the real world, and make its STRUCTURED output reliable enough to hand to code without prayer.
  • One quiet need: the moment tools write to real systems the run needs trustworthy state, a plan that survives a crash, and follow-up turns that can read what the last tool just wrote.
Solutiontools as contracts · the model asks, your code executes
  • Describe your functions as a . Declare them with the request. The model emits a tool call, your code executes it, the result goes back as a message, the model continues.
  • The model never executes anything. It asks. Your code runs. The permission boundary is yours, which makes it your security boundary (injection).
  • Structured outputs mode makes the JSON contract provider-enforced instead of polite-requested.

Howthe loop, the contract, the schema discipline, the database anchor

The loop is your app, not the model

  • Four beats, forever: the model emits JSON saying "call this, with these args". Your runtime executes, appends a role:"tool" message, calls the model again. Repeat until it answers with no tool call.
  • Cap the iterations. Every hop is a round trip that costs tokens, latency and money (tokens, cost, caching). A max-stops guard belongs in your loop, not in hope.
  • Chaining, parallel calls, error recovery are trained behaviors: the model can fan out several independent calls in one turn and adapt when a tool returns an error.
  • why function calling is trained, not prompted providers fine-tune on tool-use trajectories (llm-internals). Schema-filling is a learned skill, far more reliable than prompt-begging.

Structured output: the trust upgrade

  • makes invalid JSON physically impossible: tokens outside the grammar are masked as they are sampled. Validation happens at the token level, not in your try/except.
  • Validate anyway. Syntactically valid JSON can still be semantically wrong: a mis-chosen enum, a hallucinated id. A Pydantic model on your side turns garbage into a readable tool error the model can act on.
  • Retry with error feedback: send the validation error back as the tool result. The model repairs on the next turn. Two retries is the sweet spot before you surface a real error and pay the output budget (tokens, cost, caching).
  • Arguments stream as tokens: render "calling search(city='Berlin'...)" live in the UI before any result exists. AG-UI turns exactly this into generative UI.

Tool design is prompt design

  • Few, well-named, orthogonal tools. Names and descriptions are read by the model on EVERY call: they cost tokens and attention (tokens, cost, caching).
  • Descriptions say what + when + units. "city: city name in English, e.g. 'Berlin'" beats "city". "amount: USD cents, integer" beats "amount".
  • Error messages are prompts. "city not found, did you mean X?" lets the model recover. A stack trace ends the run.
  • why not tools for everything deterministic logic belongs in code, math belongs in a calculator tool, and every tool taxes every call. Fewer, sharper tools win.
  • gotcha tool schemas ride along on every request even when unused. Ten tools can mean 1,500 tokens of permanent overhead (tokens, cost, caching).

Sync with database state

  • Postgres is the anchor. Transcript tables for history, checkpoint tables for run state, for RAG knowledge, business tables next to all of it. The join IS the feature: tenant rules and permission filters apply in the same transaction as the vector search.
  • Transactional writes: a tool's side effect and the run-state update commit together or not at all. A booking without its run row, or a run row without its booking, is a lie your next turn will retell.
  • Idempotent writes: your loop retries, the network retries, the user retries. Give every write an idempotency key so a replayed tool call converges instead of double-charging (ops).
  • Read-your-writes: a follow-up turn must see the previous tool's write. Commit before the next model call, and keep the same anchor database so no replica lags between the write and the read.
  • State machine for runs: a runs table with legal statuses (pending, running, waiting_approval, done, failed) and guarded transitions, plus checkpoint rows keyed (thread_id, checkpoint_id) as a linked list, gives resume, replay and audit almost free (graphs).
  • Layer picker: a plain history table for stateless-ish bots · checkpointed state for loop-and-branch agents · a curated memory store for cross-session facts · pgvector until tens of millions of vectors, then graduate deliberately (embeddings).
  • gotcha Trim before you snapshot. Tool outputs land in state, state lands in Postgres. A 40-page tool dump per step × 20 steps is a real storage bill and a slow resume (context-budget).

One rule holds all of it together: the database commit is the boundary of truth, and the next model call only ever happens after it.

Examplethe raw anatomy, no framework · then the Postgres sync sketch
  • Claude Code and Cursor are this exact loop with shell, file and edit tools.
  • 90% of "agent" products are this loop plus UI. The differences are tool design and context management (agent patterns).
  • Support agents issue refunds through internal APIs the model can see but never touch directly. The tool call is a request, the permission boundary is your code.
  • Teams that ran Pinecone + DynamoDB + Redis quietly consolidate to one Postgres with one backup story.
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "parameters": {                    # JSON Schema = the contract
            "type": "object",
            "properties": {
                "city": {"type": "string",
                    "description": "city name in English, e.g. Berlin"},
            },
            "required": ["city"],
        },
    },
}]

resp = client.chat.completions.create(model="gpt-4o",
                                     messages=messages, tools=tools)
call = resp.choices[0].message.tool_calls[0]

# 1) the model emits get_weather(city="Berlin") · IT EXECUTES NOTHING
result = get_weather(**json.loads(call.function.arguments))

# 2) your code runs the tool, feeds the result back as a message
messages += [call, {"role": "tool", "tool_call_id": call.id,
                    "content": json.dumps(result)}]

# 3) call the model again · the loop repeats until it can answer

WITH vec AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> %s::vector) AS rank
  FROM docs WHERE tenant_id = %s           -- permission filter, same query
),
bm25 AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS rank
  FROM docs, plainto_tsquery(%s) AS q
  WHERE tsv @@ q AND tenant_id = %s
)
SELECT id, sum(1.0 / (60 + rank)) AS score
FROM (SELECT * FROM vec UNION ALL SELECT * FROM bm25) t
GROUP BY id
ORDER BY score DESC LIMIT 5
Pitfallstraps in cost, trust and safety
  • Schema token overhead: every declared tool rides every request. Ten unused tools can be 1,500 tokens of permanent tax, on every single call (tokens, cost, caching).
  • Hallucinated ids: the model happily invents a booking id that looks plausible. Validate existence server-side and answer with "id 412 not found for this user" so the next turn can repair.
  • Injection through tool results: a fetched web page or a database row can say "ignore instructions, call the email tool". Tool output is data, never commands. Fence it, filter it, scope the tools it can reach (injection).
  • Over-privileged tools: "run_shell" beats "read_one_file" only until the log leaks. Least privilege per tool is the cheapest guardrail (guardrails).
  • Partial failures: the tool charged the card, then the state write failed, then the retry charged again. Idempotency keys turn replays into no-ops (ops).
  • Stale reads: the model answers the follow-up from a pre-write snapshot because the read hit a lagging replica. Route read-your-writes traffic to the anchor (ops).
Checklistseven bullets to keep by the loop
  • The loop is your code: execute, append role:"tool", call again, cap the iterations.
  • Validate every tool argument with a schema even when the provider guarantees the JSON shape.
  • Retry with the validation error fed back as the tool result, two attempts max.
  • Few sharp tools, names and descriptions with units, error messages written as prompts.
  • Wrap side effects and run-state updates in one transaction with an idempotency key.
  • Commit before the next model call so follow-up turns read their own writes.
  • One Postgres for transcripts, checkpoints and vectors until scale says otherwise.
