Tool calling & structured output

A model proposes a tool call or structured value. Your application validates shape and meaning, checks authorization, then decides whether to act; schemas grant no trust or permissions.

In this chapter Follow the complete model-propose, application-validate, authorize, execute and return loop; distinguish schema validity from business safety.

Why this layer matters

  • Sealed: a raw LLM emits text only, it cannot act or fetch anything (llm-internals).
  • Polite JSON fails: "reply in JSON" drifts, fences break, parsers crash.
  • Act: tools let the model request real side effects via your code.
  • Structure: schema-constrained output reduces shape errors; the application still validates semantics and authorization.

Execution protocol

Four mechanisms, weakest to strongest, the last one for sharing tools across apps.

How it works

  • Prompt says "reply in JSON only", then parse what comes back.
  • Fine for scripts, internal tools, low-stakes one-offs.
  • Expect fences, drifting keys, format changes. Validate with Pydantic, retry with the error fed back.

How it works

  • Declare functions as a with the request. The model emits a tool call.
  • A tool call is a proposal, not execution. Your app validates, authorizes, executes, then returns the result in that API’s message format. Cap hops (graphs).
  • Trained, not prompted: parallel calls, chaining, error recovery come from fine-tuning (llm-internals).

Tool design is prompt design

  • Few, orthogonal tools. Ten unused schemas ≈ 1,500 tokens on every request (tokens, cost).
  • Descriptions say what + when + units: "amount: USD cents, integer".
  • Errors are prompts: "city not found, did you mean X?" recovers the run.
  • The permission boundary is your code. Scope tools like APIs (injection).

How it works

  • : tokens outside the schema grammar are masked while sampling.
  • The guarantee is syntactic. Validate semantics anyway: wrong enums, hallucinated ids.
  • Retry with the validation error as the tool result, two attempts max.
  • Keep schemas small, giant schemas slow the model. Skip for creative prose.

How it works

  • One MCP server exposes tools to any client: Claude, Cursor, your app.
  • Use when tools are shared across apps, teams or machines.
  • Costs one extra protocol hop. Audit what remote servers expose.

Decision boundary

Use when

  • Downstream code must parse the output, pick B or C.
  • The task needs real actions: queries, writes, API calls.
  • Streaming tool args should render live in the UI (ag-ui).
  • Several apps must share one tool surface, pick D.

Skip when

  • Plain prose answers suffice, nothing parses them.
  • Creative writing, schema constraints hurt fluency.
  • Single app, single machine, plain functions win.
  • Deterministic logic or math, that belongs in code.

Worked example

Illustrative Chat Completions loop using a supported model. The app executes validated calls; the model only proposes them. Responses API has a different message shape (agent patterns).

tools = [{"type": "function", "function": {
    "name": "get_weather",
    "parameters": {              # JSON Schema = the contract
        "type": "object",
        "properties": {"city": {"type": "string",
            "description": "city name in English, e.g. Berlin"}},
        "required": ["city"],
    }}}]

for _ in range(MAX_TOOL_ROUNDS):
    response = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
    assistant = response.choices[0].message
    messages.append(assistant)  # includes tool_calls; preserve assistant role/message shape
    if not assistant.tool_calls:
        break
    for call in assistant.tool_calls:  # zero, one, or many proposals
        args = json.loads(call.function.arguments)
        if call.function.name != "get_weather":
            raise ValueError("unsupported tool")
        validated = WeatherArgs.model_validate(args)  # validate before dispatch
        result = get_weather(city=validated.city)  # server-side implementation
        messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})
else:
    raise RuntimeError("tool round limit reached")

Failure modes

  • Schema tax: every declared tool rides every request, used or not (tokens, cost).
  • Hallucinated ids: validate existence server-side, answer "id 412 not found".
  • Tool results can inject: a fetched page may order new calls (injection).
  • Over-privileged tools: prefer read_one_file over run_shell (guardrails).
  • Partial failure: charge lands, state write dies, retry double-charges (ops).

Keep in mind

  • The loop is your app: execute, append role:"tool", call again, cap iterations.
  • Validate every argument server-side, even under schema mode.
  • Few sharp tools, units in descriptions, error messages written as prompts.
  • Commit before the next model call, so follow-ups read their own writes.

Sync with database state

Once tools write, runs need durable state. One Postgres anchors transcripts, checkpoints and retrieval, and the commit is the boundary of truth.

Transactional writes

  • Side effect and run-state update commit together or not at all.
  • Idempotency key per tool call: replays converge, nothing double-charges (ops).
  • Read-your-writes: commit before the next model call, read from the anchor.
  • Runs state machine: pending, running, waiting_approval, done, failed (graphs).

One anchor database

  • Transcripts, checkpoints, and business tables, one backup story (embeddings).
  • Tenant and permission filters apply in the same transaction as the vector search.
  • Checkpoint rows keyed by run/thread and checkpoint id support resume and audit, at real storage, consistency and retention cost.
  • Trim tool outputs before snapshotting state, or resume gets slow (context-budget).
