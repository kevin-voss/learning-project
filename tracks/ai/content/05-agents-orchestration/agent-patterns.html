Agent patterns

A chain runs a fixed sequence of prompts you wrote. An agent runs a goal: a loop that thinks, acts through tools, observes results and decides the next step itself. Extra agents are a team you may not need. This page is the ladder up, the handoff mechanics, and the honest reasons to climb.

Problemone call cannot do a job
  • "Research this market and write a brief" is steps, decisions, retries and memory. One prompt either stuffs everything into one shot or overflows the window.
  • Context landfill: after 40 tool calls the transcript is a swamp of stale results and the model's attention drowns in its own history (context budget).
  • The real problem: run a GOAL, not a prompt. Over steps, with memory, and without one polluted window.
Solutiona loop first, then (only if earned) a team
  • An agent is an LLM in a loop with tools and a goal: think, act, observe, repeat until done. The pattern.
  • Chain vs agent is where control flow lives. A chain is a flowchart you drew before runtime. An agent picks the next step at runtime from what it just observed. If you can draw the whole flowchart in advance, it is a chain and that is fine.
  • Five escalation patterns exist, from one intern with a toolbox to teams with managers.
  • Rule zero: start single-agent. Every extra agent is a distributed-systems bug you chose to have. Escalate only when you can name what you are buying.

The escalation ladder. Go one rung up only when the rung below measurably hurts.

Howeach rung, handoffs, and the only three real reasons to go multi

the ladder, honestly

  • Single + tools: one model, one context, N tools. Cheap, debuggable, surprisingly far. Most "multi-agent" products are this wearing a costume.
  • Router: classify once, dispatch to specialist prompts. The cheapest real "multi" pattern. gotcha router mistakes are silent. Log the route with every answer.
  • Supervisor and workers: a manager plans, delegates, merges, iterates. For big parallelizable jobs. why it helps the manager's context stays clean while workers absorb the noise.
  • Planner and executor: worth naming on its own. The planner emits an explicit plan (an inspectable list of steps), the executor works through it, failures trigger replanning. The plan artifact is what makes this auditable, see graphs.
  • Hierarchical: managers of managers. Only for genuinely wide pipelines. Coordination cost compounds per layer, errors get fuzzy far from home.
  • Swarm: peer handoffs with shared state, no central brain. gotcha A to B back to A loops need a circuit breaker, see ops.

handoffs: context transfer between agents

  • A handoff is one agent delegating ownership to another mid-journey. Support is the canonical shape: a triage agent hands a billing case to the billing specialist instead of pretending to be every specialist at once.
  • What travels: a task summary, distilled artifacts (ids, documents, amounts), decisions already made, constraints (policy, deadline, tone) and the requested next step.
  • What never travels: the full transcript. Forwarding raw history re-creates the context landfill you isolated to avoid (context budget).
  • Mechanics: the handoff is a structured message with a schema, shaped exactly like a tool call. "transfer to billing" is a tool whose payload is the brief, see tool calling.
  • What comes back: the result plus a short trail of what was done, so the delegating agent can answer the user without re-asking anything.
  • gotcha information loss compounds per hop. If the receiving agent re-asks the user for facts the last agent already knew, the handoff schema is too thin.

the only three real reasons to go multi-agent

  • 1 Context isolation: each subagent starts with a clean window and returns only the result. Hiring a contractor instead of reading every book yourself.
  • 2 Parallelism: genuinely independent subtasks. Five competitors researched at once, 50 eval cases run at once (evals).
  • 3 Conflicting tool sets or models per role: a read-only researcher and a write-enabled fixer should not share one toolbox or one prompt. A cheap model for breadth and a strong model for the merge is the same argument.

what it costs (the part vendors skip)

  • Token amplification: every hop re-describes the world. Worker briefs, handoffs, merges: tokens again and again (tokens & cost).
  • Error multiplication: the run is only as good as the product of its agents. Five agents at 95% each land near 77% end to end. Failures become archaeology instead of debugging.
  • Latency stacks: plan, delegate, wait, merge is the slow path through chat UX.
  • Budget enforcement across a team (steps, dollars, circuit breakers) is covered in ops.

Examplethe whole agent in 12 lines, then a real handoff
def run_agent(goal, tools, max_steps=25):
    state = {"goal": goal, "history": []}
    for step in range(max_steps):            # budget enforced here, not in hope
        reply = llm(state, tools)                   # thinks, may request tool calls
        if not reply.tool_calls:                        # no tool asked: done is the answer
            return reply.text
        state["history"].append(run_tools(reply.tool_calls))
    raise BudgetExceeded("max steps hit, goal not met")
  • Loop, tools, goal, stop condition. That is the entire agent. Everything else on this page is escalation. Tool call shapes live in tool calling, durable versions of this loop in graphs.

  • In the wild: Claude Code and Cursor are a single agent with a fat toolbox, proof the single lane goes far. Deep-research assistants are a supervisor with parallel workers. Support copilots are router plus handoffs across billing, support and sales.
  • Bullshit detector: for each extra agent in a design, name which of the three reasons it serves. Anything else is theater and token burn.
Pitfallstheater, amnesia, ping-pong
  • Multi-agent theater: extra agents serving none of the three reasons. You pay latency and tokens for a diagram.
  • Handoff amnesia: forwarding the raw transcript (landfill moves house) or nothing (user repeats themselves). Send summary plus artifacts.
  • Micromanaging supervisors: a manager that re-reads every worker output gains zero isolation and doubles the tokens.
  • Ping-pong loops: agents handing back and forth forever. Cap handoffs per run like any other budget, see ops.
  • Router drift: silent misroutes with no logging. Untraceable a week later.
  • Non-determinism squared: more agents, more branches. Trace every run or debugging is archaeology (evals).
Checklistsix bullets to remember
  • Start single agent with good tools, escalate only with a named reason
  • An agent is loop + tools + goal, with a stop condition and a budget
  • Handoffs carry summary + artifacts + constraints, never full history
  • Log every route and every handoff alongside the answer
  • Parallel fan-out only for genuinely independent subtasks
  • Isolation, parallelism, conflicting tools or models: any other reason is hype
