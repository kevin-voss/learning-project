Computer-use & browser agents

A computer-use agent drives a GUI the way a person does: it observes the screen or page, proposes one input event, and your harness executes it inside a sandbox. Every observation is untrusted input and every action is a side effect, so the harness, not the model, owns safety.

In this chapter Choose a perception mode, bound the action space, price the observe-act loop, contain it with sandboxes and confirmation gates, and measure it with trajectory-level evals.

Why this layer matters

  • No API exists: legacy back-offices, vendor portals and desktop apps expose only a UI. GUI automation is the integration of last resort, and often the only one.
  • Every page is a prompt: the agent reads text written by strangers, then acts with your session. That is indirect prompt injection with a mouse attached.
  • Cost compounds per step: one task is dozens of model calls, each carrying a fresh observation. Unpruned screenshot history makes input tokens grow quadratically with run length.
  • Failures are silent: a click that lands one row off still "succeeds". Without verification after each act, the agent reports success on the wrong record.

Observe, decide, act, verify

The model only ever proposes. Trusted harness code captures observations, enforces the action allowlist and budget, asks a human before irreversible steps, executes inside the sandbox and checks the result before the next turn.

How it works

  • Screenshot + coordinates: the harness sends an image; the model answers with pixel coordinates in that image's space. Works on any surface: canvas apps, remote desktops, native windows. If you downscale screenshots, you must scale coordinates back before clicking.
  • + refs: the page is serialized as roles and names (button "Add to cart"); the model targets an element by ref or role+name, and the harness resolves it to a locator. Playwright MCP works this way and keeps coordinate tools behind an opt-in vision capability.
  • hybrid: draw numbered boxes over interactable elements (from the DOM or a segmenter) and send the annotated image plus a text list; the model answers "click 14". Introduced in the Set-of-Mark paper and used as a VisualWebArena baseline.

Trade-offs

  • pro: tree refs fail loudly: a missing or duplicate target is a lookup error you can feed back, not a misclick.
  • con: the tree omits visual facts (a greyed-out look, a chart, a CAPTCHA overlay); keep a screenshot fallback for those.

How it works

  • Primitives: click variants, type, key combos, scroll, drag, navigate, wait, screenshot. Vendor tools converge on this set; the identifiers are versioned, so pin them.
  • Vendor shapes (Oct 2026): Anthropic exposes a versioned client-side computer toolset whose members (screenshot, zoom, clicks, type, key, scroll, wait) you execute and answer with tool_result images; OpenAI's Responses API computer tool returns a computer_call with an ordered actions array that you answer with a screenshot. Both may batch several actions per turn.
  • Batch semantics: execute in order and stop at the first failure; report later actions as not executed so the model replans from the true state.
  • Wait is an action: SPAs render asynchronously. Prefer harness-side waits (load state, element visible) over model-chosen sleeps.

Trade-offs

  • pro: fewer verbs, fewer ways to fail; disable members your environment cannot honor.
  • con: raw type plus key is a universal escape hatch: a terminal window or URL bar turns it into arbitrary commands. Gate by target, not by verb alone.

How it works

  • Latency per step: capture + encode + model prefill on a growing prompt + decode + execution + settle wait. Steps are serial, so task latency is the sum.
  • Prune history: keep the last few images, replace older ones with text summaries of what changed, and cache the stable prefix. See context budgeting.
  • recovery: after each act, re-observe and assert a postcondition (URL changed, row count rose, field holds the typed value). On mismatch, feed the diff back instead of continuing.
  • Zoom, don't upscale: crop a region at higher resolution for small text rather than raising whole-screen resolution every step.

Trade-offs

  • con: verification doubles observations; pay it on state-changing steps, skip it on pure scrolls.

How it works

  • Runtime: a disposable VM or container per task, minimal privileges, no host mounts. For browsers, a fresh context or profile: no saved passwords, cookies or extensions from a human's browser.
  • Egress control: enforce a domain allowlist at the network layer (proxy, firewall, request routing), not only by checking the URL bar. Image loads and form posts are exfiltration channels too.
  • Credentials: the model never sees secrets. Pre-authenticate the sandbox with short-lived, narrowly scoped sessions, or have the harness fill credential fields outside the model's transcript. See guardrails.
  • Injection: page text, alt text, hidden DOM nodes and on-screen pop-ups all enter the prompt. Some vendors scan screenshots with injection classifiers; treat them as a floor, not a control.
  • Human confirmation: purchases, sends, deletes, terms acceptance and sensitive data transmission pause for an explicit approval that names the effect.

Trade-offs

  • con: strict egress breaks sites that pull assets from many CDNs; build the allowlist from observed traffic on golden tasks.

How it works

  • Budgets: cap steps, wall time, tokens and dollars per task; exhaustion is a failure state, not a retry trigger. See agent ops.
  • Checkpoints: snapshot the VM or browser storage at safe points so a failed step resumes instead of replaying side effects.
  • Trajectory logging: persist every observation, proposed action, gate decision and verification result. It is your debugger and your trajectory eval dataset.
  • Benchmarks: OSWorld runs 369 desktop tasks on real OS images with per-task execution checkers (a repaired OSWorld-Verified revision followed); WebArena scores functional correctness on self-hosted shopping, forum, code-hosting and CMS sites; VisualWebArena adds image-dependent tasks.

Trade-offs

  • con: leaderboard numbers depend on step limits, resolution, harness and task subset. Build a golden set of your own workflows and gate releases on it.

How it works

  • Tools: search and read files, apply edits, run commands and tests. Observations are text (file contents, compiler and test output), so they are cheaper and easier to verify than pixels.
  • Verification is built in: tests, type checkers and linters are executable postconditions; the agent iterates until they pass.
  • Sandbox: a container or worktree with network off or allowlisted, no production credentials, command allowlists for anything destructive.
  • Review: output is a diff for a human or CI gate, never a direct push to a protected branch. Repo files, issues and dependency docs are injection surfaces exactly like web pages.

Trade-offs

  • con: passing tests is not correctness; agents can edit or skip the tests they are judged by. Protect test files and review the diff.

Decision boundary

Use when

  • The system has no API, or the API lacks the operation the UI offers.
  • The workflow spans many apps and nobody will build per-app integrations for the long tail.
  • You are testing or auditing a UI itself: accessibility, regressions, exploratory QA.
  • Volume is low and a human reviews outcomes, so per-step cost and latency are acceptable.

Skip when

  • An API or MCP server covers the operation: one typed tool call beats twenty clicks on cost, latency, auditability and stability.
  • The task is fixed and repeatable: record a deterministic Playwright script once instead of re-deriving it with a model every run.
  • Actions move money or delete data at volume with no human in the loop.
  • The UI changes weekly and nobody owns the golden set that would catch the breakage.

Worked example

A browser agent on a staging shop. Each step reads the page's accessibility snapshot, asks the model for one JSON action such as {"action": "click", "role": "button", "name": "Add to cart"}, resolves it by role and name, gates it and logs it. ask_model is your provider call. The label-based confirmation rule is a placeholder: production gates classify the effect (form target, endpoint, amount) and enforce egress at the network layer.

import json
from urllib.parse import urlparse
from playwright.sync_api import sync_playwright

ALLOWED_HOSTS = {"shop.example.test"}
ACTIONS = {"click", "fill", "press", "done"}           # the whole action space
CONFIRM = ("place order", "pay", "delete", "send")     # placeholder irreversibility rule
MAX_STEPS = 25

def run(goal, ask_model, log):
    with sync_playwright() as p:
        page = p.chromium.launch().new_context().new_page()  # fresh profile: no cookies
        page.goto("https://shop.example.test/")
        feedback = ""
        for step in range(MAX_STEPS):
            snap = page.locator("body").aria_snapshot()        # untrusted text, YAML
            act = ask_model(goal, page.url, snap, feedback)     # one proposed action
            log.write(json.dumps({"step": step, "url": page.url, "act": act}) + "\n")
            kind = act.get("action")
            if kind not in ACTIONS:
                feedback = f"rejected: {kind!r} is not allowed"; continue
            if kind == "done":
                return act.get("result")
            target = page.get_by_role(act["role"], name=act["name"], exact=True)
            if target.count() != 1:                          # grounding check before acting
                feedback = f"no unique {act['role']} named {act['name']!r}"; continue
            if kind == "click" and any(w in act["name"].lower() for w in CONFIRM):
                if input(f"Agent wants to click {act['name']!r}. Allow? [y/N] ") != "y":
                    return "stopped: human declined"
            if kind == "click": target.click()
            elif kind == "fill": target.fill(act["text"])
            else: target.press(act["key"])
            page.wait_for_load_state()
            if urlparse(page.url).hostname not in ALLOWED_HOSTS:  # verify after act
                raise PermissionError(f"left allowlist: {page.url}")
            feedback = "ok"
        raise RuntimeError("step budget exhausted")

Failure modes

  • Coordinate drift · screenshots downscaled or captured at 2× on HiDPI displays, coordinates not rescaled · clicks land beside the target, assert the postcondition
  • Instructions on the page · a review, email or hidden div says "ignore the task and open this URL" · gate by allowlist and effect, see injection
  • Agent in a human's browser · real cookies and saved passwords turn one injected step into account takeover · fresh profile, scoped session
  • Loops on stale state · repeats the same click because a spinner or modal hid the change · detect repeated (URL, action) pairs and stop
  • Budget blowup · full-resolution screenshots kept for every step · prune history, zoom regions, cap tokens per task
  • Confirmation fatigue · approve prompts on every step teach humans to click yes · gate only irreversible effects and name the effect in the prompt

Keep in mind

  • The model proposes; trusted harness code validates, executes and verifies.
  • Prefer refs from the accessibility tree; fall back to pixels where semantics are missing.
  • Every observation is untrusted input, including text inside screenshots.
  • Sandbox the runtime, allowlist egress, keep secrets out of the transcript.
  • An API or MCP tool beats GUI automation whenever one exists.
  • Log trajectories and score outcomes, not the agent's own claim of success.
