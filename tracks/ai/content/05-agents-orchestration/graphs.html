Orchestration graphs

A while-loop with an LLM inside is an agent engine nobody can see, resume or replay. An orchestration graph makes the control flow a first-class artifact: named nodes, explicit edges, state that flows through, a snapshot after every step. LangGraph is the reference shape, the concept is the point.

Problemthe hidden loop is invisible and fragile
  • Control flow buried in code: the real flowchart hides inside nested ifs, retry flags and while-loops. Nobody can review it, draw it or test it as a whole.
  • Crashes: a 20-minute research run dies at minute 17 (deploy, OOM, spot kill). Plan, tool results and draft lived in RAM. Gone.
  • Humans in the loop: a refund approval needs the run to pause for hours, then continue exactly where it stopped.
  • No replay: "why did it take that branch?" is answered by re-reading logs and guessing, if you logged at all.
  • The pattern: an agent workflow is long-running, stateful, branchy and failure-prone. The exact trifecta request/response code handles worst.
Solutionmake the control flow an explicit graph
  • A graph is a named set of nodes (functions) plus edges (who runs next) plus one state object, driven by an engine that ticks, snapshots and routes. The loop you would have written anyway, admitted and named.
  • Every orchestration composes from five shapes: chain (step after step), router (branch), agent loop (think, act, observe, repeat), map-reduce (fan-out then merge), human gate (pause then resume).
  • Three homes for the engine: agent frameworks with checkpointers (LangGraph), durable-execution platforms (Temporal, Step Functions, Inngest), or a queue plus an idempotent worker. Production mixes them, details in ops.

The five topologies every orchestration is composed of: chain, router, loop, map-reduce, human gate.

Hownodes and edges · state and reducers · checkpoints · interrupts

the vocabulary

  • Node: one function. An LLM call, a tool execution, a router decision, a summarizer, a human gate. Pure function of .
  • Edge: fixed (A always runs after B) or conditional: a function inspects state and returns the name of the next node. The conditional edge IS the "agent decides" moment, the same decision that lived in your old while-loop if/else.
  • Superstep: one tick of the engine. All runnable nodes fire, state snapshots, the next tick begins.
  • Fan-out: a node returns a list of Send(task) items and the engine spawns N worker instances of a node, one per task, merged on the way back.

why graphs beat ad-hoc while-loops

  • Visible: the graph renders as a diagram, reviews in a PR, and stays in sync with runtime because it IS the runtime. The loop in your code was always a graph, just an unreadable one.
  • Replayable: same input plus saved checkpoint equals the same walk. Re-run any historical step exactly.
  • Checkpointable: state serialized after every tick means resume, time-travel debugging and human interrupts are not features you build. They fall out of the model.
  • Testable per node: a node is a function over state, unit-testable with a fake state dict, no LLM required for the routing logic.
  • Enforceable: budgets, timeouts and gates attach to nodes, see ops.

state and reducers: merge rules make parallelism safe

  • State is a typed dict shared by all nodes, a blackboard every node reads from and writes partial updates to.
  • A reducer is a per-key merge rule applied when a node's update lands: append (messages accumulate), last-write (a verdict replaces), union (sets of found ids), or custom.
  • gotcha two parallel branches writing the same key with no reducer is a data race, order undefined. Annotate the key with a reducer or give branches separate keys.
  • Store artifacts by reference: ids and paths to documents and raw tool outputs, not the blobs inline. Snapshots stay small and resume stays fast.

checkpointing: resume after crash, time-travel debug

  • Every superstep lands in a row keyed by thread_id. MemorySaver for demos, Postgres for real, one row per (thread, tick).
  • Resume not restart: a run that dies at step 9 of 10 reloads its last checkpoint and executes only step 9 onward.
  • Time-travel debug: fork from any old checkpoint, edit state or input, re-run, compare the two walks side by side. The 2am superpower.
  • Multi-turn chat is the same mechanism: a new user message resumes the thread's graph with prior state as the starting checkpoint, see memory.
  • Versioning gotcha: a run started on graph v1 must finish under v1 semantics. Old checkpoints plus new code is corrupted state. Drain in-flight runs before swapping, more in ops.

human-in-the-loop: interrupt, then resume with a verdict

  • Interrupt before the effect: the engine stops the run at the edge of the node, persists state, releases the worker. Nothing side-effecting has happened yet.
  • Approval is a resume: hours or days later, from a different process, the verdict arrives and is injected as the interrupted node's return value. The run continues, no re-execution of earlier nodes.
  • Edited state: the reviewer may change values before resuming (fix the amount, drop a step). Resume applies the edits to the checkpoint first.
  • Reject is a route, not a crash: route to cleanup or exit on a no. Gate SLAs, escalation and audit trails are covered in ops.

Examplea StateGraph with a conditional edge and a gate
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
from operator import add

class State(TypedDict):
    messages: Annotated[list, add]      # reducer: append on merge
    critiques: int

def planner(state): ...               # LLM call, appends a plan
def tools(state): ...                 # execute tool calls, append results
def critique(state): ...              # LLM judges the draft

def route(state):                      # conditional edge: the decision point
    if state["critiques"] < 2 and has_flaws(state):
        return "tools"                # loop back, revise
    return "gate"                   # good enough, ask a human

b = StateGraph(State)
b.add_node("planner", planner)
b.add_node("tools", tools)
b.add_node("critique", critique)
b.add_edge(START, "planner")
b.add_edge("planner", "tools")
b.add_edge("tools", "critique")
b.add_conditional_edges("critique", route, {"tools": "tools", "gate": END})

graph = b.compile(checkpointer=PostgresSaver(...))  # durability, see ops
graph.invoke({"messages": [...]}, config={"configurable": {"thread_id": "case-42"}})
  • Shapes to notice: the loop lives in the conditional edge, not in a while. The reducer on messages makes the tools-to-critique hop append-safe. The checkpointer turns every tick into a resume point and every gate into a wait state, mechanics in ops.
  • In the wild: Cursor's agent checkpoints and rewinds are a durable state machine with time-travel exposed as UI. Insurance claims pause for adjuster approval and resume with the verdict injected, no re-run, no lost research.
Pitfallsmega-nodes, races, bloat
  • Mega-node: the whole workflow inside one node. No checkpoint boundaries, no resume granularity, nothing to test. A node is one clear effect.
  • Missing reducers: parallel branches racing on one key, last writer wins by accident. Annotate or isolate keys.
  • Checkpoint bloat: inline documents and raw outputs in state mean every snapshot re-serializes the world. References, not blobs.
  • Version drift: v1 checkpoints replayed under v2 code corrupt state. Drain in-flight runs before deploying graph changes.
  • Graph religion: wrapping a linear flow in a graph buys ceremony, not durability. Use plain code, see the picker above.
  • Invisible edge logic: conditional functions named route2 and decide_x, their choices unlogged. Name edges after intent and log the chosen branch every tick (evals).
Checklistseven bullets to remember
  • Make control flow explicit: nodes are functions, state in, state out
  • Conditional edges carry the model's decisions, log every chosen branch
  • Reducers on every key that parallel branches write
  • Checkpoint per tick keyed by thread_id, artifacts stored by reference
  • Humans are interrupts before effects, approval is a resume with (possibly edited) state
  • Plain code for linear flows, graphs for loops, branching and resume
  • Retries, DLQ, budgets and gate SLAs live in ops, not in the graph definition
