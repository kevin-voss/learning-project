Orchestration graphs

A while-loop with an LLM inside is an agent engine nobody can see, resume or replay. A graph makes control flow an artifact: named nodes, explicit edges, shared state, a snapshot per step. LangGraph is the reference shape; the concept is the point.

In this chapter Model orchestration as state transitions with explicit persistence, retries, interrupts and human approval points.

Problemthe hidden loop is invisible and fragile

  • Control flow buried in code: the real flowchart hides in nested ifs, retry flags and while-loops. Nobody can review, draw or test it whole.
  • Crashes: a 20-minute research run dies at minute 17 (deploy, OOM, spot kill). Plan, tool results and draft lived in RAM. Gone.
  • Humans in the loop: a refund approval must pause for hours, then continue exactly where it stopped.
  • No replay: "why did it take that branch?" means re-reading logs and guessing, if you logged at all.
  • The pattern: agent workflows are long-running, stateful, branchy and failure-prone: exactly what request/response code handles worst.

Solutionmake the control flow an explicit graph

  • A graph is nodes (functions), edges (who runs next) and one state object, driven by an engine that ticks, snapshots and routes: the loop you would have written anyway, made explicit.
  • Five shapes compose every orchestration: chain (step after step), router (branch), agent loop (think, act, observe, repeat), map-reduce (fan-out, merge), human gate (pause, resume).
  • Three homes for the engine: agent frameworks with checkpointers (LangGraph), durable-execution platforms (Temporal, Step Functions, Inngest), or a queue plus an idempotent worker. Production mixes them, see ops.

Hownodes and edges · state and reducers · checkpoints · interrupts

the vocabulary

  • Node: one function: an LLM call, tool execution, router decision, summarizer or human gate. Pure function of .
  • Edge: fixed (A always runs after B) or conditional: a function reads state and names the next node. That IS the "agent decides" moment, your old while-loop if/else.
  • Superstep: one engine tick: all runnable nodes fire, state snapshots, the next tick begins.
  • Fan-out: a node returns a list of Send(task) items; the engine spawns one worker-node instance per task and merges results on the way back.

why graphs beat ad-hoc while-loops

  • Visible: the graph renders as a diagram, reviews in a PR and cannot drift from runtime, because it IS the runtime.
  • Replayable: same input plus saved checkpoint gives the same walk; re-run any historical step exactly.
  • Checkpointable: state serialized after every tick gives resume, time-travel debugging and human interrupts for free; they fall out of the model.
  • Testable per node: a node is a function over state, unit-testable with a fake state dict; routing logic needs no LLM.
  • Enforceable: budgets, timeouts and gates attach to nodes (ops).

state and reducers: merge rules make parallelism safe

  • State is a typed dict shared by all nodes: a blackboard each node reads and writes partial updates to.
  • A reducer is a per-key merge rule applied when an update lands: append (messages accumulate), last-write (a verdict replaces), union (found ids), or custom.
  • gotcha two parallel branches writing one key with no reducer is a data race, order undefined. Add a reducer or give branches separate keys.
  • Store artifacts by reference: ids and paths to documents and raw tool outputs, not inline blobs. Snapshots stay small, resume stays fast.

checkpointing: resume after crash, time-travel debug

  • Every superstep lands in a row keyed by thread_id, one row per (thread, tick). MemorySaver for demos, Postgres for real.
  • Resume not restart: a run that dies at step 9 of 10 reloads its last checkpoint and runs only step 9 onward.
  • Time-travel debug: fork from any old checkpoint, edit state or input, re-run and compare the two walks. The 2am superpower.
  • Multi-turn chat is the same mechanism: a new user message resumes the thread with prior state as the starting checkpoint, see memory.
  • Versioning gotcha: a run started on graph v1 must finish under v1 semantics; old checkpoints plus new code corrupt state. Drain in-flight runs first, see ops.

human-in-the-loop: interrupt, then resume with a verdict

  • Interrupt before the effect: the engine stops at the node, persists state and releases the worker. No side effect has happened yet.
  • Approval is a resume: hours or days later, from any process, the verdict returns from interrupt() in the paused node. Earlier nodes do not re-run.
  • Edited state: the reviewer may change values first (fix the amount, drop a step); resume applies the edits to the checkpoint.
  • Reject is a route, not a crash: route to cleanup or exit. Gate SLAs, escalation and audit trails live in ops.

Planner, tool loop, critique loop, then a human gate before anything final ships. One graph, every topology from above inside it.

Examplea StateGraph with a conditional edge and a gate

from typing import TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt

class State(TypedDict, total=False):
    draft: str
    critiques: int
    approved: bool
    result: str

def prepare(state: State):
    # A deterministic offline stand-in for work; no LLM or external tool.
    return {"draft": "A small example", "critiques": 0}

def critique(state: State):
    # One bounded revision; this sample finds no flaw and continues to review.
    return {"critiques": state["critiques"] + 1}

def route(state: State):
    return "review" if state["critiques"] >= 1 else "critique"

def review(state: State):
    approved = interrupt({"draft": state["draft"], "critiques": state["critiques"]})
    return {"approved": bool(approved)}

def finalize(state: State):
    return {"result": "published" if state["approved"] else "rejected"}

def finish(state: State):
    return END

builder = StateGraph(State)
builder.add_node("prepare", prepare)
builder.add_node("critique", critique)
builder.add_node("review", review)
builder.add_node("finalize", finalize)
builder.add_edge(START, "prepare")
builder.add_edge("prepare", "critique")
builder.add_conditional_edges("critique", route, {"critique": "critique", "review": "review"})
builder.add_conditional_edges("review", lambda state: "finalize", {"finalize": "finalize"})
builder.add_conditional_edges("finalize", finish, {END: END})
app = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "lesson-1"}}
paused = app.invoke({}, config)
assert paused["__interrupt__"][0].value["critiques"] == 1
# Later, resume this same thread; pass False to demonstrate the rejected branch.
result = app.invoke(Command(resume=False), config)
assert result["result"] == "rejected"

Run with pip install langgraph. In-memory checkpoints die with the process; production needs a durable checkpointer. On resume, LangGraph reruns the node containing interrupt from its start, so put no side effects before that call. The pause shows in result["__interrupt__"]; resume with Command(resume=...) on the same thread_id. See the official interrupt guide.

  • Shapes to notice: the critique loop lives in the conditional edge route, not a while. interrupt() in review parks the run on a checkpoint until the second invoke on the same thread_id. Durable resume paths: ops.
  • In the wild: Cursor's agent checkpoints and rewinds: a durable state machine with time-travel as UI. Insurance claims pause for adjuster approval and resume with the verdict injected, no re-run, no lost research.

Pitfallsmega-nodes, races, bloat

  • Mega-node: the whole workflow in one node: no checkpoint boundaries, no resume granularity, nothing to test. A node is one clear effect.
  • Missing reducers: parallel branches race on one key; last writer wins by accident.
  • Checkpoint bloat: inline documents and raw outputs re-serialize with every snapshot. References, not blobs.
  • Version drift: v1 checkpoints under v2 code corrupt state. Drain before deploying graph changes.
  • Graph religion: a linear flow wrapped in a graph buys ceremony, not durability. Use plain code, see the picker above.
  • Invisible edge logic: conditionals named route2 and decide_x, choices unlogged. Name edges after intent and log the chosen branch every tick (evals).

Checklistseven bullets to remember

  • Make control flow explicit: nodes are functions, state in, state out
  • Conditional edges carry the model's decisions, log every chosen branch
  • Reducers on every key that parallel branches write
  • Checkpoint per tick keyed by thread_id, artifacts stored by reference
  • Humans are interrupts before effects, approval is a resume with (possibly edited) state
  • Plain code for linear flows, graphs for loops, branching and resume
  • Retries, DLQ, budgets and gate SLAs live in ops, not in the graph definition
