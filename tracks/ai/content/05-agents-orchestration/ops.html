Durable orchestration ops

A graph gives the workflow shape. Ops give it a pulse. This layer decides whether a run dies at minute 17 of 20, or checkpoints, retries, pauses for a human and finishes tomorrow.

Problemthe demo loop dies on Monday
  • Crashes: a 20-minute research run dies at minute 17 (deploy, OOM, spot kill). Plan, tool results and draft lived in RAM. Gone.
  • Flaky dependencies: LLM APIs throw 429 and 500. Naive retries make it worse and cost real money.
  • Long horizon: batch evals and deep research run minutes to hours. No HTTP request lives that long.
  • Humans in the loop: a refund approval needs the run to pause for hours, then continue exactly where it stopped.
  • Runaway cost: an agent that keeps searching, each result prompting more searches, is a real phenomenon, see agent patterns.
  • The pattern: an agent workflow is long-running, stateful, failure-prone. The exact trifecta request/response code handles worst.
Solutiontreat every run as a durable job
  • A run is a job, not a request. Persist state after every step, retry only what is safe to retry, park poison work in a DLQ, cap everything with budgets, model approvals as wait states.
  • Resume, not restart. A checkpointed run that dies at step 9 of 10 comes back at step 9. The checkpointing model is defined in orchestration graphs, this page is the operations around it.
  • Three homes for this logic: an orchestration engine with a checkpointer, a durable-execution platform (Temporal, Step Functions, Inngest), or the oldest one, a queue plus an idempotent worker.
Howretries · idempotency · timeouts · DLQ · fan-out · budgets · gates

retries: backoff, jitter, classification

  • Exponential backoff: wait 1s, 2s, 4s, 8s between attempts. Doubling gives the dependency time to recover.
  • Jitter is not optional: add randomness on top (full jitter: sleep a random time between 0 and the backoff). Synchronized retries stampede the API in lockstep, the thundering herd. Jitter spreads them.
  • Classify before retrying: retry transient errors (429, 500, 503, timeouts, connection resets). Never retry 400, 401 or 422, you get the same error and pay for the privilege.
  • Retry only what is safe: idempotent calls, or calls that provably failed before any side effect. A timeout on a payment POST is ambiguous, the request may have landed. That is a status lookup, not a retry.
  • Retry budget: cap retries per dependency per window (a common rule: retries may add at most 10% of traffic). Budget spent, fail fast. Retries are load amplification, worst exactly when the dependency is dying.

idempotency: exactly-once is engineered, not delivered

  • Every delivery layer is at-least-once: queues redeliver, clients replay, workers crash after committing. Some step of some run WILL execute twice eventually.
  • Idempotency key: a stable name for the effect, sent with the request and stored with the result. Same key seen again: return the stored result, skip the work.
  • Dedupe on (run_id, step): consult a checkpoint or effects table before executing a node. Already done, skip. That is the whole trick.
  • Why LLM steps break the illusion: a rerun model call returns different tokens, so same-input-same-result is gone. You cannot dedupe the model. You dedupe the effects around it: tool calls keyed by call id (call shapes live in tool calling), writes keyed by step, outputs stored once per attempt.
  • Intent log: persist "about to refund case-42" before acting, mark done after. A crash between the two becomes detectable and reconcilable instead of silent.

timeouts per node type

  • One timeout does not fit all nodes. A 5s cap kills every LLM call. A 1h cap on a refund tool hides hangs forever.
  • Starting points: LLM call 30 to 120s (streaming keeps the connection alive), tool 5 to 60s, sub-agent runs in minutes, whole run a hard wall-clock cap.
  • Human gate: the timeout is an SLA in hours or days, with escalation, nudge, then lead, then conservative auto-reject. Never auto-approve on timeout.
  • Budget the wait: the run wall clock should include gate SLAs, or one stuck approval eats the entire budget by existing.

the DLQ: where poison messages go to be understood

  • Poison message: fails every delivery attempt. Malformed payload, a schema the model refuses ten times in a row, a tool that 500s deterministically.
  • After about 3 failed deliveries, stop. Park it where a human can inspect it. A message looping forever burns money and hides the bug.
  • Alert on depth and on age. A DLQ nobody watches is a landfill.
  • Replay tooling is the other half: inspect payload plus trace, fix the cause, replay from the DLQ or the last good checkpoint. Build and test the replay button before you need it at 2am.
  • Triage loop: bug in code, bad upstream data, or model-quality issue. Each has a different fix and owner. Tag DLQ entries accordingly.

fan-out and fan-in: parallel branches

  • Fan-out: one supervisor scatters N tasks, map-reduce style. Node modeling and send-style dispatch live in graphs.
  • Barrier semantics: the join waits for all branches (AND-join) or for k of n (quorum). Decide explicitly, the silent default is usually all.
  • Partial failure policy, chosen in advance: fail fast (one dead branch kills the run, right for money-moving), quorum (continue with k of n, good for search-and-rank), continue-and-collect (gather successes plus a failures list the model can reason over).
  • Reducers make parallel writes safe: per-key merge rules (append, last-write). Two branches writing one key with no reducer is a data race.
  • Branch deadlines: one slow branch holds the join while paid context sits idle. Give every branch its own timeout.

budgets: steps, tokens, time, dollars

  • Every run gets a budget: max steps, max tokens, max wall-clock, max dollars. Enforce it in the loop, not in hope.
  • Check before each step: the cheapest error is "budget exhausted" raised before the API call, not a hard stop after the invoice.
  • Circuit breaker: when a dependency's error rate spikes (say half of calls failing in 2 minutes), stop calling it, fail fast or degrade, half-open after a cool-down. Retries without a breaker are a DDoS you run on yourself.
  • Per-user concurrency locks: one user should not run five expensive research jobs in parallel. Placement on real infrastructure is covered in full systems on AWS.

durability: checkpoint per step, resume not restart

  • Serialize state after every step, keyed by run or thread id. On crash: reload the last checkpoint, re-execute only the step that was in flight.
  • Checkpoint boundaries are the unit of resume. Well-shaped nodes, one clear effect each, are what make resume cheap. Shaping them is the graphs job.
  • Versioning gotcha: a run started on graph v1 must finish under v1 semantics. Old checkpoints plus new code is corrupted state. Let in-flight runs drain before swapping.
  • Trim state: store big artifacts (documents, raw tool outputs) by reference, or every snapshot bloats and resume slows.

human-in-the-loop as an async node

  • A gate is a wait state, not a sleep: the run hits the node, persists "awaiting approval", releases the worker. No thread parks for three days.
  • Notify with context: email, Slack or a ticket carrying what the decider needs: the action, the amount, evidence links, a deadline.
  • Approve, reject or edit: resume injects the verdict (or edited values) as the node's return value. Reject routes to a cleanup or exit path, it never crashes the run.
  • Mechanics by engine: LangGraph interrupt() plus Command(resume=...), Step Functions waitForTaskToken, or your own gates table plus a resume API.
  • Audit trail: who decided, when, what they saw. Regulators and postmortems both ask.

Exampleone durable step, then a gate resumed from another process
import time, random

def run_step(run_id, step, fn, store):
    """One durable step: dedupe, bounded retries, DLQ beyond budget."""
    key = (run_id, step)                    # the dedupe key
    done = store.get_checkpoint(key)
    if done is not None:                  # replay after crash: skip
        return done

    for attempt in range(4):                # 1 try + 3 retries
        try:
            result = fn()                   # must be idempotent
            store.save_checkpoint(key, result)
            return result
        except PermanentError as e:         # 400/401/422: retrying cannot help
            store.to_dlq(key, repr(e))
            raise
        except TransientError as e:         # 429/500/timeout
            if attempt == 3:
                store.to_dlq(key, repr(e))  # poison: park and alert
                raise
            time.sleep((2 ** attempt) + random.uniform(0, 1))
  • Shapes to notice: dedupe before execute, checkpoint before return, DLQ after budget, jitter on every sleep.
  • The gate below is two rows and a resume call, not a sleeping thread. Create and notify now, the verdict arrives hours later from any process.
def approve_node(state, store):
    gate = store.create_gate(               # wait state, not a sleep
        run_id=state["run_id"], step="approve",
        payload={"refund_id": state["id"], "usd": state["usd"]})
    notify_reviewer(gate)                   # Slack or email with evidence links

# hours later, in a different process, a human answers:
verdict = store.resolve_gate(gate_id, answer)  # approve / reject / edit
engine.resume(state["run_id"], verdict)          # continues at approve_node
Pitfallsstorms, doubles, landfills
  • Retry storms on billed APIs: every retry is a full-price call. A 429 storm with unbounded retries is a self-inflicted outage with an invoice. Cap attempts and alert on retry rate.
  • Double side effects: crash after the charge but before the checkpoint, and the retry charges again. Put the idempotency key on the payment itself and log intent before acting.
  • Visibility timeout shorter than the job: the queue hands the in-flight message to a second worker and you process it concurrently. Long jobs need heartbeat extensions.
  • Retrying the ambiguous: a timed-out POST may have landed. Retry after a status lookup, not blindly.
  • DLQ as landfill: no alert, no replay tooling, no owner. Six months later nobody knows what is safe to replay.
  • Budgets in hope: caps checked after the call are invoice reports. Check before the call.
  • Blocking gates: a thread that sleeps until approval holds a worker, leaks memory and dies on deploy. Gates are rows plus a resume path.
Checklistseven bullets to remember
  • Backoff with full jitter on every remote call, hard cap on attempts
  • Classify errors first: retry transient only, DLQ the permanent
  • Idempotency key on every effect that bills, ships or messages
  • Dedupe on (run_id, step), checkpoint after each step, store bulk by reference
  • Per-node timeouts: LLM 30-120s, tool 5-60s, gate SLA in days with escalation
  • DLQ with alerts on depth and age, plus a tested replay button
  • Budgets per run: steps, tokens, wall clock, dollars, circuit breaker on error spikes
