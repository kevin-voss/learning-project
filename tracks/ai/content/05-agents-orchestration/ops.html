Durable orchestration ops

A graph gives the workflow shape. Ops give it a pulse. This layer decides whether a run dies at minute 17 of 20, or checkpoints, retries, pauses for a human and finishes tomorrow.

In this chapter Design durable work around idempotency, at-least-once delivery, retry budgets and observable terminal failure.

Problemthe demo loop dies on Monday

  • Crashes: a 20-minute research run dies at minute 17 (deploy, OOM, spot kill). Plan, tool results and draft lived in RAM. Gone.
  • Flaky dependencies: LLM APIs throw 429 and 500; naive retries make it worse and cost real money.
  • Long horizon: batch evals and deep research run minutes to hours. No HTTP request lives that long.
  • Humans in the loop: a refund approval must pause for hours, then continue exactly where it stopped.
  • Runaway cost: an agent whose every search result prompts more searches is a real phenomenon, see agent patterns.
  • The pattern: agent workflows are long-running, stateful and failure-prone: exactly what request/response code handles worst.

Solutiontreat every run as a durable job

  • A run is a job, not a request. Persist state after every step, retry only what is safe, park poison work in a DLQ, cap everything with budgets, model approvals as wait states.
  • Resume, not restart. A checkpointed run that dies at step 9 of 10 comes back at step 9. Orchestration graphs defines the checkpoint model; this page covers the operations around it.
  • Three homes for this logic: an orchestration engine with a checkpointer, a durable-execution platform (Temporal, Step Functions, Inngest), or a queue plus an idempotent worker.

Howretries · idempotency · timeouts · DLQ · fan-out · budgets · gates

retries: backoff, jitter, classification

  • Exponential backoff: wait 1s, 2s, 4s, 8s between attempts so the dependency can recover.
  • Jitter is not optional: full jitter sleeps a random time between 0 and the backoff. Without it, synchronized retries hit the API in lockstep: the thundering herd.
  • Classify before retrying: retry transient errors (429, 500, 503, timeouts, connection resets). Never retry 400, 401 or 422: same error, paid again.
  • Retry only what is safe: idempotent calls, or calls that provably failed before any side effect. A timed-out payment POST may have landed: that calls for a status lookup, not a retry.
  • Retry budget: cap retries per dependency per window (a common rule: at most 10% extra traffic), then fail fast. Retries amplify load exactly when the dependency is dying.

idempotency: exactly-once is engineered, not delivered

  • Every delivery layer is at-least-once: queues redeliver, clients replay, workers crash after committing. Some step WILL eventually execute twice.
  • Idempotency key: a stable name for the effect, sent with the request and stored with the result. Seen again: return the stored result, skip the work.
  • Dedupe on (run_id, step): check a checkpoint or effects table before executing a node; already done means skip. That is the whole trick.
  • LLM steps break the illusion: a rerun model call returns different tokens, so you cannot dedupe the model. Dedupe the effects around it: tool calls keyed by call id (tool calling), writes keyed by step, outputs stored once per attempt.
  • Intent log: persist "about to refund case-42" before acting, mark done after. A crash in between becomes detectable and reconcilable, not silent.

timeouts per node type

  • One timeout does not fit all nodes. 5s kills every LLM call; 1h on a refund tool hides hangs forever.
  • Starting points: LLM call 30 to 120s (streaming keeps the connection alive), tool 5 to 60s, sub-agent runs in minutes, whole run a hard wall-clock cap.
  • Human gate: the timeout is an SLA in hours or days with escalation: nudge, then lead, then conservative auto-reject. Never auto-approve on timeout.
  • Budget the wait: include gate SLAs in the run wall clock, or one stuck approval eats the whole budget.

the DLQ: where poison messages go to be understood

  • Poison message: fails every delivery: malformed payload, a schema the model refuses ten times, a tool that 500s deterministically.
  • After about 3 failed deliveries, stop and park it for a human. A message looping forever burns money and hides the bug.
  • Alert on depth and on age. A DLQ nobody watches is a landfill.
  • Replay tooling is the other half: inspect payload and trace, fix the cause, replay from the DLQ or last good checkpoint. Test the replay button before 2am needs it.
  • Triage loop: code bug, bad upstream data or model quality: each has a different fix and owner, so tag DLQ entries.

fan-out and fan-in: parallel branches

  • Fan-out: a supervisor scatters N tasks, map-reduce style; node modeling and send-style dispatch live in graphs.
  • Barrier semantics: the join waits for all branches (AND-join) or k of n (quorum). Decide explicitly; the silent default is usually all.
  • Partial-failure policy, chosen up front: fail fast (one dead branch kills the run, right for moving money), quorum (k of n, good for search-and-rank), or continue-and-collect (successes plus a failures list the model can reason over).
  • Reducers make parallel writes safe: per-key merge rules (append, last-write); two branches writing one key without one is a data race.
  • Branch deadlines: one slow branch holds the join while paid context idles. Give each branch its own timeout.

budgets: steps, tokens, time, dollars

  • Every run gets a budget: max steps, tokens, wall clock and dollars, enforced in the loop, not in hope.
  • Check before each step: the cheapest "budget exhausted" is raised before the API call, not after the invoice.
  • Circuit breaker: when a dependency's error rate spikes (say half of calls failing over 2 minutes), stop calling it, fail fast or degrade, and half-open after a cool-down. Retries without a breaker are a DDoS on yourself.
  • Per-user concurrency locks: one user should not run five expensive research jobs at once. Infrastructure placement: full systems on AWS.

durability: checkpoint per step, resume not restart

  • Serialize state after every step, keyed by run or thread id. On crash, reload the last checkpoint and re-execute only the in-flight step.
  • Checkpoint boundaries are the unit of resume. Nodes with one clear effect each make resume cheap; shaping them is the graphs job.
  • Versioning gotcha: a run started on graph v1 must finish under v1 semantics; old checkpoints plus new code corrupt state. Drain in-flight runs before swapping.
  • Trim state: store big artifacts (documents, raw tool outputs) by reference, or snapshots bloat and resume slows.

human-in-the-loop as an async node

  • A gate is a wait state, not a sleep: the run persists "awaiting approval" and releases the worker. No thread parks for three days.
  • Notify with context: email, Slack or a ticket with the action, amount, evidence links and deadline.
  • Approve, reject or edit: resume injects the verdict (or edited values) into the paused node. Reject routes to cleanup or exit; it never crashes the run.
  • Mechanics by engine: LangGraph interrupt() plus Command(resume=...), Step Functions waitForTaskToken, or your own gates table plus a resume API.
  • Audit trail: who decided, when, what they saw. Regulators and postmortems both ask.

The worker loop that carries most production agent traffic: dedupe before execute, retry with jitter, DLQ beyond the retry budget, gates as wait states.

Exampleone durable step, then a gate resumed from another process

import time, random

def run_step(run_id, step, fn, store):
    """One durable step: dedupe, bounded retries, DLQ beyond budget."""
    key = (run_id, step)                    # the dedupe key
    done = store.get_checkpoint(key)
    if done is not None:                  # replay after crash: skip
        return done

    for attempt in range(4):                # 1 try + 3 retries
        try:
            result = fn()                   # must be idempotent
            store.save_checkpoint(key, result)
            return result
        except PermanentError as e:         # 400/401/422: retrying cannot help
            store.to_dlq(key, repr(e))
            raise
        except TransientError as e:         # 429/500/timeout
            if attempt == 3:
                store.to_dlq(key, repr(e))  # poison: park and alert
                raise
            time.sleep(random.uniform(0, 2 ** attempt))  # full jitter
  • Shapes to notice: dedupe before execute, checkpoint before return, DLQ after budget, jitter on every sleep.
  • The gate below is two rows and a resume call, not a sleeping thread: create and notify now; the verdict arrives hours later from any process.
def approve_node(state, store):
    gate = store.create_gate(               # wait state, not a sleep
        run_id=state["run_id"], step="approve",
        payload={"refund_id": state["id"], "usd": state["usd"]})
    notify_reviewer(gate)                   # Slack or email with evidence links

# hours later, in a different process, a human answers:
verdict = store.resolve_gate(gate_id, answer)  # approve / reject / edit
engine.resume(state["run_id"], verdict)          # continues at approve_node

Pitfallsstorms, doubles, landfills

  • Retry storms on billed APIs: every retry is a full-price call; unbounded retries in a 429 storm are a self-inflicted outage with an invoice. Cap attempts, alert on retry rate.
  • Double side effects: crash after the charge but before the checkpoint, and the retry charges again. Put the idempotency key on the payment itself and log intent first.
  • Visibility timeout shorter than the job: the queue hands the in-flight message to a second worker. Long jobs need heartbeat extensions.
  • Retrying the ambiguous: a timed-out POST may have landed. Look up status first.
  • DLQ as landfill: no alert, no replay tooling, no owner; months later nobody knows what is safe to replay.
  • Budgets in hope: caps checked after the call are invoice reports. Check before the call.
  • Blocking gates: a thread sleeping until approval holds a worker, leaks memory and dies on deploy. Gates are rows plus a resume path.

Checklistseven bullets to remember

  • Backoff with full jitter on every remote call, hard cap on attempts
  • Classify errors first: retry transient only, DLQ the permanent
  • Idempotency key on every effect that bills, ships or messages
  • Dedupe on (run_id, step), checkpoint after each step, store bulk by reference
  • Per-node timeouts: LLM 30-120s, tool 5-60s, gate SLA in days with escalation
  • DLQ with alerts on depth and age, plus a tested replay button
  • Budgets per run: steps, tokens, wall clock, dollars, circuit breaker on error spikes
