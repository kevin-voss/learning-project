Memory: short-term, long-term, summaries

Two clocks run in every assistant. The window is short-term: this session as the model sees it, rebuilt every call, gone when the session ends. The store is long-term: facts written back after sessions and retrieved across them. Memory is the plumbing between the two clocks.

In this chapter Separate current context, summaries, durable user memory and model weights; make retrieval scoped, inspectable and correctable.

Why this layer matters

  • Amnesia at session end. The transcript dies, the next session starts from zero.
  • Windows fill mid-session. Long threads overflow the budget, see context budgeting.
  • Users expect continuity. "Remember my preferences" must actually work.
  • Re-typing is not memory. Restating decisions every session is the failure mode.

Memory lifecycle

A and B manage the window inside the session, C and D manage the store across sessions.

How it works

  • Keep the last N turns, drop everything older.
  • Anchored upgrade: pin turn one, the goal, plus the last K.
  • Fits stateless FAQ only, loses decisions and constraints silently.

How it works

  • Running summary of old turns, last K stay verbatim, promises stay quotable.
  • at ~70% of the history budget, never at overflow.
  • Summaries keep decisions, numbers, constraints, open questions.

Drift

  • Summary-of-summary merges lose detail, errors compound like lossy copies.
  • Re-derive periodically from source turns kept in the transcript table.
  • Structured blocks merge cheaper than narrative paragraphs.

How it works

  • One fact per row: timestamped, scoped, embedded.
  • Top-k by similarity injects a labeled block, see embeddings.
  • Label it "known facts", data to use, not gospel.

Kinds

  • Profile: small, high-trust, injected whole, never left to retrieval.
  • : summarized past threads, always fetched by similarity.
  • Procedural: AGENTS.md-style rule files, the file is the store.

How it works

  • Explicit: dedicated extraction call at session end, testable.
  • Automatic: extract mid-session, fresher but noisier writes.
  • Dedupe before insert, embedding similarity plus exact keys.
  • Scope every row: user, session, org, project.

Supersede and forget

  • Contradictions mark old rows superseded, keep the lineage.
  • "Moved to Berlin" must retire "lives in Paris".
  • TTL volatile facts, prune what retrieval never picks.

Privacy

  • Multi-user isolation is a security boundary, see guardrails.
  • PII flows in freely, decide what is allowed, encrypt at rest.
  • Delete-me removes the row, the vector copy, backups, logs.

Decision boundary

Use when

  • Sessions run long with decisions and constraints.
  • The product promise is cross-session continuity.
  • Source turns are kept for re-derivation.
  • Retrieval filters by user and scope server-side.

Skip when

  • One-shot tasks, stateless FAQ, anonymous traffic.
  • Regulated flows where retention is a liability.
  • You cannot isolate or delete per user.
  • A wrong remembered fact is worse than asking again.

Worked example

One table carries the whole policy: isolation, scope, TTL, lineage, retrieval. Every query filters on user_id and scope.

CREATE TABLE memory (
  fact_id       uuid PRIMARY KEY,  -- one durable fact per row
  user_id       uuid NOT NULL,     -- isolation boundary, always filter
  scope         text NOT NULL,     -- 'user' · 'session' · 'org' · 'project'
  content       text NOT NULL,     -- 'user prefers concise answers'
  source_id     uuid,                    -- originating session, for audit
  created_at    timestamptz NOT NULL,
  expires_at    timestamptz,             -- TTL volatile facts, null means durable
  superseded_by uuid,                    -- contradiction resolution keeps lineage
  embedding     vector(1536)       -- similarity retrieval, top-k
);

Failure modes

  • Memory bleed: one missing user filter shows customer A to B.
  • Stale facts steer silently: "free plan" from last year.
  • Injection persists: planted facts steer every future session, see prompt injection.
  • Flaky evals: unfrozen stores break goldens, see evals.
  • Cost creep: every turn pays embedding plus memory tokens, cap k.

Keep in mind

  • Two clocks: the window dies with the session, the store survives.
  • Default is the hybrid, compact at ~70%, see context budgeting.
  • Re-derive summaries from source turns on a schedule.
  • Retrieve like RAG: top-k into a labeled block, embeddings.
  • Write-back: dedupe, scope, supersede, make delete real.

Try, verify, explain

  1. Given a user correction, decide whether it belongs in the current conversation, a summary, a durable profile or nowhere; state who can read it and how it expires.
  2. Measure summary drift: plant 5 constraints and 3 numbers in a 40-turn transcript, summarize turns 1-30, then re-summarize that summary three times. Count which facts survive each pass.
  3. Explain why "moved to Berlin" must mark "lives in Paris" superseded instead of adding a second row, and what top-k retrieval would inject if superseded_by were ignored.
