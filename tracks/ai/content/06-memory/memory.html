Memory: short-term, long-term, summaries

Two clocks run in every assistant. The window is short-term: what the model sees of this session, rebuilt on every call, dead when the session ends. The store is long-term: facts written back after sessions and retrieved across them. Memory is the plumbing between the two clocks, and none of it is magic.

Problemthe window dies with the session, users do not
  • Amnesia at session end. The transcript dies with the thread. Next session starts from zero and "last week you said" points nowhere.
  • Users expect continuity anyway. Products ship memory toggles, so "remember that I prefer concise answers" must actually work. The feature is all engineering, none of it magic.
  • Long sessions fill the window long before they end, and naive trimming cuts the wrong things. Those budget mechanics live in context budgeting, this topic is the memory built on top.
  • Re-typing is not memory. Forcing users to restate preferences, project names and past decisions every session is the failure mode memory exists to remove.
Solutiona window for the session, a store for the year
  • why Two clocks: the window holds this session's working context and is reassembled on every call. The store holds facts that outlive sessions and is read back into the window on demand.
  • Within a session: a sliding window, or better, the summary + last-K verbatim hybrid, compacted at ~70% of budget.
  • Across sessions: at checkpoints, extract durable facts and write them to a store keyed by user and scope.
  • Per turn: retrieve the relevant stored facts and inject them into the window as a labeled block, exactly like retrieval, see RAG.

Howtwo clocks · summarization · the fact store · write-back · forgetting

the two clocks, precisely

  • Short-term, the window: this thread's messages, the agent scratchpad, tool results in flight. Checkpointed per step for durability in orchestration graphs. Dies with the task.
  • Long-term, the store: rows you own in your own database. Survives restarts, deployments and sessions. The model only ever sees what you retrieve back into the window.
  • The bridge, two different jobs: compaction turns old turns into a running summary inside the session. Extraction turns finished sessions into facts across sessions. Conflating them is the classic design bug.

short-term mechanics, the recap that matters

  • Sliding window: keep the last N turns. Cheapest, loses the goal and every decision.
  • Anchored trim: first turn (the goal) plus the last K. Cheap upgrade over plain sliding.
  • Summary + last-K hybrid, the default: a running summary of old turns plus the last K verbatim. Recent promises stay quotable, old decisions survive compressed.
  • Compact at ~70% of the history budget, never at overflow. The full ladder, slice budgets and token math: context budgeting.

automatic summarization, in depth

  • What to keep, in order: decisions made and their reasons, names and numbers, constraints, open questions. Everything else is optional.
  • Structured beats narrative: a "facts / decisions / open questions" block outlives a flowing paragraph and is cheaper to merge on the next compaction pass.
  • gotcha Summary-of-summary drift: each merge loses a little detail and each further merge loses more, errors compound like lossy copies of copies. After enough merges the thread confidently misremembers.
  • Fix: re-derive from source. Keep the original turns in your transcript table and periodically rebuild the summary from them, not from the previous summary.
  • Anchor preservation: a summary that loses the decision is worse than truncation, because the model still sounds sure of itself with half the context gone.

long-term memory is retrieval

  • Fact store (semantic): discrete rows, "user prefers concise answers", "repo uses Postgres 16", written back after sessions. One fact per row, timestamped, scoped.
  • User profile: curated, high-trust facts, name, timezone, role, preferences. Small enough to inject whole, too important to gamble on retrieval missing it.
  • store: summarized past threads kept as documents. Large, so always fetched by similarity, never wholesale.
  • Procedural: learned rules and updated instructions. In coding agents this is AGENTS.md-style files, the file IS the memory, readable by any tool.
  • The retrieval loop: embed each stored fact, embed the current turn, top-k into a labeled block. The user's own history is just another corpus, see embeddings.
  • Label the block: "known facts about this user" as its own section, so the model treats it as data to use, not gospel to obey.

write-back policies

  • Explicit extraction: a small dedicated LLM call at session end, "list durable facts from this transcript". Predictable, testable, costs one call per session.
  • Automatic continuous: extract while the session runs. Fresher, but writes noise mid-flow and multiplies extraction calls.
  • Dedupe and timestamp: match new facts against stored ones before insert, embedding similarity plus exact keys catches most repeats.
  • Contradiction resolution: a new fact supersedes the old one, mark it superseded and keep lineage, rather than blind last-write-wins. "User moved to Berlin" must retire "user lives in Paris".
  • When to forget: staleness TTL on volatile facts (plan tier, current project), user-initiated deletion, and low-confidence facts that retrieval never picks up.
  • Write scope on every row: user, session, org, project. Retrieval filters on scope, always.

privacy and isolation

  • Multi-user isolation is a security boundary: memory rows keyed by user id, retrieval filtered server-side. A leak here is a data breach between customers, see guardrails.
  • PII flows in freely: memory happily stores addresses, health hints and moods. Decide what is allowed in, encrypt at rest, keep a user-to-rows mapping.
  • Delete-me must actually delete: the row, the vector copy, backups, and logs of what was shown to the model. Regulators treat "we still have the embedding" as not deleted.
  • Retention: age facts out on a schedule. "She mentioned a layoff in 2023" is not a fact you want surfaced forever.
  • Audit: log which memories were injected into which call so any answer can be explained afterwards.

memory changes behavior

  • Determinism breaks: same input, different answer, because the store changed between runs. Reproducibility now depends on memory state, not just prompts and temperature.
  • Eval problems: goldens need frozen memory fixtures or a per-test user with a seeded store, see evals. A memory-off regression suite stays the baseline.
  • Injection surface: retrieved memories are content that steers the model. A poisoned or planted fact persists and fires in every future session. Treat memory reads as untrusted data, see prompt injection.
  • Steering risk: one wrong stored fact steers every future answer, silently. Uncurated memory becomes lint.

When NOT to add memory: one-shot tasks (summarize this document), compliance regimes where retention is a liability, anonymous or shared traffic, and any flow where a wrong remembered fact is worse than asking again. Memory is a feature you default off, then enable with intent.

Examplememory as a product feature, plus the table
  • Coding agents remember repo conventions: procedural memory persisted to AGENTS.md or CLAUDE.md. The file is the store, reviewable in a diff, readable by any tool.
  • Assistants remember preferences: "concise answers, no emojis, deploys on Thursdays" as semantic facts, injected each session as a profile block.
  • Support agents know account history: plan tier, last three tickets, outcome of the last outage. Scoped to the account, TTL on anything volatile.
  • Companion apps with months of continuity run nightly summary re-derivation, because drift is the difference between "it remembers" and "it confabulates".
CREATE TABLE memory (
  fact_id       uuid PRIMARY KEY,            -- one durable fact per row
  user_id       uuid NOT NULL,             -- isolation boundary, always filter on it
  scope         text NOT NULL,             -- 'user' · 'session' · 'org' · 'project'
  kind          text NOT NULL,             -- 'semantic' · 'episodic' · 'procedural'
  content       text NOT NULL,             -- 'user prefers concise answers'
  source_id     uuid,                          -- session it came from, for audit
  confidence    numeric DEFAULT 1.0,
  created_at    timestamptz NOT NULL,
  expires_at    timestamptz,                   -- null means durable, set TTL on volatile facts
  superseded_by uuid,                         -- contradiction resolution keeps lineage
  embedding     vector(1536)
);
def build_messages(user, turn):
    profile = store.profile(user.id)               # small, injected whole
    facts = store.top_k(user.id, embed(turn), k=8)  # filtered by scope
    return [
        {"role": "system", "content": SYSTEM + profile_block(profile)},
        {"role": "system", "content": memory_block(facts)},  # labeled data
        *summary_block(),
        *last_k_verbatim(12),
    ]
Pitfallswrong memories are worse than none
  • Memory bleed: one missing user filter in retrieval shows customer A's facts to customer B. Test isolation like an auth test.
  • Uncurated accumulation: every session writes, nothing retires, retrieval fills with lint that steers answers wrong.
  • Stale facts: "user is on the free plan" from last year changes today's answer. TTL volatile facts and prefer fresh on conflict.
  • Drift: summary-of-summary compounds errors until the thread confidently misremembers. Re-derive from source turns.
  • Delete that does not delete: the row is gone but the vector, the backup and the prompt log still hold it.
  • Memory in evals: unfrozen stores make goldens flaky in ways that look random, see evals.
  • Injection persistence: a planted fact keeps steering after the attacker leaves the session, see prompt injection.
  • Cost creep: every turn now pays an embedding call and extra input tokens for the memory block. Measure it, cap k.
Checklistthe memory review in 7 lines
  • Two clocks: the window dies with the session, the store survives. Every fact has a home.
  • Short-term: summary + last-K hybrid, compact at ~70% per context budgeting.
  • Summaries keep facts, decisions and open questions. Re-derive from source turns on a schedule.
  • Write-back: explicit extraction, dedupe, timestamp, scope, supersede on contradiction.
  • Retrieve like RAG: top-k, labeled block, fresh beats old, see embeddings.
  • Isolate per user, TTL volatile facts, make delete real, audit what the model was shown.
  • Freeze memory in evals. Default to no memory for one-shot and regulated flows.
