Guardrails & least privilege

Injection will succeed sometimes. Guardrails are automated filters deciding what reaches the model and what leaves it. Least privilege is the keyring policy deciding what a hijacked hop can touch. Together they turn a compromise into a bad log entry.

In this chapter Place deterministic validation, policy checks, least privilege and human review around probabilistic model behavior.

Problemraw hops and oversized keys

  • No filters anywhere: every LLM hop ingests raw user text, retrieved docs and tool output. One poisoned chunk reaches the model with full voice.
  • One permission level for all tools: the agent holds an admin credential, so any successful injection is a breach.
  • Fail-open everywhere: when a filter errors it is bypassed "temporarily", which quietly becomes permanent.
  • No audit trail: after an incident nobody can say what the agent saw, called, or who approved it.

Solutionfilters at every edge, keys too small to matter

  • Staged filters: screen input before the model, output after it, permissions between model and tools. Every hop, not just the user-facing one.
  • Least privilege per tool: read-only default, scoped short-lived credentials, approval gates on writes. Injection succeeds and nothing happens.
  • Explicit fail policy per stage: fail-closed where blast radius is big, fail-open where small. Decide in writing, before the outage.
  • Log everything: every tool call with redacted args and approver, replayable for forensics.

How it worksstages, fail policy, permissions, PII, logs, costs

The two filter stages

input filters before the model

  • PII detection: find emails, card numbers, names; redact before anything reaches the provider.
  • Jailbreak and injection classifiers: score user text and retrieved content for attack patterns.
  • Topic refusal: banned domains get a fixed refusal, no model hop.
  • Runs on user text AND retrieved chunks AND tool results; skipping one reopens the indirect injection door.

output filters after the model

  • Secret scanning: keys and tokens in the answer are blocked, not displayed.
  • PII redaction: masks personal data the model repeats on the way out.
  • Toxicity and policy: topic rules applied to what users actually see.
  • Schema validation: structured output checked against its declared shape before tool arguments or UI code trust it.

Fail-closed vs fail-open

  • : the safe default. The cost is availability.
  • : the convenient default. The cost is every incident you later read about.
  • Choose per stage, by blast radius: topic filter down → fail-open, chat survives, worst case a rude answer. Output filter down → fail-closed, answers can carry secrets. Permission checker down → always fail-closed.
  • gotcha The policy only counts if it also fires on timeouts and provider errors, not just clean refusals.

Least privilege per tool

  • Read-only default: the retrieval path's DB user cannot write. The most effective single control you own.
  • Scoped credentials: per-tenant, per-session tokens, no shared admin key.
  • TTL tokens: minutes, not days; a leaked token expires before anyone notices.
  • Per-tenant quotas and rate caps: even a hijacked loop cannot burn unbounded money or rows.
  • Approval gates for writes: refunds, deletes, sends wait for a human, wired as durable interrupts that survive restarts.
  • MCP servers publish capability lists. Grant the narrowest slice, re-audit when tools change.

PII handling

  • Redact before send: mask personal data at the gateway, before prompts leave your perimeter (Presidio-style pipelines).
  • Retention: prompts and completions are personal data. Set TTLs and contractually exclude them from provider training.
  • Delete-me: deletion must cascade to vector stores, memory profiles and logs, where the copies hide.
  • gotcha Redaction can leak by shape: a rare masked value in a small tenant is re-identifiable.

Audit logging

  • Every tool call logged: tool name, redacted arguments and their digest, decision, approving identity (human or policy).
  • Immutable and append-only: the attacker's first goal is editing the log that convicts them.
  • Replay for forensics: from an incident id, rebuild what the agent saw and did, step by step.
  • Feeds evals: real attacks found in logs become regression cases.

When guardrails hurt

  • Latency budget: each classifier adds tens to hundreds of milliseconds; stacked filters can double time-to-first-token. Budget them like any hop.
  • False positives block legit traffic: an over-eager output filter silently mangles valid answers and users blame the model.
  • The tuning loop: every rule needs thresholds, allowlist exceptions and monitoring. Filters are components under test.
  • Track trigger rates per rule: one firing 100 times a day is a product decision, not a guardrail.

In codea scoped credential with TTL and an approval gate

  • What this buys you: when injection lands, stolen authority covers one tenant, read-only, for ten minutes, every call logged against a session.
  • In the field: regulated deployments ship evidence: filtered-request counts, approval trails, replayable traces. Auditors read logs.
# Integration sketch: identity/approval helpers below are trusted server contracts.
def authorize_call(principal, tool_name, args, approval_id=None):
    claims = trusted_identity_provider.claims(principal)  # verified, unexpired claims
    if tool_name not in claims.tool_permissions:
        raise Denied("tool not granted to principal")
    tool = FIXED_TOOL_REGISTRY.get(tool_name)  # never dispatch a model-supplied callable
    if tool is None:
        raise Denied("unknown tool")
    validated = tool.validate(args)
    if claims.tenant_id != validated.tenant_id:
        raise Denied("tenant mismatch")
    if claims.read_only and tool.writes:
        raise Denied("read-only identity cannot write")
    digest = canonical_digest(tool_name, validated)
    approval = None
    if tool.writes:
        approval = approval_store.consume_once(
            approval_id, subject=claims.subject, tenant=claims.tenant_id,
            tool=tool_name, args_digest=digest, expires_after_now=True)
        if approval is None:
            raise NeedsApproval(tool_name)
    audit.redacted(tool_name, claims.subject, claims.tenant_id, digest, approval)
    return tool.run(validated, scope=claims)

# claims(principal) verifies signature, issuer, audience and expiry before returning.
# consume_once atomically checks subject/tenant/tool/args digest/expiry, then rejects reuse.
# Only redacted values or digests enter the audit log; raw arguments do not.

Integration sketch: the identity provider verifies claim signature, issuer, audience and expiry and supplies the tool-permission allowlist; neither claims nor approvals come from model arguments. The fixed server-side registry validates normalized arguments. Approval records bind identity, tenant, tool, argument digest and expiry, and are consumed once. Audit values are redacted or digests, never raw arguments.

Pitfallsways good guardrails go bad

  • gotcha One filter config for every hop. The retrieval hop needs different rules than the user-facing one; shared config is tuned for neither.
  • gotcha Fail-open on the permission checker during an outage. That "temporary" bypass is the incident report.
  • Logging raw args with secrets inside. The audit log becomes the leak. Log redacted values, keep the vault copy separate.
  • Redacting outputs but sending raw PII in prompts. The provider-side copy is the exposure you forgot.
  • Filters without eval coverage. Rules drift silently until a legit answer is shredded in production.
  • Approval fatigue. Gate everything and humans rubber-stamp. Gate the irreversible only.

Checklistthe six things that matter

  • Every LLM hop: input filter before, output filter after, permission check before any tool runs.
  • Every tool: read-only default, scoped token, short TTL, per-tenant quota.
  • Writes require approval. Permission failures block, never pass.
  • Fail policy written per stage, fires on timeouts, not just clean refusals.
  • PII redacted before send, retention and delete-me defined across stores and logs.
  • Every tool call logged with redacted fields, argument digest, approval record ID and an operation-scoped replay key, feeding the eval suite.
