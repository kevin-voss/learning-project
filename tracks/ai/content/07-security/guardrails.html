Guardrails &amp; least privilege

Injection will succeed sometimes. Guardrails are the automated filters that decide what reaches the model and what leaves it. Least privilege is the keyring policy that decides what a hijacked hop can actually touch. Together they turn a compromise into a bad log entry.

Problemraw hops and oversized keys
  • No filters anywhere: every LLM hop ingests raw user text, raw retrieved docs, raw tool output. One poisoned chunk reaches the model with full voice.
  • One permission level for all tools: the agent holds an admin credential, so any successful injection is instantly a breach.
  • Fail-open everywhere: when a filter errors it is bypassed "temporarily", which quietly becomes permanent.
  • No audit trail: an incident happens and nobody can say what the agent saw, called, or who approved it.
Solutionfilters at every edge, keys too small to matter
  • Staged filters: screen input before the model, screen output after it, check permissions between model and tools. Every hop, not just the user-facing one.
  • Least privilege per tool: read-only by default, scoped and short-lived credentials, approval gates on writes. Injection succeeds and nothing happens.
  • Explicit fail policy per stage: fail-closed where blast radius is big, fail-open where it is small. Decide in advance, in writing, not during an outage.
  • Log everything: every tool call with args and approver, replayable for forensics.

How it worksstages, fail policy, permissions, PII, logs, costs

The two filter stages

input filters before the model

  • PII detection: find emails, card numbers, names. Redact before anything is sent to the provider.
  • Jailbreak and injection classifiers: score user text and retrieved content for attack patterns.
  • Topic refusal: banned domains answered with a fixed refusal, no model hop at all.
  • Runs on user text AND retrieved chunks AND tool results. Skipping any one reopens the indirect injection door.

output filters after the model

  • Secret scanning: keys and tokens in the answer are blocked, not displayed.
  • PII redaction: the model repeats personal data it should not, the filter masks it on the way out.
  • Toxicity and policy: topic rules applied to what users actually see.
  • Schema validation: structured output checked against the declared shape before tool arguments or UI code trust it.

Fail-closed vs fail-open

  • : the safe default. The cost is availability.
  • : the convenient default. The cost is every incident you later read about.
  • Choose per stage, by blast radius: topic filter down → fail-open keeps chat alive and the harm is a rude answer. Output filter down → fail-closed, because answers can carry secrets. Permission checker down → always fail-closed, no exceptions.
  • gotcha The policy only counts if it also fires on timeouts and provider errors, not just clean refusals.

Least privilege per tool

  • Read-only default: the retrieval path uses a DB user that cannot write. The most effective single control you own.
  • Scoped credentials: per-tenant, per-session tokens. No shared admin key across the whole agent.
  • TTL tokens: minutes, not days. A leaked token dies of old age before anyone notices it.
  • Per-tenant quotas and rate caps: even a fully hijacked loop cannot burn unbounded money or rows.
  • Approval gates for writes: refunds, deletes, sends pause for a human, wired as durable interrupts so they survive restarts.
  • MCP servers publish capability lists. Grant the narrowest slice that works, and re-audit grants when tools change.

PII handling

  • Redact before send: strip or mask personal data at the gateway, before prompts leave your perimeter (Presidio-style pipelines).
  • Retention: prompts and completions are personal data. Set TTLs, and contractually exclude them from provider training.
  • Delete-me: user deletion must cascade to vector stores, memory profiles and logs. That is where the copies hide.
  • gotcha Redaction can leak by shape: a rare masked value in a small tenant is re-identifiable. Measure, do not assume.

Audit logging

  • Every tool call logged: tool name, full arguments, decision, and the approving identity (human or policy).
  • Immutable and append-only: the attacker's first goal is editing the log that convicts them.
  • Replay for forensics: given an incident id, rebuild exactly what the agent saw and did, step by step.
  • Feeds directly into evals: real attacks found in logs become regression cases.

When guardrails hurt

  • Latency budget: each classifier adds tens to hundreds of milliseconds. Stacked filters can double time-to-first-token. Budget them like any hop.
  • False positives block legit traffic: an over-eager output filter silently mangles valid answers, and users blame the model.
  • The tuning loop: every rule needs thresholds, allowlist exceptions and monitoring. Filters are components under test, not set-and-forget.
  • Track filter trigger rates per rule. A rule that fires 100 times a day is a product decision, not a guardrail.

In codea scoped credential with TTL and an approval gate
  • What this buys you: when injection lands, the stolen authority covers one tenant, read-only, for ten minutes, with every call logged against a session.
  • In the field: regulated deployments ship evidence, not architecture: filtered-request counts, approval trails, replayable traces. Auditors read logs.
import time

def issue_tool_token(session_id, tenant_id, ttl_s=600):
    """Read-only, tenant-scoped, short-lived. A hijacked call has
    ten minutes and one tenant's rows to play with."""
    claims = {"sub": session_id, "tenant": tenant_id, "ro": True}
    token = sign(claims, int(time.time()) + ttl_s)
    audit("issue_token", tenant_id, session_id, approver="system")
    return token

def call_tool(tool, args, token):
    if not verify(token):          # fail closed on any doubt
        raise Denied("bad or expired token")
    if tool.writes and not args.get("approved_by"):
        raise NeedsApproval(tool.name)
    audit(tool.name, tenant_of(token), args,
          approver=args.get("approved_by"), replay_key=token.claims["sub"])
    return tool.run(args, scope=token.claims)
Pitfallsways good guardrails go bad
  • gotcha One filter config for every hop. The retrieval hop needs different rules than the user-facing hop. Shared config means tuned for neither.
  • gotcha Fail-open on the permission checker during an outage. That "temporary" bypass is the incident report.
  • Logging raw args with secrets inside. The audit log becomes the leak. Redact into the log, keep the vault copy separate.
  • Redacting outputs but sending raw PII in prompts. The provider-side copy is the exposure you forgot.
  • Filters with no eval coverage. Rules drift silently until a legit answer is shredded in production.
  • Approval fatigue. Gate everything and humans rubber-stamp. Gate the irreversible only.
Checklistthe six things that matter
  • Every LLM hop: input filter before, output filter after, permission check before any tool runs.
  • Every tool: read-only default, scoped token, short TTL, per-tenant quota.
  • Writes require approval. Permission failures block, never pass.
  • Fail policy written per stage, fires on timeouts, not just clean refusals.
  • PII redacted before send, retention and delete-me defined across stores and logs.
  • Every tool call logged with args and approver, replayable, and feeding the eval suite.
