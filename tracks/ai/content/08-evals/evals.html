Evals & observability

Every change to an LLM system moves behavior in ways nobody can hold in their head. Evals turn that unease into numbers measured on a fixed set of questions, and traces turn a bad number into a named stage. This is the topic that makes every other topic safe to change.

In this chapter Build an evaluation loop from representative cases, task metrics, regression slices and production traces without mistaking judge scores for truth.

Problemnon-determinism ships regressions dressed as updates

  • Change anything and everything moves. New model version, prompt edit, chunk size 800 → 600: behavior shifts silently across the product.
  • Vibes do not scale. Without evals the only test is "seems fine", so teams either ship regressions or stop touching the prompt.
  • Non-determinism: the same input answers differently on Tuesday. A spot check proves nothing; only a score over a fixed question set is an honest signal.
  • Wrong answer, no suspects. Retrieval, tools, prompt, memory: without traces you cannot tell which one broke.

Solutionthe evaluation pyramid, run as a CI gate on every change

  • why Four layers: component, task, system (end to end), online (real users). Cheap and broad at the base, expensive and rare at the top.
  • A runs the pyramid in CI: every prompt, model or retrieval change gets scored; a drop blocks the merge.
  • A trace for every run turns a red score into a named node: which query, which chunks, which tool call.

Howeach layer · the golden set · judges and their biases · metrics · CI gates · traces

the pyramid, layer by layer

  • Component, did each part work: retrieval recall against expected chunks, tool-call validity (right tool, sane arguments, valid JSON per structured output), asserts. Fast and pinpointed.
  • Task, is each answer good: score every golden question. Judges with rubrics for the fuzzy middle, pairwise for decisions, a human sample for calibration.
  • System, does the pipeline hold: end-to-end runs over a workload: p50 and p95 latency, cost per task against token budgets, success rate.
  • Online, do real users succeed: A/B on task success, thumbs, drift.
  • Split retrieval from generation: "answers are bad" is unactionable; "recall fine, faithfulness tanked" names the layer. This split is the whole game, see RAG.

the golden set, your fixed ruler

  • 30 to 200 curated questions, each with expected facts (what a good answer must contain) and expected sources (the chunks retrieval should fetch).
  • Write it before v2 of anything. Without a ruler, a ported prompt, swapped model or tuned reranker is only different, not provably better.
  • Refresh from real failures: every incident becomes a case, so the suite proves the fix holds. The floor ratchets up.
  • Version it like code: reviewed diffs, an owner, a changelog. A golden set nobody can reproduce is a rumor.
  • Keep a holdout: a slice you never tune against, so its score measures generalization, not memorization.
  • Freeze the world around it: pinned model and judge versions, temperature 0 where possible, a corpus snapshot, fixed memory fixtures. Otherwise runs are not comparable.

offline evals, deterministic checks first

  • Free and unglamorous, catches plenty: JSON parses, every citation is in the retrieved sources, the answer mentions the refund window, each red-team prompt from prompt injection and guardrails is refused.
  • These are unit tests: plain asserts on every commit. No judge, no tokens, no flakiness.
  • Then the fuzzy middle: faithful, complete, grounded, tone: the judge's job.

LLM-as-judge, with humility

  • grades faithful (every claim supported by context, the anti-hallucination number), complete (answers the question asked), grounded (cites real sources).
  • Position bias: the first answer quietly wins. Fix: run both orders, average.
  • Verbosity bias: longer looks better. Fix: a concise rubric, reasons before scores.
  • Self-preference: models favor their own style. Fix: a judge ensemble, including a different model family than the system under test.
  • Calibrate: measure agreement with a human-labeled sample; re-check when the judge model changes. Read scores as trends.

RAGAS-style metrics, plainly

  • Faithfulness: share of answer claims grounded in the retrieved context. Low means hallucination.
  • Answer relevancy: does the answer address the question asked, or something adjacent.
  • Context precision: are the useful chunks ranked at the top, where the prompt uses them.
  • Context recall: did retrieval fetch every chunk the expected answer needs. Misses are a retrieval problem.
  • Read them as a pair: low recall means fix search; high recall with low faithfulness means fix prompts and grounding.

agent evals, trajectories not just answers

  • Tool-call correctness: did the agent in agent patterns call the right tool, with sane arguments, in a sensible order. Grade the path, not just the answer.
  • Step efficiency: loops and retries burn budget; track steps per task.
  • Compaction checks: does the summary still hold the decision after three compactions, see memory.

online evals, real users

  • A/B with task-success metrics: resolution rate, completed checkout, retry count. Never thumbs alone.
  • Thumbs are a weak signal: happy users click nothing, unhappy ones often leave silently.
  • before A/B: run the candidate on duplicated requests, judge offline, zero user risk.
  • Watch drift, not averages: query mix and retrieval scores shift with the corpus and users; slice by query class.

regression gates in CI

  • Eval on every behavior change: prompt edit, model bump, chunking or retrieval tweak, guardrail rule.
  • Block on drop: fail the PR when a metric falls past a threshold (say 0.03) or latency or cost exceed budget.
  • Report per question, not just the mean, which hides a broken query class.
  • Stage it: a smoke subset (10-20 cases) per PR, the full set nightly. Cache judge verdicts; reruns are pure cost.

A flaky red is worse than no eval. Once red sometimes means nothing, nobody trusts green either. Fix flakiness (unfrozen fixtures, live APIs, temperature above 0) the day it appears.

observability, trace every run

  • One run, one tree: every prompt, retrieved chunk and score, tool call and result, tokens, latency, cost. The is the difference between debugging and guessing.
  • Log what the model saw, including injected memory and retrieved context, so any past answer is explainable.
  • Tooling: LangSmith, Braintrust, OpenTelemetry; a queryable span table you own is the minimum.

No golden set yet? Start today: 30 questions from real logs, expected facts per question, deterministic asserts around them. A small ruler beats vibes immediately and grows with every incident you feed it.

Examplethe ruler, the judge, the report

  • Headline numbers are eval results. Anthropic's "contextual retrieval cuts retrieval failures by 49 percent" is a golden-set measurement; that is what made it shippable.
  • Support bots gate prompt changes behind a 100-ticket golden set, so regressions die in CI, not the ticket queue.
  • Teams with trend dashboards (faithfulness next to latency and cost) refactor prompts weekly; teams without them freeze the prompt at launch.
CREATE TABLE golden_case (
  case_id          uuid PRIMARY KEY,
  question         text NOT NULL,
  expected_facts   jsonb NOT NULL,   -- facts a good answer must contain
  expected_sources jsonb NOT NULL,   -- chunk ids retrieval should fetch
  tags             text[],                -- 'rag' · 'agent' · 'redteam'
  origin           text NOT NULL,        -- 'curated' · 'prod-incident-2026-10-14'
  added_at         timestamptz NOT NULL DEFAULT now(),
  added_by         text NOT NULL         -- version it like code, own the diff
);
RUBRIC = (
    "Grade ANSWER against CONTEXT for faithfulness.\n"
    "1. List every claim in ANSWER.\n"
    "2. Mark each claim supported or unsupported by CONTEXT.\n"
    "3. Return one valid JSON object only, with no prose outside it. Schema: {\"claims\": [{\"claim\": string, \"supported\": boolean, \"evidence\": string}], \"summary\": {\"supported\": integer, \"unsupported\": integer}}. Counts must match the claim objects."
)

verdict = judge_model(RUBRIC, context=run.chunks, answer=run.answer)
# pairwise: swap A and B, run both orders, average the verdicts
def retrieval_metrics(retrieved_ids, relevant_ids):
    """Precision@k counts unique retrieved IDs; recall uses unique gold IDs."""
    retrieved = list(dict.fromkeys(retrieved_ids))
    relevant = set(relevant_ids)
    hits = sum(item in relevant for item in retrieved)
    precision = hits / len(retrieved) if retrieved else 0.0
    recall = hits / len(relevant) if relevant else None  # undefined: no gold items
    return precision, recall

# Offline fixture: one relevant hit among two unique retrieved; two gold items.
precision, recall = retrieval_metrics(["a", "x", "a"], ["a", "b"])
print(f"precision@k={precision:.2f}, recall@k={recall:.2f}")
# Expected: precision@k=0.50, recall@k=0.50
# Empty retrieval -> precision 0.0; empty relevant set -> recall None (undefined).
assert retrieval_metrics([], ["a"]) == (0.0, 0.0)
assert retrieval_metrics(["a"], [])[1] is None

This ID-based precision@k / recall@k fixture needs only labeled chunk IDs, no model judgment. Ragas has reference-based metrics (context precision/recall against reference contexts or answers) and reference-free ones (faithfulness, answer relevancy); check each metric’s required dataset fields first. See the current context precision documentation.

Pitfallsoverfitting · judge drift · the cost of measuring

  • Overfitting the golden set: you optimize 100 questions, not users. Keep the holdout, refresh quarterly from production, retire stale cases.
  • Judge drift: a silent judge update moves scores with zero code change. Pin the judge version; re-calibrate on the human sample on a schedule.
  • Cost of evals: full judge runs burn tokens and minutes. Smoke per PR, full nightly, cache verdicts, sample.
  • Flaky goldens: live APIs, unfrozen memory and unpinned models produce random reds that teach the team to ignore red.
  • Averages hide regressions: one broken query class sits behind a fine mean. Per-question diffs on every report.
  • Env mismatch: a stale corpus snapshot or a different model than production scores a system you do not run.
  • Survivorship bias online: silence is not satisfaction. Pair thumbs with task-success metrics.

Checklistthe evals review in 7 lines

  • Pyramid: component → task → system → online, cheap and broad at the base.
  • Golden set: 30-200 questions with expected facts and sources, versioned, refreshed from real failures.
  • Deterministic first: JSON parses, citations real, injections refused.
  • Judges: reasons before scores, swap order, ensemble, calibrate against humans.
  • Metrics: faithfulness, answer relevancy, context precision; context recall needs reference contexts. Split retrieval from generation.
  • CI gate on every behavior change: block on drop, per-question report, smoke per PR, full nightly.
  • Trace every run. Bad answer → trace → stage → fix → new golden case.

Try, verify, explain

  1. Create one adversarial regression case for a retrieval/tool workflow, name a measurable success metric and one human review signal that could disagree with an LLM judge.
  2. Measure position bias: take 20 answer pairs, have a judge pick the winner in A/B order, then again in B/A order. Count how often the verdict flips; that flip rate is the noise floor for any pairwise result you report.
  3. Explain why "faithfulness dropped from 0.91 to 0.78" sends you to prompts and grounding while "context recall dropped" sends you to chunking and search, and which golden-set fields make that split measurable.
