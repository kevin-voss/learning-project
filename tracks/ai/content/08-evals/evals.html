Evals & observability

Every change to an LLM system moves behavior in ways nobody can hold in their head. Evals turn that unease into numbers measured on a fixed set of questions, and traces turn a bad number into a named stage. This is the topic that makes every other topic safe to change.

Problemnon-determinism ships regressions dressed as updates
  • Change anything and everything moves. New model version, prompt edit, chunk size 800 → 600: behavior shifts silently across the whole product.
  • Vibes do not scale. A team without evals has one test, "seems fine". They either ship regressions or grow too scared to touch the prompt at all.
  • Non-determinism: the same input gives a different answer on Tuesday. One manual spot check proves nothing, only a measured score over a fixed question set is an honest signal.
  • Wrong answer, no suspects. Retrieval, tools, prompt, memory: when the answer is bad you cannot tell which one broke. Debugging without traces is guessing with extra steps.
Solutionthe evaluation pyramid, run as a CI gate on every change
  • why Four layers: component (did each part work), task (is each answer good), system (is the pipeline fast, cheap and successful end to end), online (do real users succeed). Cheap and broad at the base, expensive and rare at the top.
  • A runs the pyramid in CI: every prompt, model or retrieval change gets scored, a drop blocks the merge.
  • A trace for every run turns a red score into a named node: which query, which chunks, which tool call.

the pyramid, layer by layer

  • Component, did each part work: retrieval recall against expected chunks, tool-call validity (right tool, sane arguments, valid JSON per structured output), deterministic asserts. Fast, cheap, pinpointed.
  • Task, is each answer good: score every golden question. Rubrics and judges for the fuzzy middle, pairwise for decisions, a small human sample for calibration.
  • System, does the pipeline hold: end-to-end runs over a workload. Latency p50 and p95, tokens and cost per task next to token budgets, task success rate.
  • Online, do real users succeed: A/B on task-success metrics, weak signals like thumbs, drift watch as the corpus shifts.
  • Split retrieval from generation: "answers are bad" is unactionable. "Recall fine, faithfulness tanked" names the layer and halves the debugging time. This split is the whole game, see RAG.

the golden set, your fixed ruler

  • 30 to 200 curated questions, each with expected facts (what a good answer must contain) and expected sources (the chunks retrieval should fetch).
  • Write it before v2 of anything. Porting prompts, swapping models, tuning search and rerankers without a ruler means you cannot tell better from different.
  • Refresh from real failures: every production incident becomes a new case. Reproduce it, fix it, and the suite proves it stays fixed. The floor ratchets up.
  • Version it like code: reviewed diffs, an owner, a changelog. A golden set nobody can reproduce is a rumor, not a test.
  • Keep a holdout: a slice you never tune against, so its score measures generalization, not memorization.
  • Freeze the world around it: pinned model and judge versions, temperature 0 where possible, frozen corpus snapshot, fixed memory fixtures. Otherwise runs are not comparable.

offline evals, deterministic checks first

  • Free and unglamorous, catches plenty: does the JSON parse, is every citation real (present in the retrieved sources), does the answer mention the refund window, did each red-team prompt from prompt injection and guardrails get refused.
  • These are unit tests: plain asserts in the existing suite, run on every commit. No judge, no tokens, no flakiness.
  • Only then the fuzzy middle: faithful, complete, grounded, tone. Deterministic checks cannot grade these, that is the judge's job.

LLM-as-judge, with humility

  • grades what asserts cannot: faithful (every claim supported by context, the anti-hallucination number), complete (answers the question asked), grounded (cites real sources).
  • Position bias: in a comparison, the first answer quietly wins. Mitigation: run both orders and average.
  • Verbosity bias: longer looks better. Mitigation: a concise rubric that requires reasons before scores.
  • Self-preference: models favor outputs in their own style. Mitigation: an ensemble judge, several models vote, and pick a judge from a different family than the system under test.
  • Calibrate: hand-score a human-labeled sample, measure judge agreement, re-check whenever the judge model changes. Read absolute scores as trend lines, not gospel.

RAGAS-style metrics, plainly

  • Faithfulness: the fraction of answer claims grounded in the retrieved context. High means answers stick to sources, low means hallucination.
  • Answer relevancy: does the answer address the question actually asked, or something adjacent.
  • Context precision: of the chunks retrieved, are the useful ones ranked at the top where the prompt will actually use them.
  • Context recall: did retrieval fetch all the chunks the expected answer needs. Misses here are a retrieval problem, not a generation problem.
  • Read them as a pair: low recall fixes search, high recall with low faithfulness fixes prompts and grounding. One number alone cannot say which.

agent evals, trajectories not just answers

  • Tool-call correctness: did the agent in agent patterns call the right tool with sane arguments in a sensible order. Grade the path, not just the destination.
  • Step efficiency: loops and retries burn budget. Track steps per task alongside answer quality.
  • Compaction checks: long-session evals verify the summary still holds the decision after three compactions, see memory.

online evals, real users

  • A/B with task-success metrics: resolution rate, completed checkout, retry count. Never thumbs alone.
  • Thumbs are a weak signal: happy users click nothing, unhappy ones vanish without clicking either. Survivorship bias by design.
  • before A/B: run the candidate on duplicated requests, judge the outputs offline, zero user risk.
  • Watch drift, not averages: retrieval scores and query mix shift as the corpus and users change. A flat average can hide a newly broken query class.

regression gates in CI

  • Eval on every change: prompt edit, model bump, chunking or retrieval tweak, guardrail rule. If it changes behavior, it runs the suite.
  • Block on drop: fail the PR when any metric falls past a threshold (say 0.03) or latency and cost regress past budget.
  • Report per question, not just the mean: an average can hide one badly broken query class.
  • Stage it: a smoke subset (10-20 cases) on every PR, the full set nightly. Cache judge verdicts, they are pure cost on reruns.

A flaky red is worse than no eval. The moment a team learns red sometimes means nothing, they stop trusting green too. Fix flakiness (unfrozen fixtures, live APIs, temperature above 0) the day it appears.

observability, trace every run

  • One run, one tree: every prompt, retrieved chunk with its score, tool call and result, token counts, latency, cost. The is the difference between debugging and guessing.
  • Log what the model saw, including injected memory and retrieved context, so any past answer can be explained after the fact.
  • Tooling: LangSmith, Braintrust, OpenTelemetry. A span table you own and can query is the honest minimum.

No golden set yet? Start today with 30 questions pulled from real logs, expected facts jotted per question, deterministic asserts around them. A small ruler beats vibes immediately, and it grows with every incident you feed it.

Examplethe ruler, the judge, the report
  • Headline numbers are eval results. Anthropic's "contextual retrieval cuts retrieval failures by 49 percent" is a golden-set measurement, that is what made it shippable.
  • Support bots gate every prompt change behind a 100-ticket golden set. Regressions die in CI, not in the ticket queue.
  • Teams with trend dashboards (faithfulness next to latency and cost) refactor prompts weekly. Teams without them have not touched the prompt since launch. Be the first team.

Pitfallsoverfitting · judge drift · the cost of measuring
  • Overfitting the golden set: you optimize 100 questions, not your users. Keep the holdout, refresh quarterly from production, retire stale cases.
  • Judge drift: the judge model gets silently updated and scores move with zero code change on your side. Pin the judge version, re-calibrate on the human-labeled sample on a schedule.
  • Cost of evals: full-suite judge runs burn tokens and minutes on every PR. Smoke per PR, full nightly, cache verdicts, sample instead of scoring everything always.
  • Flaky goldens: live APIs, unfrozen memory, unpinned models produce random reds. Random reds train the team to ignore reds.
  • Averages hide regressions: one broken query class sits happily behind a fine mean. Per-question diffs on every report.
  • Env mismatch: evals on a stale corpus snapshot or a different model than production score a system you do not actually run.
  • Survivorship bias online: silence is not satisfaction. Pair thumbs with task-success metrics before believing them.
Checklistthe evals review in 7 lines
  • Pyramid: component → task → system → online. Cheap and broad at the base, rare and expensive at the top.
  • Golden set: 30-200 questions with expected facts and sources, versioned like code, refreshed from real failures.
  • Deterministic first: JSON parses, citations real, injections refused, in plain unit tests.
  • Judges: reasons before scores, swap order, ensemble, calibrate against humans, read trends not gospel.
  • Metrics: faithfulness, answer relevancy, context precision, context recall. Split retrieval from generation.
  • CI gate on every behavior change: block on drop, report per question, smoke per PR and full nightly.
  • Trace every run, prompts to chunks to tools to tokens. Bad answer → trace → stage → fix → new golden case.
