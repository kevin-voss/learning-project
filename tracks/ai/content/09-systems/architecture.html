The AI system architecture

Every earlier topic handed you a component. Systems fail between components: who owns auth, what happens when the provider throttles mid-run, where state sleeps, who watches the hops. This page is the box the components live in.

Problemsystems fail at the seams, not inside sections
  • Demo to prod gap: a notebook that answers questions is not a system. The gap is not the model, it is auth, retries, tenancy, budgets and state.
  • Seam failures: the provider 429s mid-orchestration, three tenants see each other's index slices, a deploy kills a 20-minute run. None of these live inside one component.
  • Some decisions cannot be patched later: multi-tenancy model, idempotency contract, where cost is metered. Retrofitting those under load is rewriting the plane mid-flight.
  • The opposite error: teams who fear the seams split into eight services on day one and build the most expensive hello world ever. Both failures are architecture failures.
Solutionone layered reference box · stateless middle · observable hops
  • The path: client, then edge and gateway, then orchestrator, then the model layer, retrieval, tools and memory, then the data plane. One process or ten deployables, the layers stay.
  • Stateless middle: the orchestrator owns no durable state. All of it lives in the data plane: run state, history, vectors. Any instance can die at any time, resume is a ops concern.
  • Cross-cutting, not optional: observability and security wrap every layer from day one, traces per evals, least privilege per guardrails.

Howrequest path · sync vs async · model facade · retrieval · config · traces

the request path, hop by hop

  • Edge: CDN for static assets, WAF and coarse rate limits before anything expensive runs.
  • Gateway: authn and authz, per-tenant quotas, request budgets, cost metering. Bill and alert from here, the numbers feed evals.
  • Orchestrator: the agent loop and graph execution, context assembly, memory reads and writes. Shaping the loop is graphs, this page only places it.
  • Model layer: a facade over providers, below. Never a raw vendor SDK call from business logic.
  • Tools: internal APIs and MCP servers, each scoped to least privilege, shapes and sync rules in tool calling.
  • Data plane: Postgres for run state, history and vectors. The one place truth lives.

sync vs async: two paths, one system

  • Sync path, under 2 s budget: chat answers, autocomplete, classify. The user waits. Budget the p95 so gateway, retrieval and the first streamed token land inside 2 s, tokens stream after that.
  • Async path: reindex, report generation, deep research, eval batches. Too big for a request. Push a job, a worker owns it, retries and checkpoints per ops.
  • Status channel back: job id now, results later. Poll an endpoint or push over WebSocket or SSE. The UI must show "working, 40 of 500 docs" or users resubmit and double the load.
  • Never block a sync request on async work: the request enqueues and returns the job id. The queue, not the HTTP timeout, is the boundary.

the model layer behind a facade

  • One interface, many providers: business code calls complete(messages, prefs). The facade maps to vendor SDKs, so a provider swap is a config change, not a rewrite.
  • Routing cheap vs dear by task: a classifier or heuristics send FAQ-shaped traffic to a small model and complexity to the big one. Small models can be 10× cheaper, routing is a bigger lever than prompt tuning, see tokens, cost, caching.
  • Fallback chains, not single retries: primary provider, then backup provider, then a degraded honest answer. A chain survives a vendor outage, a retry only survives a blip.
  • Streaming passes through: the facade returns streams, it never buffers them to "simplify" the interface.

retrieval: inline or service, plus cache tiers

  • Inline retrieval, a function the orchestrator calls: simplest, one deploy unit, fine until multiple consumers need the same corpus.
  • Retrieval as a service, its own API with its own index and filters: many consumers, independent scaling, one place for tenant filtering and reranking. The search mechanics are RAG overview.
  • Exact cache: hash of the normalized question to a stored answer. Nearly free, hits rarely on natural language.
  • Embedding cache: hash of the text to its vector. Embedding the same chunk twice is pure waste.
  • Semantic cache: similarity to a cached question above a high threshold serves the cached answer. Powerful, dangerous at low thresholds, judge it with evals.

config and prompts are versioned artifacts

  • Not code constants: model id, temperature, retrieval knobs, tool lists, system prompts. These change weekly, and a redeploy per tweak is a tax and an audit gap.
  • Versioned and reviewable: prompts live in the repo or a config store, tagged like code. Every trace records the versions it ran with, so an eval regression maps to a diff.
  • Rollout discipline: prompt changes ship behind a flag to a slice of traffic, get judged by evals, then promote. Same ceremony as code, because it is code.
  • Per-environment values: dev points at a cheap model and a small index, prod at the real ones. The config is the environment contract.

every hop emits a trace

  • A run is a tree: root span per request, child spans per gateway check, retrieval, model call, tool call. Latency, tokens, cost and verdicts attach per span.
  • Why architecturally: without spans every incident is archaeology and every eval is unexplainable. Wiring traces late means grep, not a dashboard.
  • Skip sampling early: full traces for the first months, the storage cost is tiny next to model spend. Practice and dashboards live in evals.
Whenmonolith first, split on evidence
  • Build monolith-first: one deployable service with clean internal modules for gateway, facade, retrieval and orchestrator, until load or team shape demands splits.
  • Split on evidence: a component that scales differently (embedding workers), fails differently (a flaky vendor adapter) or is owned by another team. Not before.
  • The box survives every stage: in a monolith the layers are modules, in microservices they are deployables. The seams stay put, so the eventual split is cheap.

Examplethe facade: routing plus fallback in one small module
PROVIDERS = ["primary", "backup"]      # different vendors: no single point of failure

def route(task):
    if task.simple:                    # classify once: FAQ-shaped traffic
        return "small-model"           # 10x cheaper, most of the traffic
    return "big-model"                 # complexity or eval signal earns the spend

def call_with_fallback(task):
    for p in PROVIDERS:               # a chain, not a single retry
        try:
            return call(p, route(task), idem_key=task.key)  # idempotent by key
        except RateLimit:
            backoff(p)                 # jittered, see ops
    return degraded_answer(task)     # honest fallback, never a hang
  • Every AI SaaS quietly converges on this shape: gateway with per-tenant budgets, stateless app tier, one facade over a provider chain, Postgres backbone.
  • One call site is the payoff: provider swap, routing change and spend caps are each a one-file diff, not an incident.
Pitfallsdistributed hello world · hidden coupling · buffering proxies
  • Distributed hello world: eight services, a mesh and an event bus serving 40 requests a day. Every hop adds latency, auth, tracing and on-call surface. Split on evidence.
  • Hidden coupling via a shared DB: two "independent" services where one reads the other's tables. The schema is now a public contract nobody versioned. Own the split or stay one service.
  • Buffering proxies: SSE through a proxy that batches responses destroys token-by-token UX. Test streaming through the real path, many gateways need explicit no-buffering config.
  • Tenancy retrofitted: per-tenant filters bolted onto a populated index after one customer sees another's data. Design filters into retrieval from day one.
  • Double side effects: a retry executes a tool twice, two refunds, two emails. Idempotency keys on every mutation, per ops.
  • Config as constants: prompt tweaks require redeploys, so people stop tweaking. Versioned artifacts with flags keep the iteration loop alive.
  • Traces bolted on late: the first 3am incident without spans is where you learn this, expensively.
Checklistseven bullets to remember
  • Layered box: client, edge and gateway, orchestrator, model layer, retrieval, tools, memory, data plane
  • Sync under 2 s and streamed, anything longer is a queued job with a status channel
  • One model facade: routing cheap vs dear, fallback chain, honest degraded answer at the end
  • Cache tiers in order: exact, embedding, semantic with a high threshold
  • Prompts and config are versioned artifacts, versions recorded per trace
  • Every hop emits a span with latency, tokens and cost
  • Monolith with clean seams first, split on load or team evidence
