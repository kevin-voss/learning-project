The AI system architecture

Every earlier topic handed you a component. Systems fail between components: who owns auth, what happens when the provider throttles mid-run, where state sleeps, who watches the hops. This page is the box the components live in.

In this chapter Trace request and data paths across client, model, retrieval, tools and storage; place reliability and policy controls at boundaries.

Problemsystems fail at the seams, not inside sections

  • Demo to prod gap: a notebook that answers questions is not a system. The gap is auth, retries, tenancy, budgets and state, not the model.
  • Seam failures: the provider 429s mid-orchestration, tenants see each other's index slices, a deploy kills a 20-minute run. None live inside one component.
  • Some decisions cannot be patched later: tenancy model, idempotency contract, where cost is metered. Retrofitting them under load is rebuilding the plane mid-flight.
  • The opposite error: teams who fear the seams split into eight services on day one and build the most expensive hello world ever.

Solutionone layered reference box · stateless middle · observable hops

  • The path: client, edge and gateway, orchestrator, then model layer, retrieval, tools and memory, then the data plane. One process or ten deployables, the layers stay.
  • Stateless middle: the orchestrator owns no durable state; run state, history and vectors live in the data plane. Any instance can die anytime; resume is an ops concern.
  • Cross-cutting from day one: traces on every layer per evals, least privilege per guardrails.

Requests enter at the top, durable state lives at the bottom, the middle can be killed and replaced anytime. The AWS mapping of this box is full systems on AWS.

Howrequest path · sync vs async · model facade · retrieval · config · traces

the request path, hop by hop

  • Edge: CDN for static assets, WAF and coarse rate limits before anything expensive runs.
  • Gateway: authn and authz, per-tenant quotas, request budgets, cost metering. Bill and alert from here; the numbers feed evals.
  • Orchestrator: agent loop and graph execution, context assembly, memory reads and writes. Shaping the loop is graphs; this page only places it.
  • Model layer: a facade over providers, below. Never a raw vendor SDK call from business logic.
  • Tools: internal APIs and MCP servers, each least-privilege; shapes and sync rules in tool calling.
  • Data plane: Postgres for run state, history and vectors, the one place truth lives.

sync vs async: two paths, one system

  • Sync path, under 2 s: chat, autocomplete, classify; the user waits. Budget p95 so gateway, retrieval and the first streamed token land inside 2 s.
  • Async path: reindex, reports, deep research, eval batches. Push a job; a worker owns it, with retries and checkpoints per ops.
  • Status channel back: job id now, results later, by polling or WebSocket/SSE push. Show "working, 40 of 500 docs" or users resubmit and double the load.
  • Never block a sync request on async work: enqueue and return the job id. The queue, not the HTTP timeout, is the boundary.

the model layer behind a facade

  • One interface, many providers: business code calls complete(messages, prefs); the facade maps to vendor SDKs, so a provider swap is a config change.
  • Route cheap vs dear by task: a classifier or heuristics send FAQ-shaped traffic to a small model, complexity to the big one. Small models can be 10× cheaper, so routing often beats prompt tuning, see tokens, cost, caching.
  • Fallback chains, not single retries: primary provider, backup provider, then an honest degraded answer. A chain survives an outage; a retry only survives a blip.
  • Streaming passes through: the facade returns streams and never buffers them.

retrieval: inline or service, plus cache tiers

  • Inline retrieval, a function the orchestrator calls: simplest, fine until several consumers need the same corpus.
  • Retrieval as a service, with its own API, index and filters: many consumers, independent scaling, one place for tenant filtering and reranking. Mechanics in RAG overview.
  • Exact cache: hash a normalized request to a stored answer. A hit skips model tokens, but lookup, storage, freshness, privacy and invalidation have costs, and natural-language queries may rarely repeat.
  • Embedding cache: text hash to vector. Embedding the same chunk twice is pure waste.
  • Semantic cache: a question similar to a cached one above a high threshold gets the cached answer. Dangerous at low thresholds; judge it with evals.

config and prompts are versioned artifacts

  • Not code constants: model id, temperature, retrieval knobs, tool lists, system prompts change weekly; a redeploy per tweak is a tax and an audit gap.
  • Versioned and reviewable: prompts live in the repo or a config store, tagged like code. Every trace records its versions, so an eval regression maps to a diff.
  • Rollout discipline: prompt changes ship behind a flag to a traffic slice, get judged by evals, then promote. Same ceremony as code.
  • Per-environment values: dev uses a cheap model and small index, prod the real ones. Config is the environment contract.

every hop emits a trace

  • A run is a tree: root span per request, child spans per gateway check, retrieval, model call and tool call, each carrying latency, tokens, cost and verdicts.
  • Why architecturally: without spans every incident is archaeology and every eval unexplainable.
  • Skip sampling early: keep full traces for the first months; storage is tiny next to model spend. Dashboards live in evals.

Whenmonolith first, split on evidence

  • Build monolith-first: one deployable with clean modules for gateway, facade, retrieval and orchestrator, until load or team shape demands splits.
  • Split on evidence: a component that scales differently (embedding workers), fails differently (a flaky vendor adapter) or belongs to another team.
  • The box survives every stage: layers are modules in a monolith and deployables later. The seams stay put, so the split is cheap.

Examplethe facade: routing plus fallback in one small module

PROVIDERS = ["primary", "backup"]      # different vendors: no single point of failure

def route(task):
    if task.simple:                    # classify once: FAQ-shaped traffic
        return "small-model"           # 10x cheaper, most of the traffic
    return "big-model"                 # complexity or eval signal earns the spend

def call_with_fallback(task):
    for p in PROVIDERS:               # a chain, not a single retry
        try:
            return call(p, route(task), idem_key=task.key)  # idempotent by key
        except RateLimit:
            backoff(p)                 # jittered, see ops
    return degraded_answer(task)     # honest fallback, never a hang
  • Most AI SaaS converges on this shape: gateway with per-tenant budgets, stateless app tier, one facade over a provider chain, Postgres backbone.
  • One call site is the payoff: provider swap, routing change and spend caps are each a one-file diff.

Pitfallsdistributed hello world · hidden coupling · buffering proxies

  • Distributed hello world: eight services, a mesh and an event bus serving 40 requests a day. Every hop adds latency, auth, tracing and on-call surface.
  • Hidden coupling via a shared DB: one "independent" service reads the other's tables, making the schema an unversioned public contract. Own the split or stay one service.
  • Buffering proxies: a proxy that batches SSE destroys token-by-token UX. Test streaming through the real path; many gateways need explicit no-buffering config.
  • Tenancy retrofitted: per-tenant filters bolted on after one customer sees another's data. Design them into retrieval from day one.
  • Double side effects: a retry runs a tool twice: two refunds, two emails. Idempotency keys on every mutation, per ops.
  • Config as constants: prompt tweaks need redeploys, so people stop tweaking. Versioned artifacts with flags keep iteration alive.
  • Traces bolted on late: you learn this at the first 3am incident without spans.

Checklistseven bullets to remember

  • Layered box: client, edge, gateway, orchestrator, model layer, retrieval, tools, memory, data plane
  • Sync under 2 s and streamed; anything longer is a queued job with a status channel
  • One model facade: cheap vs dear routing, fallback chain, honest degraded answer
  • Cache tiers in order: exact, embedding, semantic with a high threshold
  • Prompts and config are versioned artifacts, recorded per trace
  • Every hop emits a span with latency, tokens and cost
  • Monolith with clean seams first, split on load or team evidence

Try, verify, explain

  1. Trace a request from client through model, retrieval, tool execution and durable storage. Mark the tenant identity source and each place it must be checked.
  2. Build a 2 s sync budget: take p95 values for gateway auth, retrieval plus rerank and the provider's time to first token (from your traces or a 20-request test), sum them, and see how much headroom remains for context assembly.
  3. Explain why a fallback chain survives a provider outage when a retry does not, and why the call must carry an idempotency key once a tool with side effects sits behind it.
