Full systems on AWS

The layered box from the AI system architecture, now with AWS names on the hops. Same seams, same queues, same traces, one ingest path and one query path.

Problema working notebook is not a system
  • Friday 18:00: 10,000 documents arrive at once. The ingest melts, or it eats the budget, or both.
  • Monday: a 20-minute agent run dies mid-deploy, the answer stream times out behind the load balancer, and API keys sit in a repo.
  • Nobody knows which run cost 38 dollars or why the same PDF got processed twice.
  • None of these are model problems. All of them are composition problems, the difference between a demo and a product.
Solutionmanaged piece per job · queues as shock absorbers
  • Ingest is a pipeline: object storage absorbs uploads, a queue absorbs the burst, stateless workers parse, chunk and embed, an index serves queries. Ingestion mechanics per RAG overview.
  • Queries are a path: API edge, orchestrator compute, retrieval from the index, model access, tokens streamed back.
  • Long work is jobs: queues plus worker fleets plus DLQs, the durable discipline of ops with AWS service names.

Ingest on top (async, queued, rate-limited by the queue), query below (sync, streamed), one shared index in the middle. Two paths, one system.

Howingest · query · async jobs · state · scopes · cost

the document RAG pipeline, stage by stage

  • S3 for source docs: durable, cheap, versioned, event-capable. Every later stage re-derives from here, so S3 is the source of truth for content.
  • Event into a queue, not into compute: S3 notifications land in SQS. Without the queue, one upload spike means 10,000 concurrent parse jobs, dead rate limits and a spiked bill. The queue IS the rate limiter.
  • Parse workers: Lambda for small, quick, bursty parsing (15-minute hard cap), Fargate or ECS containers for giant PDFs and layout models.
  • Chunk and embed workers on a second queue: parsing is CPU-bound, embedding is API-bound with provider rate limits, so the stages scale on different knobs. Sizing choices live in chunking and embeddings.
  • Index: OpenSearch for managed hybrid search (lexical plus k-NN), or Aurora Postgres with pgvector when the one-database story matters more than raw scale.
  • Incremental reindex: content hash plus doc version in a registry. Unchanged doc means skip. Re-embed only when the doc or the embedding model changed, and treat a model swap as a planned backfill job, never a surprise full rebuild.
  • gotcha S3 events are at-least-once. The same upload can notify twice. The worker dedupes on the registry key, deletes the duplicate message, moves on.

the query path

  • Edge: API Gateway plus a WAF for simple request/response entry, or an ALB when answers stream for minutes.
  • Compute: Lambda fits short orchestrations, containers on ECS or Fargate fit stateful long-lived orchestrators and streaming connections.
  • Model access: Bedrock for VPC-only reachability and IAM-authenticated model calls, or an external LLM behind the facade from the architecture page when a niche model demands it.
  • Stream the answer back: SSE from the orchestrator through the edge to the client. First token inside the sync budget, tokens stream after.
  • gotcha API Gateway caps integrations near 29 seconds. Long streams get cut. Route them through an ALB or a WebSocket API, keep API Gateway for short control calls.

async agent jobs

  • SQS work queues plus a worker fleet: deep research, report generation, batch evals. Workers checkpoint progress so a die-off resumes rather than restarts, mechanics per ops.
  • DLQ plus redrive: maxReceiveCount near 3, park poison messages, inspect with the trace, fix the cause, replay fixed batches. An unwatched DLQ is a landfill.
  • Fan-out: Step Functions Map for per-item retries over big batches (eval suites), or plain queue batching, receive up to 10, with per-item failure handling.
  • Human gates: Step Functions waitForTaskToken pauses a flow for minutes or days and resumes on the approver's callback, the AWS shape of a HITL gate.
  • Visibility timeout above worst-case work: a job longer than its timeout gets redelivered and runs twice concurrently. Heartbeat extensions for long jobs.

state

  • Aurora Postgres is the anchor: app state, run checkpoints and pgvector knowledge in one place, so tenant rules and permission filters join the vector search in one transaction.
  • DynamoDB for sessions: single-key session or conversation state with a TTL, high churn, no joins. One purpose, never the system of record.

secrets and scopes

  • IAM role per worker type: the parse worker reads S3 and writes the registry, the embed worker calls the model API, and neither can do the other's job. Least privilege per guardrails.
  • No long-lived keys in env vars or task definitions: task execution roles and Secrets Manager instead, rotation without redeploying consumers.
  • VPC endpoints keep model and index traffic off the public internet, which is also how compliance reviews end quickly.

cost and latency notes

  • Batch embedding: many inputs per API call where the provider allows it, fewer calls, better throughput against rate limits.
  • Cache before you call: embedding cache for repeated text, exact answer cache before semantic, per the architecture page.
  • Route by model size: small model as the default lane, big model on complexity signal. Model choice dominates cost per query.
  • Alarms that matter: queue depth (backlog forming), DLQ above zero (poison), per-run spend (runaway loops), index write rejections (throttling).

Examplethe whole ingest discipline in one worker loop
import boto3, hashlib
sqs = boto3.client("sqs")

while True:
    msgs = sqs.receive_message(
        QueueUrl=Q, MaxNumberOfMessages=10,
        VisibilityTimeout=900,          # 15 min, above worst-case work
        WaitTimeSeconds=20,                # long poll: no busy-spin, no cost
    ).get("Messages", [])

    for m in msgs:
        key = hashlib.sha256(m["Body"].encode()).hexdigest()
        if not registry.try_insert(key):       # at-least-once: dedupe first
            sqs.delete_message(Q, m["ReceiptHandle"])  # already done: skip
            continue
        process(m["Body"])                   # parse, chunk, embed, index
        sqs.delete_message(Q, m["ReceiptHandle"])  # success means delete
        # crash before delete: message reappears, retried, then DLQ
  • In the field: quarterly filings arrive as a Friday spike of 40,000 documents, the queue drips them through parsing and embedding all weekend, Monday's search works and nobody was paged.
  • Same shape nightly for e-commerce catalogs, so "cozy winter jacket" finds the right SKU by morning.
  • The agent flavor: query path plus async jobs, a PR comment lands in a queue, a worker runs the fix agent, a task-token gate holds the merge for a human.
Pitfallscross-region hops · reindex storms · throttles
  • Cross-region latency: docs in one region, index or workers in another, every hop pays inter-region round trips and transfer fees. Pick one region, and check model availability there before you design around it.
  • Reindex storms: a deploy or config tweak triggers a full rebuild, thousands of embedding calls and index writes at once. Incremental by hash, backfills as budgeted background jobs.
  • Throttles from every side: Lambda concurrency, embedding provider rate limits, index bulk-write queues. The fixes are one shape: queue in front, sensible batch size, backoff with jitter per ops.
  • The 29-second cut: long streamed answers routed through API Gateway die at the integration cap. ALB or WebSocket for streams.
  • Visibility timeout below the job: the queue hands the in-flight message to a second worker, double processing at full concurrency.
  • At-least-once everywhere: S3 events, SQS redelivery, EventBridge. Any worker that is not idempotent will eventually bill someone twice.
  • Secrets in task definitions: convenient, then leaked in a log line or a copy-pasted config. Task roles and Secrets Manager, always.
Checklistseven bullets to remember
  • Queue between upload and workers, the queue is the rate limiter
  • Two ingest stages, parse CPU-bound and embed API-bound, on separate scaling
  • Idempotent workers: registry hash, delete on done, DLQ at about 3, redrive tested
  • Incremental reindex by content hash, embedding model swaps are planned backfills
  • Streams through ALB or WebSocket, API Gateway for short calls only
  • Aurora Postgres for state plus pgvector, DynamoDB only for TTL session state
  • IAM role per worker, least privilege, batch embeddings, small-model default lane
