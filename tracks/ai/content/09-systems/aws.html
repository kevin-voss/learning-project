Full systems on AWS

The layered box from the AI system architecture, now with AWS names on the hops. Same seams, same queues, same traces, one ingest path and one query path.

In this chapter Map ingestion and query responsibilities onto AWS services while reasoning about identity, network, scaling and failure boundaries.

Problema working notebook is not a system

  • Friday 18:00: 10,000 documents arrive at once. Ingest melts, eats the budget, or both.
  • Monday: a 20-minute agent run dies mid-deploy, the answer stream times out at the load balancer, and API keys sit in a repo.
  • Nobody knows which run cost 38 dollars or why the same PDF got processed twice.
  • None of these are model problems. They are composition problems: the gap between demo and product.

Solutionmanaged piece per job · queues as shock absorbers

  • Ingest is a pipeline: object storage absorbs uploads, a queue absorbs the burst, stateless workers parse, chunk and embed, an index serves queries. Mechanics per RAG overview.
  • Queries are a path: API edge, orchestrator compute, retrieval from the index, model access, tokens streamed back.
  • Long work is jobs: queues, worker fleets and DLQs: the discipline of ops with AWS names.

Ingest on the left (async, paced by queues), query on the right (sync, streamed), one shared index where they meet. Parse runs on Lambda or Fargate, the orchestrator on Lambda or ECS, the index on OpenSearch or Aurora pgvector, and agent workers checkpoint to Aurora Postgres.

Howingest · query · async jobs · state · scopes · cost

the document RAG pipeline, stage by stage

  • S3 for source docs: durable, cheap, versioned, event-capable. Every later stage re-derives from here; S3 is the source of truth for content.
  • Event into a queue, not into compute: S3 notifications land in SQS. Without it, one upload spike means 10,000 concurrent parse jobs, blown rate limits and a spiked bill. The queue IS the rate limiter.
  • Parse workers: Lambda for small, bursty parsing (15-minute hard cap), Fargate or ECS containers for giant PDFs and layout models.
  • Chunk and embed on a second queue: parsing is CPU-bound, embedding is bound by provider rate limits, so the stages scale on different knobs. Sizing in chunking and embeddings.
  • Index: OpenSearch for managed hybrid search (lexical plus k-NN), or Aurora Postgres with pgvector when one database matters more than raw scale.
  • Incremental reindex: content hash plus doc version in a registry; unchanged means skip. Re-embed only when the doc or embedding model changed, and treat a model swap as a planned backfill, never a surprise rebuild.
  • gotcha S3 events are at-least-once. The same upload can notify twice. Workers key on a stable business work ID, process idempotently and acknowledge only after durable completion, so a crash leaves retryable work.

the query path

  • Edge: API Gateway plus a WAF for simple request/response entry, or an ALB when answers stream for minutes.
  • Compute: Lambda for short orchestrations, ECS or Fargate containers for long-lived orchestrators and streaming connections.
  • Model access: Bedrock for VPC-only reachability and IAM-authenticated calls, or an external LLM behind the architecture page facade when a niche model demands it.
  • Stream the answer back: SSE from orchestrator through edge to client, first token inside the sync budget.
  • gotcha API Gateway caps integrations near 29 seconds. Long streams get cut: route them through an ALB or WebSocket API, keep API Gateway for short calls.

async agent jobs

  • SQS work queues plus a worker fleet: deep research, reports, batch evals. Workers checkpoint so a die-off resumes rather than restarts, per ops.
  • DLQ plus redrive: maxReceiveCount near 3 parks poison messages; inspect with the trace, fix the cause, replay. An unwatched DLQ is a landfill.
  • Fan-out: Step Functions Map for per-item retries over big batches (eval suites), or plain queue batches of up to 10 with per-item failure handling.
  • Human gates: Step Functions waitForTaskToken pauses a flow for minutes or days until the approver's callback: the AWS shape of a HITL gate.
  • Visibility timeout above worst-case work: a longer job is redelivered and runs twice concurrently. Extend by heartbeat for long jobs.

state

  • Aurora Postgres is the anchor: app state, run checkpoints and pgvector in one place, so tenant and permission filters join the vector search in one transaction.
  • DynamoDB for sessions: single-key session state with a TTL, high churn, no joins. Never the system of record.

secrets and scopes

  • IAM role per worker type: the parse worker reads S3 and writes the registry, the embed worker calls the model API, neither can do the other's job. Least privilege per guardrails.
  • No long-lived keys in env vars or task definitions: task roles and Secrets Manager, rotation without redeploys.
  • VPC endpoints keep model and index traffic off the public internet, which also shortens compliance reviews.

cost and latency notes

  • Batch embedding: many inputs per call where the provider allows, for better throughput against rate limits.
  • Cache before you call: embedding cache for repeated text, exact answer cache before semantic, per the architecture page.
  • Route by model size: small model by default, big model on a complexity signal. Model choice dominates cost per query.
  • Alarms that matter: queue depth (backlog), DLQ above zero (poison), per-run spend (runaway loops), index write rejections (throttling).

Examplethe whole ingest discipline in one worker loop

import boto3, hashlib
sqs = boto3.client("sqs")

while True:
    msgs = sqs.receive_message(
        QueueUrl=Q, MaxNumberOfMessages=10,
        VisibilityTimeout=900,          # 15 min, above worst-case work
        WaitTimeSeconds=20,                # long poll: fewer empty receives, request charges still apply
    ).get("Messages", [])

    for m in msgs:
        work_id = stable_business_work_id(m["Body"])
        # Contract: effects + durable completion commit atomically by work_id.
        # Concurrent duplicates serialize; incomplete work remains retryable.
        process_idempotently(work_id, m["Body"])
        # Acknowledge only after durable completion; crashes before here retry safely.
        sqs.delete_message(QueueUrl=Q, ReceiptHandle=m["ReceiptHandle"])
  • In the field: a Friday spike of 40,000 quarterly filings drips through parsing and embedding all weekend; Monday's search works and nobody was paged.
  • Same shape nightly for e-commerce catalogs, so "cozy winter jacket" finds the right SKU by morning.
  • The agent flavor: a PR comment lands in a queue, a worker runs the fix agent, a task-token gate holds the merge for a human.

Pitfallscross-region hops · reindex storms · throttles

  • Cross-region latency: docs in one region and index or workers in another means every hop pays round trips and transfer fees. Pick one region, after checking model availability there.
  • Reindex storms: a deploy or config tweak triggers a full rebuild: thousands of embedding calls and index writes at once. Incremental by hash, backfills as budgeted jobs.
  • Throttles from every side: Lambda concurrency, embedding rate limits, index bulk-write queues. One fix shape: queue in front, sensible batches, jittered backoff per ops.
  • The 29-second cut: long streams through API Gateway die at the integration cap. ALB or WebSocket for streams.
  • Visibility timeout below the job: the in-flight message goes to a second worker: double processing.
  • At-least-once everywhere: S3 events, SQS redelivery, EventBridge. A non-idempotent worker will eventually bill someone twice.
  • Secrets in task definitions: convenient, then leaked in a log line or pasted config. Task roles and Secrets Manager, always.

Checklistseven bullets to remember

  • Queue between upload and workers, the queue is the rate limiter
  • Two ingest stages, CPU-bound parse and API-bound embed, scaled separately
  • Idempotent workers: registry hash, delete on done, DLQ at about 3, tested redrive
  • Incremental reindex by content hash, embedding model swaps are planned backfills
  • Streams through ALB or WebSocket, API Gateway for short calls only
  • Aurora Postgres for state plus pgvector, DynamoDB only for TTL session state
  • IAM role per worker, batch embeddings, small model by default

Try, verify, explain

  1. For an AWS document-answering service, assign ingestion, object storage, vector retrieval, model inference, identity and audit responsibilities; identify one regional failure mode.
  2. Size the queue: if 10,000 documents land at once, each parse takes 20 s and you allow 50 concurrent workers, compute the drain time, then pick a visibility timeout from the worst-case parse time and check the DLQ threshold against it.
  3. Explain why S3 events plus SQS can process the same upload twice, and what the stable work ID and "acknowledge after durable completion" each prevent.
